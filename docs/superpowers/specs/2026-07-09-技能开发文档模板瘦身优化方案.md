# 技能开发文档模板瘦身优化方案

## 方案概述

本方案目标是收缩 Nocturnel 技能开发文档当前过度膨胀的正文结构，把文档从“过程留痕载体”调整为“高价值设计决策载体”。重点解决当前 `dev_doc` 中引用清单、字段补齐清单、重复同步提醒等内容占比过高的问题，同时保留完整评分过程，但将其调整为“结论前置、完整依据后置”的结构，确保真正有复用价值的信息优先出现。

范围包括三部分：

1. 现有技能开发文档正文的信息分层与冗余识别。
2. 技能开发文档模板本身的结构重构与段落裁剪原则。
3. 与模板直接耦合的设计指南、评分模板和执行规范的同步调整建议。

各阶段任务概要如下：

1. 现状取证：对比新长模板与旧短模板，区分哪些段落在长期复查时真正有价值。
2. 结构收敛：定义新的正文主结构，明确前置、后置、删除和下沉内容。
3. 规则对齐：指出需要同步修改的指南与模板约束，避免后续新文档再次被流程性要求推胖。

整体结构框架建议改为“摘要前置、规则前置、预算前置、风险前置、过程后置”的五层结构：

1. 技能摘要
2. 正式规则
3. 预算账本
4. 风险与待确认
5. 评分结论前置、完整评分后置

完整 BU 预算模型、分值表、校准流程和评分衔接统一由 Nocturnel 的 [技能预算指南（AI 专用）](C:/Code/Nocturnel/项目文档/标准&指南/技能预算指南（AI%20专用）.md) 维护。技能开发文档只写该技能自己的预算账本，不复制预算指南内容。

---

## 一、现状诊断

### 1.1 当前冗余的主要表现

当前技能开发文档已经出现明显的双峰结构：

- 旧文档多为“基本信息 + 开发记录 + 评分记录 + 待办”的短模板。
- 新文档开始叠加“设计依据 + 引用清单 + 数值补全记录 + 完整评分记录 + 本次覆盖内容”等大段过程性内容。

以 `skill_axe_throw.md` 为代表的新模板，正文已经显著偏向“完整审计报告”，而不是“长期可复用的开发文档”。这会直接带来三个问题：

1. 用户打开文档后，前半屏看不到最关键的玩法定位和正式规则结论。
2. 文档内容和 `data/skills.json`、评分规则、对话 checkpoint 大量重复。
3. 后续维护者很难快速区分“这是正式规则”还是“这是当时的一次性分析过程”。

### 1.2 当前信息类型的价值分层

结合现有样本文档和数据规范，可以把正文内容分成四类：

#### A. 高价值长期信息

这类内容应保留在正文前部：

- 技能的玩法定位与职责
- 正式规则摘要
- 正式规则与特殊边界
- 该技能自己的预算账本与预算结论
- 当前风险、待确认项、投放前门槛
- 最终评分结论及其核心理由

#### B. 中价值补充信息

这类内容可以保留，但应后置或压缩：

- 关键对照样本
- 重要设计依据
- 少量开发时间线

#### C. 低价值过程信息

这类内容不适合长期留在正文：

- 引用清单的逐项展开
- 本次补全字段清单
- “本次覆盖内容”总结
- 对每一个字段的回填流水账

#### D. 仓库级重复规则

这类内容不应出现在单篇文档中：

- `dev_doc` 路径同步提醒
- Notion `#开发文档` 对齐提醒
- “评分后同步更新 `rating` 字段”这类流程要求

这些规则应保留在 skill 指南、truth 或仓库级执行规范中，而不是每篇文档重复一遍。

## 二、冗余来源分析

### 2.1 引用清单被错误持久化

`技能设计指南（AI 专用）` 当前把“引用清单 checkpoint”定义为开工前的强制动作。这本来是设计过程中的真实性预检，但在实际产出中被抄进了最终 `dev_doc` 正文，导致：

- 正文前部被大量来源说明占据
- 与真实设计结论相比，阅读优先级倒置
- 长期复查时几乎没有新增信息价值

结论：引用清单应该保留为执行前 checkpoint，不应作为默认正文段落。

### 2.2 字段补齐过程和正式数据重复

`数值补全记录` 里的大量内容，实际上已经在 `data/skills.json` 中存在稳定落点，例如：

- `ap_cost`
- `cooldown`
- `mana_cost`
- `tags`
- `nodes`
- `rating`

如果正文只是逐项抄写这些结果，就相当于把数据文件重新写一遍，信息增量很低。

结论：正文只保留“为什么这样定”，不再保留“具体补了哪些字段”的流水账。

### 2.3 完整评分模板默认过重

`技能(玩家)品质标准（AI专用）` 当前提供的是完整评分模板，包含：

- 红线检查
- 横向样本
- 分项得分表
- 修改建议
- 覆盖内容

这套模板适合作为完整评审记录，但不适合作为所有技能文档的默认正文。对“普通合格技能”而言，完整大表会把“结论”埋到很后面。

结论：完整评分内容应继续保留在 `dev_doc` 中，但需要把“评分结论摘要”和“完整评分展开”拆成前后两层，而不是让完整评分大表占据正文主路径。

### 2.4 单文档承担了过多角色

当前 `dev_doc` 实际上被混合要求承担了四个角色：

1. 开发文档
2. 审计记录
3. 评分记录
4. 字段变更说明

角色混合会导致正文越来越长，因为每个流程都在向文档加自己的必填段落。

结论：需要重新划清边界，让 `dev_doc` 回到“设计决策文档”的主职责。

## 三、优化目标

优化后的技能开发文档应满足以下目标：

1. 打开文档前半屏就能看懂“这是什么技能、为什么这样设计、现在风险是什么”。
2. 不重复抄写已稳定存在于 `data/skills.json` 的字段事实。
3. 把一次性检查过程下沉到对话、评审记录或附录。
4. 保留完整评分依据，确保读者仍能检查评分过程和判断逻辑是否合理。
5. 让后续维护者可以快速判断该技能是否还能继续投放、复评或改动。

## 四、推荐的新正文结构

建议将技能开发文档正文统一收敛为以下结构。

### 4.1 一级结构

```markdown
# <skill_id>

## 技能摘要

## 正式规则

## 预算账本

## 风险与待确认

## 评分结论摘要

## 完整评分记录

## 附录：开发记录（可选）
```

### 4.2 各段落职责

#### 1. 技能摘要

放在最前面，只保留高价值结论：

- 技能名
- 技能 ID
- 一句话玩法定位
- 当前状态：保留 / 待投放 / 待复评 / 废案
- 最关键的 1 到 3 条设计边界

这一段的目标是让读者在 20 秒内知道“这技能是干什么的”。

#### 2. 正式规则

这一段只写正式结论，不写字段流水账：

- 正式效果摘要
- 特殊边界
- 必要的机制口径说明

这里的重点是“规则是什么”，不是“本次改了哪些字段”。

#### 3. 预算账本

这一段前置到风险与评分之前，用于解释该技能是否在预算上成立：

- 可用预算
- 消耗预算
- 差额
- 判定
- 待数据
- 必要的横向比较样本

完整 BU 分值表不写在单篇 `dev_doc` 中，必须回源 [技能预算指南（AI 专用）](C:/Code/Nocturnel/项目文档/标准&指南/技能预算指南（AI%20专用）.md)。当前可参考 [skill_axe_throw.md](C:/Code/Nocturnel/项目文档/开发/技能/skill_axe_throw.md) 的 235/235 BU 样例。

#### 4. 风险与待确认

这一段提前放到正文中部，而不是尾部：

- 当前最大风险
- 尚未验证的强度点
- 进入真实奖励池前必须完成的验证

它比完整评分细节更值得前置，因为它直接影响后续是否继续使用该技能。

#### 5. 评分结论摘要

这一段默认前置，只保留：

- 评分结论
- 2 到 4 条核心理由
- 是否需要完整复评

它的作用是让读者先看到结论，再决定是否继续查看完整评分展开。

#### 6. 完整评分记录

完整评分内容继续保留在同一篇 `dev_doc` 里，但统一放到正文后段，包含：

- 红线检查
- 横向比较样本
- 分项得分表
- 主要问题
- 修改建议
- 待回源项

这样既保留完整评审依据，也不会让正文前半段被大表压住。

#### 7. 附录：开发记录

把时间线、回源线索和历史动作放在最后：

- 关键日期
- 重要改动说明
- 必要的迁移备注

附录是可选的，不再承载正文的主要信息密度。

## 五、建议删除、后置和下沉的内容

### 5.1 建议从正文默认删除

以下内容建议不再默认生成：

1. `引用清单`
2. `本次补全字段`
3. `本次覆盖内容`
4. 冗长的“同 AP / 同类型 / 同环境”样本清单
5. `dev_doc` / Notion 同步提醒
6. 完整 BU 分值表或预算指南全文复制

### 5.2 建议改为后置或附录

以下内容可保留，但必须后置：

1. 开发时间线
2. 历史回源说明
3. 少量关键对照样本

### 5.3 建议下沉到其他载体

以下内容建议迁出 `dev_doc` 正文：

1. 引用清单
   - 下沉到对话阶段的真实性 checkpoint
2. 仓库级流程提醒
   - 下沉到 skill 指南、truth 或执行规范

## 六、需要同步调整的指南与模板

### 6.1 调整 `技能设计指南（AI 专用）`

建议修改点：

- 保留“引用清单 checkpoint”作为执行前强制动作。
- 明确说明：引用清单默认不写入最终 `dev_doc` 正文，除非该条目本身存在真实性争议，必须保留回源锚点。

理由：

- 这样可以保留真实性门禁，但不把过程检查误当成长期文档内容。

### 6.2 调整 `技能(玩家)品质标准（AI专用）`

建议把“评分记录模板”调整成单文档内的双层结构：

#### 评分结论摘要层

始终前置，保留：

- 评分结论
- 核心理由
- 是否存在待验证点

#### 完整评分展开层

始终保留在后部，继续包含：

- 红线检查
- 横向样本
- 分项得分表
- 主要问题
- 修改建议
- 待回源项

理由：

- 这样既不会丢失评分依据，也能避免读者在打开文档时先被完整评审大表阻塞。

### 6.3 调整预算相关职责边界

最新收口后，不建议把完整预算模型分别写进 `战斗数值平衡手册`、`技能设计指南` 和 `技能(玩家)品质标准`。

职责应拆成：

| 文档 | 职责 |
|---|---|
| `技能预算指南（AI 专用）` | 唯一维护 BU 模型、分值表、账本模板、校准流程和预算评分衔接 |
| `战斗数值平衡手册 2.0（AI 专用）` | 维护伤害公式、AP 效率、层级数值锚点和数值红线 |
| `技能设计指南（AI 专用）` | 维护技能设计流程、字段语义、标签要求和输出模板入口 |
| `技能(玩家)品质标准（AI专用）` | 维护评分流程、评分维度和完整评分记录 |

理由：

- 预算模型会持续校准，单点维护能降低漂移风险。
- 其他指南保留入口和边界即可，避免文档体积继续膨胀。

### 6.4 调整 `data-design-skill-player` 或对应执行模板

建议修改点：

- 默认产物改为“摘要型开发文档”
- 不再自动生成完整引用清单
- 生成 `预算账本`，但只填写当前技能账本，不复制预算指南分值表
- 保留完整评分矩阵，但统一移动到评分结论摘要之后

理由：

- 如果模板生成器不改，单靠人工约束，文档仍会继续被流程推胖。

## 八、落地建议

建议按以下顺序实施：

### Phase A：先冻结新模板原则

- 确认 `dev_doc` 的主职责是“设计决策摘要 + 风险入口”
- 不再把过程性 checkpoint 默认写入正文

### Phase B：改指南与生成模板

- 改 `技能设计指南（AI 专用）`
- 改 `技能(玩家)品质标准（AI专用）`
- 保持 `技能预算指南（AI 专用）` 为完整预算模型唯一维护入口
- 改 `data-design-skill-player` 的默认输出模板

### Phase C：用少量样本回填验证

- 选 2 到 3 份代表性技能文档试填
- 优先以 `skill_axe_throw.md` 作为正式 BU 样例，再扩展到同池校准样本
- 验证是否还能支持评分、回源和后续复评

### Phase D：再决定是否批量迁移历史文档

- 若新模板稳定，再决定是否只迁移新文档
- 默认不建议立刻批量重写旧文档

## 九、预期效果

按本方案收缩后，技能开发文档应出现以下变化：

1. 正文长度明显下降，重点从“过程说明”转回“设计结论”。
2. 前半屏即可读到技能定位、规则、风险和评分结论。
3. 与 `data/skills.json` 的重复描述显著减少。
4. 评分过程继续完整保留，但不再压住正文前半段。
5. 预算模型单点维护，技能文档只保留当前技能账本，降低分值漂移风险。
6. 后续维护者更容易快速判断技能是否可投放、需复评，还是应暂缓使用。

---

## 十、推荐决策

推荐直接采用以下收口口径：

1. `dev_doc` 只保留长期可复用的高价值信息。
2. 引用清单退出正文，回到执行 checkpoint。
3. 字段补齐流水账退出正文，只保留关键设计理由。
4. 预算账本进入正文前部，但完整 BU 模型只在 `技能预算指南（AI 专用）` 维护。
5. 完整评分继续保留，但固定为“评分结论前置、完整过程后置”的展示方式。
6. 通用流程提醒统一移出单篇文档，回收到仓库级指南。

这样可以在不削弱真实性和评分约束的前提下，把当前过胖的技能开发文档收回到一个更可读、更可维护的形态。
