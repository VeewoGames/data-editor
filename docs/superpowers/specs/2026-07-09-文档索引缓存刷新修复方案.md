# 文档索引缓存刷新修复方案

## 概述

### 1. 总体目标和范围

本方案目标是修复 `data-editor` 中 `Document` 字段对应 Markdown 文档“新建后在编辑器里看不到”的问题，确保像 `skill_axe_throw.md` 这类在服务启动后新增的文档，能够在不重启服务的前提下被重新发现并正确展示。

本次方案范围只覆盖文档索引缓存与正文读取链路，不改变 `Document` 字段的基础语义，不修改 Nocturnel 项目中 `skill_id -> <docRoot>/<skill_id>.md` 的文档约定，也不扩展 `dev_doc` 字段为“任意路径直读”模式。

本方案范围包括：

- 服务端文档索引缓存的定向失效与强制重扫能力
- `/api/document-index` 与 `/api/document-content` 的刷新参数支持
- 前端“重新加载文档索引”操作的真实刷新接线
- `missing` 状态下的可选自动回源重扫兜底
- 相关单元测试与回归测试补齐

本方案不包括：

- 重做 `Document` 字段语义
- 支持按 `dev_doc` 字段值直接读取任意 Markdown 相对路径
- 文件系统监听或自动热更新
- Markdown 编辑、写回、冲突恢复

### 2. 各阶段任务概要

#### 阶段一：收敛缓存失效模型

主要工作：

- 明确当前缓存 key 与失效边界
- 为单个 `projectRoot + docRoot` 增加定向清缓存或强制绕过缓存能力
- 保证索引重建后会覆盖旧缓存

预期成果：

- 服务端不再把某个 `docRoot` 的首次扫描结果永久固定
- 可以明确触发某个文档根目录的重新扫描

执行顺序：

1. 先补 `document-service` 缓存失效能力
2. 再让索引与正文读取链路都能透传刷新意图

#### 阶段二：打通前后端刷新链路

主要工作：

- 为索引接口增加 `refresh` 参数
- 为正文读取接口增加 `refresh` 参数
- 让前端“重新加载文档索引”按钮真正触发服务端重扫

预期成果：

- 用户点击刷新后，服务端会重新扫描磁盘，而不是继续返回旧缓存
- 新增 Markdown 文件可以在当前会话内被发现

执行顺序：

1. 先补 API 参数
2. 再补客户端调用签名
3. 最后接上 `App.tsx` 中的刷新动作

#### 阶段三：补自动兜底与测试

主要工作：

- 明确自动回源重扫下沉到服务端 `readResolvedDocument()`
- 在正文读取 `missing` 时增加一次自动回源重扫兜底
- 补齐“服务启动后新增文档，再刷新后可见”的测试
- 覆盖索引与正文两条链路的回归场景

预期成果：

- 即使用户没有先手动刷新，也能在常见场景下自动恢复
- 后续不会因为缓存问题再次出现“文件存在但编辑器显示缺失”的回归

执行顺序：

1. 先明确兜底归属与触发条件
2. 再补测试
3. 最后验证现有手动刷新提示文案与行为一致

### 3. 整体结构框架

- 服务层：`src/document-service.mjs` 负责缓存、扫描、索引与正文读取
- API 层：`server.mjs` 负责把刷新意图透传到服务层
- 客户端层：`src/api/client.ts` 负责暴露 `refresh` 选项
- 页面层：`src/App.tsx` 负责首次加载、手动刷新和文档面板联动
- 测试层：`tests/document-service.test.mjs` 负责覆盖缓存刷新回归

## 背景与问题定位

当前 `Document` 字段的文档解析模型本身是正确的：

- `data/skills.json:skills` 的主键是 `skill_id`
- `data/skills.json` 的 `docRoot` 是 `项目文档/开发/技能`
- `skill_axe_throw` 理论上应命中 `项目文档/开发/技能/skill_axe_throw.md`

因此，`skill_axe_throw` 在编辑器中显示“未找到匹配的 Markdown 文档”，并不是因为主键配置错误，也不是因为命名规则不匹配。

真正根因在于服务端文档索引缓存的生命周期设计：

- `document-service` 以 `projectRoot + docRoot` 为 key 缓存扫描结果
- 首次扫描后结果常驻内存
- 代码中没有针对“外部新增/删除/改名 Markdown 文件”的失效逻辑
- 前端的“重新加载文档索引”只重新请求接口，但接口继续返回旧缓存

这会导致一个稳定故障模型：

1. 服务启动，首次扫描 `docRoot`
2. 用户在磁盘上新建 `skill_axe_throw.md`
3. 编辑器继续沿用旧索引
4. 详情文档面板持续显示 `missing`

## 目标行为

修复后应满足以下行为：

1. 首次打开文件时仍可使用缓存，避免无意义重复扫盘。
2. 用户点击“重新加载文档索引”后，服务端必须真实重扫当前 `docRoot`。
3. 若当前文档正文读取命中 `missing`，系统可以自动进行一次回源重扫并重试。
4. 刷新后新建的 Markdown 文件应立刻进入索引，并可正常显示正文。
5. 该修复不应影响现有 `Document` 字段的主键映射规则。

## 方案选择

### 方案 A：仅修手动刷新

只在用户点击“重新加载文档索引”时强制清缓存并重扫。

优点：

- 改动最小
- 风险最低
- 容易验证

缺点：

- 首次打开详情时仍可能看到旧的 `missing`
- 用户必须知道要手动点刷新

### 方案 B：手动刷新 + `missing` 自动回源重扫

在保留手动刷新的同时，为正文读取增加一次“`missing` 后自动重扫并重试”的兜底。

优点：

- 保持缓存收益
- 用户显式刷新时一定生效
- 常见“刚新建文档就点进详情”场景也能自动恢复

缺点：

- 实现稍复杂于方案 A
- 需要注意不要把每次读取都变成全量扫盘

### 方案 C：彻底取消缓存

每次索引或正文请求都重新扫描 `docRoot`。

优点：

- 逻辑简单
- 不会再有 stale cache

缺点：

- 文档数量增加后性能会明显变差
- 不符合当前已有缓存设计方向

### 推荐方案

采用方案 B：保留缓存，但增加“手动强制刷新 + `missing` 自动回源重扫”双层修复。

原因：

- 当前故障是缓存失效问题，不是字段模型问题
- 方案 B 能以较小改动修复真实痛点，同时保持现有缓存收益
- 它既覆盖用户主动刷新路径，也覆盖新建文档后直接查看详情的常见路径

## 详细设计

## 一、服务端缓存模型调整

### 1. 当前缓存模型

当前缓存以 `projectRoot + docRoot` 作为 key，值中包含：

- `indexEntries`
- `contentByRelativePath`

问题不在 key 设计，而在于缓存没有失效入口。

### 2. 目标缓存模型

保留现有 key 模型，但增加两类能力：

- 定向清除某个 `projectRoot + docRoot` 的缓存
- 在读取时显式要求 `forceRefresh`

建议接口形态：

```js
buildDocumentIndex(projectContextOrRoot, documentFiles, dataFilePath, options?)
readResolvedDocument(projectContextOrRoot, documentFiles, dataFilePath, documentId, options?)
```

其中：

```js
{ forceRefresh?: boolean }
```

服务内部的 `getDocumentCache(projectRoot, docRoot, options?)` 在 `forceRefresh` 为 `true` 时应绕过旧缓存并重建。

### 3. 缓存失效粒度

本次只做 `docRoot` 级别失效，不做单文件级别失效。

理由：

- 当前索引本来就是按整个 `docRoot` 建立
- `Document` 字段匹配依赖全局唯一性，单文件局部刷新没有明显收益
- `docRoot` 级失效更简单，也更不容易遗漏冲突场景

## 二、API 设计调整

### 1. `/api/document-index`

增加可选查询参数：

```text
refresh=1
```

行为：

- 无 `refresh`：按现有缓存逻辑读取
- `refresh=1`：强制重扫当前 `docRoot`，重建索引并覆盖缓存

### 2. `/api/document-content`

同样增加可选查询参数：

```text
refresh=1
```

行为：

- 无 `refresh`：按缓存读取
- `refresh=1`：强制重扫后再解析正文

补充约束：

- 自动回源重扫只在普通读取路径触发
- 当请求已显式带 `refresh=1` 时，服务端只执行一次强制重扫，不再在内部追加第二次重扫

### 3. 参数语义约束

`refresh` 只表达“对当前 `path` 对应的 `docRoot` 强制重扫”，不表达：

- 刷新整个项目
- 刷新其他数据文件的文档根目录
- 清空所有运行时缓存

## 三、客户端调用调整

### 1. `src/api/client.ts`

扩展以下调用签名：

- `loadDocumentIndex(path, projectId?, options?)`
- `loadDocumentContent(path, id, projectId?, options?)`

其中：

```ts
type DocumentRequestOptions = {
  refresh?: boolean;
};
```

客户端只负责把 `refresh` 转成 URL 参数，不在前端自行实现缓存。

### 2. 参数使用原则

- 首次自动加载：`refresh = false`
- 用户手动刷新：`refresh = true`
- `missing` 自动兜底重试：第二次请求使用 `refresh = true`

## 四、页面层交互调整

### 1. 首次索引加载

当前 `selectedPath` 切换时自动执行 `loadDocumentIndex`。此行为保留，但仍走普通缓存路径。

原因：

- 大多数情况下首次打开文件不需要强制扫盘
- 保持现有性能特征

### 2. 手动刷新按钮

当前 `handleRefreshDocumentIndex()` 需要从“重新请求旧缓存”改为“触发服务端强制重扫”。

即：

- 刷新动作必须调用 `loadDocumentIndex(..., { refresh: true })`
- 成功提示文案可保留为“已重新加载 xxx 的文档索引”
- 若当前详情文档面板已有激活的 `documentId`，索引刷新成功后还要同步重载该文档正文，避免面板继续停留在旧的 `missing` 或旧正文状态

这样用户点击刷新后，`skill_axe_throw.md` 这类新文件会真实进入索引。

### 3. 文档正文读取兜底

自动回源重扫的最终归属放在服务端 `readResolvedDocument()`，而不是页面层手工发起两次请求。

原因：

- 这样可以把“正文读取遇到 stale cache 时如何恢复”的逻辑收口在文档服务层
- 前端不需要为普通读取额外维护双请求编排、取消态和重复 loading 状态
- 测试可以集中落在服务层，避免只有方案写了兜底、真实页面行为却没锁住

服务端行为应为：

1. 先用普通模式请求
2. 若返回 `missing`，并且本次请求不是显式 `refresh=true`
3. 则在 `readResolvedDocument()` 内部自动执行一次 `forceRefresh` 重试
4. 若重试后命中，则直接返回 `resolved`

若第二次仍是 `missing`，则说明磁盘上确实不存在匹配文档，应正常展示缺失状态。

### 4. 为什么只在 `missing` 时兜底

因为当前真实故障是“文件新增后缓存未更新”，对应的直接表现就是：

- 索引里没有该 `id`
- 读取正文返回 `missing`

对 `resolved` 或 `conflict` 场景默认不自动重扫，可以避免不必要的全量扫描。

页面层仍然保留一个职责：

- 用户点击“重新加载文档索引”后，除了刷新索引，还要同步重载当前激活文档正文

这样“刷新索引”和“刷新当前可见正文”两条用户可见结果会同时成立。

## 五、测试设计

### 1. 服务层测试

`tests/document-service.test.mjs` 建议新增以下场景：

1. 先建缓存，再新增 Markdown 文件，不 `refresh` 时仍返回旧结果。
2. 同场景下，`forceRefresh` 后新文件进入索引。
3. `readResolvedDocument` 在 `forceRefresh` 下可读取新增文档正文。

### 2. 兜底行为测试

建议增加场景：

1. 第一次正文读取返回 `missing`
2. 磁盘上此时已存在目标文件
3. `readResolvedDocument()` 在内部自动触发一次 `forceRefresh` 重试
4. 第二次重试后返回 `resolved`

此外建议补一条页面层联动测试或最小集成验证：

1. 当前文档面板处于 `missing`
2. 用户点击“重新加载文档索引”
3. 当前面板正文同步刷新为新文档内容，而不是只刷新侧边索引状态

### 3. 回归重点

必须覆盖以下回归边界：

- 新增文档后可见
- 删除文档后刷新可变为 `missing`
- 重名冲突文档刷新后可变为 `conflict`
- 刷新只影响当前 `docRoot`
- 相同 `docRoot` 字符串但不同 `projectRoot` 不串缓存

## 六、风险与边界

### 1. 性能风险

强制刷新会重新扫描整个 `docRoot`，在文档量较大时会有一次性开销。

本方案接受这一点，因为：

- 强制刷新通常由用户主动触发
- 自动回源重扫只发生在 `missing` 场景
- 与彻底取消缓存相比，总体成本仍低得多

### 2. 一致性边界

本方案解决的是“运行中缓存过旧”的一致性问题，不解决：

- 文件系统实时监听
- 外部编辑器持续写入后的秒级同步
- 多个客户端之间的共享刷新通知

这些都属于后续增强，不应在本次修复里膨胀范围。

### 3. 语义边界

本次不改 `Document` 字段语义，仍坚持：

- 字段值是文档 ID
- 文档路径由 `docRoot + <id>.md` 推导
- 不支持把 `dev_doc` 当作任意路径字符串直读

这能保证修复目标始终聚焦在真正的故障点，而不是引入新的双语义复杂度。

## 七、推荐落地顺序

1. 先修改 `src/document-service.mjs`，补 `forceRefresh` 与定向缓存重建能力。
2. 再修改 `server.mjs` 和 `src/api/client.ts`，打通 `refresh` 参数。
3. 在 `readResolvedDocument()` 内落地 `missing` 自动回源重扫，并限定只在普通读取路径触发。
4. 然后修改 `src/App.tsx`，让手动刷新真正触发强制重扫，并在成功后同步重载当前正文。
5. 最后补回归测试。

## 八、最终结论

本问题的根因是文档索引缓存缺少失效机制，不是 `Document` 字段语义错误，也不是 Nocturnel 的 `skill_id -> skill_axe_throw.md` 约定错误。

因此，完整修复方案应当是：

- 保留现有 `Document` 字段模型
- 为 `docRoot` 级文档缓存增加强制刷新能力
- 让手动刷新成为真实的服务端重扫
- 在 `missing` 场景下增加一次自动回源重扫兜底
- 用测试锁住“服务启动后新增 Markdown 文档仍可被发现”的回归边界

这条路径改动收敛、风险可控，并且能够直接修复 `skill_axe_throw` 当前看不到开发文档内容的问题。
