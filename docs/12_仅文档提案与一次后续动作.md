# 仅文档提案与一次后续动作

## 通用提案

proposal-v3 支持 `changes=[]`，前提是有授权的 `textArtifact` 且其完整 Markdown 的摘要确实变化。空字段列表加 null 文档、同摘要文档、旧文档摘要、旧源 ETag、旧身份或 fencing token 均拒绝。文档创建仍使用当前条目的规范文档路径。

仅文档组提交精确保留原始源文件内容，不重新序列化。源文件仍是身份、ETag 与 lease 的校验见证，并保留源子 journal；只有 before/after digest 与 ETag 均完全相等时才接受空字段子提交。正常执行和崩溃恢复均保持源文件字节，但不承诺 mtime 不变；文档沿用既有组提交 journal 恢复。

## 一次后续动作

在 automation-profile 的 project-skill / proposal rule 顶层配置：

```json
"followup": {
  "actionId": "review-item",
  "on": ["completed_with_writeback", "no_changes"]
}
```

`completed_with_writeback` 指受控提交成功，`no_changes` 指父模型返回 result-only 且其结果状态明确为 no_changes。failed、stopped、evidence_insufficient 等报告不会自动触发。提交成功的局部维护可以启动独立动作，由项目评审工具自行判断证据是否足够；服务不读取或相信模型 readiness，也不理解项目评分规则。

目标 action 必须是已有、启用的 project-skill，且自己没有 followup。只支持一次既有 action run，不允许链或循环。子 run 重新加载 canonical 行、快照与本机 binding，独立申请 fresh admission 和 fencing；父 authority 不会传给子。请求保留相同 sourcePath / collectionPath / rowId，以最新行重算 expectedRowDigest。

父 handoff 在受理时冻结 profile 与本机 bindings 的配置摘要。父提交发布后，owner 写入独立 `parentRunId.followup.json` 意图，以 parentRunId + actionId + 稳定目标确定唯一键和唯一 childRunId；子 started receipt 的 exclusive create 是唯一接受 CAS。服务启动及结果轮询会恢复已发布父成果，即使发布后 pending 尚未落盘，也只补齐相同意图。

恢复窗口：意图存在但子尚未接受，继续相同 childRunId；子结果已发布但父关系尚未更新，绑定既有结果；子已接受而重启后无终态结果，终止相同意图并标记取消，要求用户显式重试，不重新执行未知状态的模型。配置或 binding 漂移、目标移动、权限失效均报告停止，并保留父成果。

`POST /api/entry-actions/cancel` 使用 `{projectId,runId}` 取消 project-skill。取消标记先持久化，再终止本进程持有的 supervisor handle；认领、启动、返回结果及 fresh admission 文件替换前检查该标记。取消父会停止其尚未完成的子；已提交父成果不会回滚。

结果 API 的 `followup` 包含 state、actionId、childRunId、childOutcome、childResultStatus 或停止原因。父终态和子状态独立；界面继续轮询后续动作，并明确展示成果已保留及后续尚未完成。子失败不回滚父提交。


## 结构化执行结果

result-only 输出必须包含已识别的 `status`，或现有正式评审的 `designVerdict` / `verdict`（也支持既有嵌套 result）。合法值为 `completed`、`no_changes`、`failed`、`blocked`、`stopped`、`evidence_insufficient`、`changes_required`、`approved`、`checked`、`passed`、`rejected`；缺失或未知状态拒绝。外层 completed 不能掩盖内层失败或缺口。不根据自然语言 summary 判断成功。

`no_changes` 仅表示必要读取及分析已经完成，确实无需修改。工具、策略、权限、合同读取或适配器调用失败使用 `failed`；已分析但证据不足使用 `blocked`。两种 resultPolicy 都把 failed 发布为失败终态；blocked 等未完成报告在 UI 显示需要处理，不显示已完成。

proposal-v3 允许唯一可选字段 `resultStatus`。旧提案缺字段仍合法；部分合法修改可带 `blocked`，提交回执仍保留写入成功事实，同时展示“已保存部分修改，动作未完成”。写提案不能带 `failed` 或 `no_changes`，这两种状态必须走零写入的 result-only 路径。正式评审状态仍可使用。状态经绑定、fresh admission、源/组 journal 和最终回执保持；同 run、跨 run及崩溃恢复均不丢失。

执行完成或受阻时，将 host events 和 diagnostics 保存到本次 run 的 runtime 制品，再清理 snapshot scratch。Windows host 在忽略用户配置时明确传入既有原生 `windows.sandbox="elevated"` 设置；仍使用 `workspace-write` 与 `approval_policy="never"`，不修改全局配置，不回退到无沙箱。非 Windows 不传 Windows 设置。
