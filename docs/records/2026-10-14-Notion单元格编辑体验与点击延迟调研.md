# Notion 单元格编辑体验与点击延迟调研

## 方案概述

本报告是**非权威调研分析**，不是正式方案、执行计划或实施授权。适用项目：通用 Data Editor；调研日期：2026-10-14（Asia/Shanghai）；深度：标准版。用户显式调用 `game-external-research`，因此沿用其证据、项目适配和报告交付方法；本次对象是工具产品交互，不引入游戏业务。

目标是解释点击后的明显停顿，调查 Notion 数据库文本属性的相关体验，给出可采纳的交互方向。顺序为当前实现取证、官方资料核查、Notion 网页只读复现、适配与风险分析。正文按项目事实、外部证据、对比建议和验证边界组织。

关键结论：当前鼠标点击有明确的 **220ms 人为等待**。建议在编辑模式开启时直接响应单击，把关闭编辑模式时的双击启用捷径与编辑态内的文字操作分开。Notion 的内部计时机制与精确输入延迟未知；本报告不把“单击进入编辑”的外部行为推断成“内部没有任何计时器”。本轮未修改代码、测试、配置、业务数据或 Truth/ADR；没有在 Notion 输入或修改任何内容。

### 延迟从哪里来

当前调用链：`TextCellSurface.handleActivate` → `window.setTimeout(..., 220)` → `onActivate(cellId)` → `DataTable.handleActivateTextCell` → `activeTextCellId` → runtime → `TableColumnCellView.textEditingActive` → 编辑器挂载。

- [`TextCellSurface.tsx:60-67`](../../src/table/TextCellSurface.tsx)：每次可编辑、未激活的文本/数字单元格收到 click，都先等 220ms；实际响应还包括后续调度与渲染时间。
- [`TextCellSurface.tsx:70-82`](../../src/table/TextCellSurface.tsx)：Enter/空格直接激活；dblclick 则清除待激活计时器，并在尚不可编辑时请求启用编辑模式。
- [`DataTable.tsx:993-1013`](../../src/table/DataTable.tsx)：pointerdown 先 blur 当前输入并建立选中态。因此蓝框先出现，输入框后出现，形成两个明显节拍。
- [`DataTable.tsx:598,719,761`](../../src/table/DataTable.tsx)：编辑目标仍由 DataTable 单一持有，runtime 已包含修复后的依赖。本次等待与此前漏依赖是两个问题。
- [`TextCellTruncationHint.tsx:34-40`](../../src/table/TextCellTruncationHint.tsx) 的 1000ms 是截断文本悬停提示，与点击进入编辑的 220ms 不同，不应一起删除。

**解释：**等待主要服务于现有的单击/双击互斥合同，而不是等待网络或自动保存完成。不能据此断言所有额外卡顿均来自计时器，但这段固定等待本身足以解释稳定的停顿感。

直接复现的步骤与证据：

1. 在现有数据库表格选择一个普通 description 文本格，执行单击，读取焦点和可见编辑节点：出现带原值的文本编辑器。
2. Esc 关闭，换另一个文本格单击，得到同样结果。
3. 在第二格已打开的文字编辑器内双击，dialog 和 contenteditable 焦点保持；随后 Esc 退出，确认 dialog 数量为 0。
4. 保存[局部截图](../../output/playwright/2026-10-14-Notion单击编辑局部证据.png)。它记录可见编辑体验；焦点与 contenteditable 的结论来自同步 DOM 读取，不只靠截图。

限制与反证：一次“从关闭状态直接对展示按钮执行自动化 dblclick”的尝试最终没有获得输入焦点；不能据此概括 Notion 的闲置态双击语义。一次 Esc 后通过 body 发送 Enter 也没有重新打开编辑器；本报告不把网上“Enter 编辑选中格”的说法升级为本次已验证行为。官方 shortcuts 页主要描述 block 快捷键，不能直接当作数据库格子合同。本次没有形成两个独立产品的跨样本模式，只做 Notion 单产品范围的比较。

## 对比、推荐与有效备选

以下均为**当前项目推论**，依据项目实现与 E1/E3/E4，不是 Notion 官方给 Data Editor 的建议。

| 方面 | 当前 Data Editor | 本次观察到的 Notion | 建议适配 |
| --- | --- | --- | --- |
| 普通文本开始编辑 | 已开启编辑模式也固定等待 220ms | 普通文本格一次单击可打开输入浮层并取得焦点 | 已开启编辑模式时直接响应 click。 |
| 双击职责 | 负责全表编辑模式切换，且会取消格子激活 | 已打开编辑器内双击仍保持编辑态 | 模式关闭时才处理双击启用；模式开启后让双击服务文字编辑。 |
| 输入类型 | 文本/数字与选项编辑器已有分工 | 官方按属性类型使用不同编辑入口 | 不把 TextCellSurface 的改动扩展到 Select、Relation 等编辑器。 |
| 文字长短与浮层 | 展示层保持行高，编辑 overlay 可向下扩展 | 本样本用单格浮层编辑文字 | 保留现有 overlay 和稳定行高，不为降低延迟更换表格框架。 |

### 推荐 A：按当前编辑模式分流，取消已开启模式的固定等待

拟议行为：编辑关闭时，单击即时选中，双击仍可启用全表编辑模式；编辑开启时，普通 click 完成后直接打开所点格子的编辑器，第二次点击不再把已开始的文字编辑撤销。不要改成 pointerdown 就立刻抢焦点，以免干扰拖选判断。

推荐理由：用户希望消除编辑操作的停顿；当前可编辑状态已经提供了区分条件，不必再通过等待来猜测动作；E3 证明 Notion 的单击直接编辑体验是可行参照，E4 解释了当前冲突来源。最小改动集中于 TextCellSurface 的激活/双击分支和对应测试，不增加新的全局状态、项目专属行为或持久化规则。

成本与风险：需要明确更新“编辑已开启时双击不能激活”的旧测试合同（`tests/data-editor.spec.ts:7025`）。不能只删除 setTimeout 却保留互相冲突的双击语义；也不能为了抢快跳过外部切换前的 blur/flush。切换不同格、已有输入草稿、快速连续点击和拖选都须重新验收。

### 有效备选 B：单击只选中，第二次单击或 Enter 才编辑

适用于用户以范围选择、复制为主要操作的工作流。它可避免单击/双击互斥等待，但每次编辑多一个明确动作，并改变当前“编辑已开启时一次单击编辑”的体验。相较用户本次目标，优先级低于 A；不能当作本次 Notion 行为结论，需独立产品选择。

不推荐仅将 220 改为更小数值：等待仍存在，且更容易在系统双击阈值与应用硬编码之间产生竞态。也不推荐增加 loading 动画掩盖本地等待。

## 验证、未知与后续交接

本轮是调研，未实施 A/B，也未运行与新交互有关的通过性测试。上一轮测试通过不能作为本建议已实现的证据。

若授权采用 A，建议验收：

1. 在编辑模式开启后，测量 click 至首个可交互编辑帧；确认不再存在固定 220ms 平台，不只依赖 Playwright 最终 `toBeVisible`。
2. 单击跨行、跨列以及快速 A→B→C：蓝框、唯一编辑器、焦点与写回目标一致；旧草稿提交不丢失。
3. 单击、双击和较慢双击分别验证；编辑器内文字定位/双击选择、拖选必须自然，不触发全表模式切换。
4. 模式关闭时双击启用的行为单独保留测试；已开启模式的旧双击抑制测试须按采纳的产品合同重写。
5. 覆盖 Text、Number、换行、长文本、空值与键盘激活；离散属性的原有编辑方式保持独立。
6. 验证 npm run typecheck、针对性 Playwright、正式构建及正式 URL 的真实操作；检查两个健康端点并执行 service:finalize。

关键未知：Notion 的数值耗时、内部实现、移动端行为及闲置态双击的完整语义；它们不阻止提出 A，但禁止把 A 表述为对 Notion 内部架构的复刻。更大数据量下的额外渲染延迟需要另行性能测量。

后续需要用户选择是否采纳 A；本报告的交付不自动改变既有测试合同或授予实施权限。来源锚点已附在项目事实、E1—E4 与复现步骤旁。
