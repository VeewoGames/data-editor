# 视图与图标系统

## 概述

### 1. 总体目标和范围

本章定义 collection 视图的共享与个人状态边界，以及视图和自动化动作使用的图标系统。它说明运行时行为和持久化模型，不记录一次性资产采集方案。

### 2. 各阶段任务概要

1. 团队在共享视图中定义查询、筛选、排序和分组结构。
2. 用户在个人 draft 中调整视图内容、结构和布局。
3. 用户选择发布或重置；图标通过统一 registry 选择和渲染。

### 3. 整体结构框架

```text
shared-views.json  -> 团队视图/组/图标
view profile        -> 个人 draft、布局与收藏图标
ViewTabs + FilterBar -> 有效视图
icon registry       -> 视图与自动化动作渲染
```

## 共享视图与个人状态

共享视图保存在 `<project>/.data-editor/shared-views.json`。每个 collection 使用 `<filePath>:<collectionPath>` 作为 key，`items[]` 是唯一的结构真值：顶层普通视图为 `kind: "view"`，视图组为 `kind: "group"`，组中只容纳实际视图。默认视图必须指向实际 view，不能指向组。

具体视图包含名称、图标、搜索文本、筛选规则和排序规则。顶层筛选规则固定按 AND 生效；需要复杂组合时使用唯一的高级筛选树。排序按规则数组顺序应用。

用户的 `UserViewProfile` 保存个人视图状态：最近激活视图、内容 draft、视图顺序 draft、组结构 draft、列布局、文件排序和收藏图标。个人 draft 不会立即改写团队配置；“为所有人保存”将当前视图内容与当前 collection 的结构 draft 一起发布，“重置”丢弃对应 draft。

列顺序、列宽、隐藏、换行和详情字段顺序始终属于个人布局，不随共享视图发布。创建视图副本时，系统复制当前有效状态，并连同当前用户的布局生成新 view 的个人布局。

## 图标模型

视图和自动化规则都保存稳定的图标 ID，而不保存 SVG 文本。运行时 registry 由以下生成模块提供：

```text
src/generated/streamline-shared-view-icons.mjs
src/generated/tabler-shared-view-icons.mjs
```

服务提供 `GET /api/shared-view-icon-pack-manifest` 和 `GET /api/shared-view-icon-pack` 供前端按需读取图标包。选择器支持按名称和标签检索；个人收藏保存在 profile 的 `favoriteSharedViewIconIds`，不会修改共享图标资源。

图标资产更新使用 package scripts 中的 `streamline:*` 与 `tabler:*` 入口。生成 registry 前必须处理 ID collision；生成产物是代码资产，正式文档只要求其保持可生成、可加载和 ID 稳定。

## 选择器交互边界

图标网格是选择器内部的滚动区域。指针位于网格时，滚轮事件在网格捕获阶段停止向外传播，滚动由网格自身处理；外层 Popover 或自动化设置容器不应接管该事件。此边界只约束滚动事件，不改变图标包加载、名称和标签筛选、个人收藏或图标选择的语义。

## 使用边界

- 共享视图发布直接覆盖团队配置，不提供多人冲突合并。
- 图标只是展示与识别资产，不改变筛选、排序或自动化语义。
- 旧的 `views[]` 格式仅用于读取迁移；新写入统一使用 `items[]`。
