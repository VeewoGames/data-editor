# 方案概述：条目自动化可见生命周期与稳定提案合同修复执行计划

## 总体目标与执行顺序

本计划将通用 project-skill 自动化从“同步复制后才启动”的不可见流程，收敛为可观察、可终止、单 run 的受控生命周期。执行顺序不得颠倒：先冻结状态与 authority 合同，再实现准备 worker/UI，最后接入稳定 skill/proposal 与 Nocturnel 样本验收。

## 第 1 章：冻结通用合同

### 1.1 准入、状态与兼容边界

输入：架构设计文档与当前 entry-action state。

动作：定义 receipt、active phase、`acceptedAt === startedAt`、`failedPhase` 与 terminal 语义；实现 durable idempotency 回放。冻结 `ProjectInput` 仅为额外读取、平台提供目标 row/file 的合同；明确 `commitAdmittedProposal({ runDefinition, lease, result })` 与旧 fresh-admission/candidate-create 的保留范围；持久化 prepare worker intent/process ownership 及重启 fail-closed 规则；定义 SkillArtifact 闭包、上限、digest、staging 与链接拒绝。

验收：状态/API/测试清单可由另一执行者接手；覆盖 receipt 网络重试、worker 在登记前后崩溃、旧时间字段读取、同 run lease 提交与 SkillArtifact 路径逃逸；不包含 Nocturnel 业务规则。

## 第 2 章：可见且可终止的准备

### 2.1 后台准备与最小输入

动作：将 queued receipt 与后台 worker 解耦；用受监督 worker 复制显式 `projectInput`；删除隐式整仓 snapshot；补恢复和清理。

验收：receipt 短时返回；准备超时具有进程树退出和 terminal 证据；空输入不复制仓库。

### 2.2 前端阶段投影

动作：按服务端 phase/时间显示排队、准备、检查、执行、校验、提交和失败阶段；观察超时不得冒充执行超时。

验收：真实窗口在准备阶段立即显示时长，刷新后可从状态恢复。

## 第 3 章：稳定 skill 与 proposal 合同

### 3.1 SkillArtifact 与同 run proposal

动作：准入时冻结并 stage 完整 skill 包；复用 proposal authority handoff/commit，不新建 child run；非法结果 fail-closed。

验收：准入后原 skill 删除或变化不影响该 run；runId、ETag、digest、fencing token 从 handoff 到提交一致。

### 3.2 Nocturnel 配置与真实验证

动作：依据 `fill-data-name` 实际引用闭包配置最小 `projectInput` 并恢复有效 binding；仅作样本，不进入 Data Editor 业务代码。

验收：fixture 定向测试、真实窗口、Nocturnel 受控 proposal 写回分别通过；更新自动化文档；仅在本任务启动过服务/Browser 后执行 `npm run service:finalize`。

## 非范围与失败处置

- 不迁移项目业务规则、不扩张 project-write、不执行全仓复制兼容。
- 准备或 Codex 失败只发布终态与诊断；commit 中断仍走既有 journal/recovery。
- 每章完成后再进入下一章；若 SkillArtifact 打包闭包无法由现有证据确定，停在 3.1 并补决定性调查，不猜测实现。
