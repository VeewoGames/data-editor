# 条目自动化授权双真值收敛修复方案

## 概述

### 1. 总体目标和范围

本方案将普通用户的条目自动化配置收敛为一份真值：`Automation Settings` 保存的
`.data-editor/automation-profile.json`。规则中的 `id`、`enabled`、目标 `file + collection`、
`textArtifactId` 与运行参数共同定义该动作可以处理的范围。

目标是在不降低条目级安全边界的前提下，删除独立
`.data-editor/entry-action-policy.json` 对同一动作目标的重复声明。这样新增或修改自动化
规则后不再需要同步维护第二份授权文件，也不会再出现“设置页可见且已启用，但执行时因 policy
缺少对应 actionId 而失败”的断裂。

本轮覆盖 Data Editor 的通用运行时、配置读写、授权快照和迁移。不为 Nocturnel 或任何具体
skill 写入专属规则；Nocturnel 的 `data-design-trait` 失败只是本问题的已验证案例。

### 2. 各阶段任务概要

1. 将授权来源改为自动化规则目标，并保留服务端不可变运行快照。
2. 将文本产物的声明迁入规则目标，形成同一份 profile 内的完整动作能力描述。
3. 删除 policy 文件、加载链、校验模块、项目上下文路径及旧测试。
4. 为旧 profile 做一次性结构迁移，并验证新增动作、范围变更、并发写回和过期回包。

执行顺序必须是先完成 profile schema 与服务端读链，再迁移现有项目配置，最后物理删除
policy 机制；不得双读或长期兼容。

### 3. 整体结构框架

```text
Automation Settings
  -> automation-profile.json                 唯一用户配置真值
  -> automation-bindings.json                 本机 Codex/skill 绑定

POST /api/entry-actions/run
  -> profile rule + binding 解析
  -> 固定 actionId / file / collection / __entry_id / document ETag
  -> 创建 handoff、fencing token 与 authority snapshot
  -> Codex proposal
  -> 对比当前 profile ETag、文档 ETag、稳定条目身份与 snapshot
  -> 只提交同一条目、同一目标的字段补丁和已声明文本产物
```

## 一、问题与根因

当前运行时同时读取：

- `automation-profile.json`：用户在 Automation Settings 中配置的规则及目标。
- `entry-action-policy.json`：服务端再次以 `actionId + file + collection` 声明允许范围，另含
  `rowMatch` 与文本产物策略。

两者重复表达“某个动作能处理哪个文件和合集”。例如，Nocturnel 已配置并启用了
`data-design-trait -> data/content/traits.json -> traits`，但 policy 没有该 actionId 的目标；
`createAuthoritySnapshot(...)` 调用 policy 校验时会将其转成
`ENTRY_ACTION_AUTHORITY_STALE`，前端便显示“Entry-action authority changed or was narrowed.”。

这不是用户修改了范围，而是双真值不同步造成的错误语义。

## 二、目标模型

### 1. Profile 是普通用户动作范围的唯一配置真值

规则 target 继续使用稳定的配对结构：

```json
{
  "id": "data-design-trait",
  "enabled": true,
  "targets": [
    {
      "file": "data/content/traits.json",
      "collection": "traits"
    }
  ]
}
```

运行时只允许动作访问自身规则内存在的 target pair。其他 rule、其他文件、其他 collection 都
不能因模型回包而被扩展。

### 2. 行身份与文档版本仍由服务端控制

profile 不负责并发安全。服务端启动任务时必须固定并持久化：

- `actionId`、`file`、`collection`；
- `rowId` / `__entry_id` 与解析得到的源行位置；
- `baseDocumentEtag`、当前规则的规范化 `ruleDigest`；
- canonical file key、fencing token 和 runId。

proposal 返回时，服务端重新读取 profile 和文档，只在下列条件全部成立时提交：规则仍启用、
目标 pair 仍存在、当前规则 `ruleDigest` 未变化、文档 ETag 未变化、同一稳定条目仍存在，且补丁字段
属于该条目当前对象。这样替代 policy 的重复 target 声明，而不削弱“模型不能写错文件/条目”的
保护。保存其他无关规则不应使正在运行的动作失效；整个 profile ETag 仍用于保存时的并发冲突检测。

`ruleDigest` 固定为 `sha256(canonicalJson(toRuleAuthorityShape(normalizeRule(rule))))`：先按 profile 的
正式规范化规则得到完整 rule，再投影为仅含 `id`、`enabled`、`targets`、`payload` 与 `runtime` 的
`toRuleAuthorityShape`，最后按递归键排序的 canonical JSON 序列化。该投影明确排除显示用
`label`、`icon`；`targets` 保持用户配置的数组顺序。因而修改动作范围、输入内容或运行参数会使在途
任务失效，单纯改名或换图标不会。该合同必须由独立单元测试固定。

### 3. 文本产物改为规则 target 的可选声明

现有 `textArtifactId` 已属于 profile target，应扩展为 target 内的可选对象：

```json
{
  "file": "data/content/skills.json",
  "collection": "skills",
  "textArtifact": {
    "pathTemplate": "项目文档/开发/技能/{value}.md",
    "sourceField": "skill_id",
    "allowCreate": true,
    "allowUpdate": true,
    "maxBytes": 131072
  }
}
```

路径模板、源字段、大小、创建/更新权限仍由服务端校验；它们只是与动作 target 同存于唯一的
profile，不再拆到另一个 policy 文件。只有需要产出文档的规则才声明该对象。

### 4. 不在通用编辑器内固化业务行谓词

`rowMatch` 不迁入普通的 Automation Settings。它是项目业务语义，不是编辑器通用配置。
首版删除它后，动作范围由用户显式选择的文件和 collection 决定；条目级身份与版本控制继续
保证一次任务只写其启动时选中的条目。对 Nocturnel 当前的 `owner=player` 限制，
`data-design-skill-player` 与 `review-player-skill` 必须在各自 skill 内读取当前条目并拒绝非玩家
技能；该行为是项目 skill 的职责，不由 Data Editor 授权层表达。

如果未来存在团队管理员限制需求，应另建可选的部署级管理员策略层，并明确其 owner、加载
位置和优先级。它不能再作为个人自动化的第二份必填配置。

## 三、实施阶段

### 阶段一：收敛 profile schema 与 API

1. 扩展 `src/automation-profile.mjs`：允许并规范化 target 内的 `textArtifact` 对象。
2. 更新 Automation Settings：仅在需要文档输出时展示并编辑文本产物字段；普通动作不展示
   额外权限配置。
3. 更新 `src/api/client.ts`、保存校验和 profile 测试，确保 ETag 保存仍覆盖整个规则真值。

成果：用户只在一个入口配置动作范围和可选输出文档规则。

### 阶段二：替换服务端授权快照

1. 将 `src/entry-action-authority.mjs` 改为只基于 profile target 构造快照，不再接收 policy 或
   policy digest。
2. `assertAuthorityCurrent(...)` 只比较当前规则的 `ruleDigest`、规则启用状态、target pair、稳定行身份、
   文档版本和文本产物声明。
3. `src/entry-action-service.mjs`、proposal commit、group commit 与 writeback adapter 改为传递
   immutable handoff/snapshot，而不是调用 policy 校验。
4. 保持 proposal identity 由服务端回填，禁止模型覆盖 `actionId`、`rowId`、文件和 ETag。

成果：安全校验留在服务器，但其权限来源不再重复。

### 阶段三：一次性迁移并删除 policy

1. 以 profile 的原始 JSON 为唯一迁移源，不能先调用会静默去重的常规加载链。预检必须严格拒绝
   重复 `actionId`、重复 `file + collection` target、未知字段、残留非法形状及重复文本产物引用。
   profile-only target 是合法状态，直接迁入新 profile；这覆盖当前 `data-design-trait` 已配置但 policy
   缺失的场景。policy-only target 从未构成可见动作配置，列入诊断清单后随 policy 清理。
2. 对 profile 的 `textArtifactId`，只允许迁移同一 `actionId` 且 `id` 完全相同的 policy 文本产物；
   悬空引用、重复产物、路径模板非法或 target 冲突必须停止并给出明确诊断，不自动猜测。所有 policy
   文本产物都必须被恰好一个 profile target 映射；未引用产物必须由项目 owner 显式处置后才能删除 policy。
3. policy 含 `rowMatch` 时，先完成对应项目 skill 的业务前置校验并由项目 owner 验收；未验收的
   项目不得进入删除阶段。Nocturnel 的两个玩家技能动作属于此硬前置项。
4. 预检通过后备份两份源文件，生成并校验新 profile，再写回 profile；最后删除
   `entry-action-policy.json`。迁移标记必须包含迁移 ID、两个源文件的路径与内容 digest、生成后 profile
   的内容 digest、每个文件的预期存在状态和当前阶段。每一步在互斥锁内以这些 digest 做 CAS；任一
   不匹配即进入 `failed_needs_recovery`，不得自动重试删除或整套回退。profile 可能位于
   `DATA_EDITOR_PROFILE_HOME`，因此不能假定两份文件可用一次原子重命名处理。
5. 删除 `src/entry-action-policy.mjs`、project context policy path、policy API/加载路径、相关测试
   与文档中的正式依赖描述。

由于项目仍处于早期阶段，不保留双读、fallback 或 policy 兼容开关。迁移完成后只存在 profile
真值。

成果：不存在可继续漂移的双配置链。

### 阶段四：验证与项目迁移

Data Editor 最小自动化回归：

- 新增规则后，无需任何第二份文件即可启动并完成同目标条目的 proposal/writeback。
- 禁用当前规则、移除当前规则 target、变更当前规则文本产物声明或修改源文档后，旧 proposal 必须被拒绝；
  保存无关规则不能使其失效。
- 模型返回不同 `rowId`、不同文件、不同 collection 或未存在字段时必须被拒绝。
- 文本产物必须受 target 内 path template、来源字段和大小约束。
- 同源并发、fencing、恢复与状态持久化测试继续通过。

Nocturnel 验收：`data-design-trait` 配置目标后能够直接运行，不再需要手工向 policy 补充
`actionId`；`data-design-skill-player` 的开发文档输出仍只按其规则自身的文本产物声明写入。

## 四、接口与错误语义

`POST /api/entry-actions/run` 的请求格式不因本修复扩权：前端仍只提交已配置的 `actionId` 与当前
条目上下文，不能提交任意文件、collection 或 skill。

错误需拆分为可理解的原因：

| 场景 | 错误代码建议 | 用户含义 |
| --- | --- | --- |
| 规则不存在、禁用或不匹配目标 | `ENTRY_ACTION_TARGET_NOT_CONFIGURED` | 此动作未配置为处理当前条目 |
| 当前规则已改变 | `ENTRY_ACTION_PROFILE_STALE` | 此自动化规则已变更，请重新发起 |
| 文档内容已改变 | `ENTRY_ACTION_DOCUMENT_STALE` | 条目已更新，请重新发起 |
| 行身份不存在或不一致 | `ENTRY_ACTION_ROW_STALE` | 原条目已变化或被删除，请重新发起 |
| 产物模板不合法 | `ENTRY_ACTION_TEXT_ARTIFACT_DENIED` | 文档输出不符合该规则的声明 |

不再使用含糊的 `ENTRY_ACTION_AUTHORITY_STALE` 覆盖“配置缺失”和“运行中变更”两类不同问题。

## 五、范围、非目标与风险

### 本轮范围

- 普通用户 Automation Settings 的单一配置真值。
- 服务端条目、文档、并发和回包完整性校验。
- 现有 policy 到 profile 的一次性迁移与物理删除。

### 明确不做

- 不把 Nocturnel 的 `owner=player` 等业务规则写进 Data Editor。
- 不新增团队管理员策略或 RBAC。
- 不允许自动化规则删除条目、修改任意路径或执行任意 shell 命令。
- 不降低 Codex binding、skill 解析、stable row identity、document ETag、fencing 的现有安全要求。

### 主要风险与控制

迁移时 policy 可能包含 profile 尚未表达的 `rowMatch`。首版不自动迁移该业务谓词；对应项目
skill 的业务前置校验未完成并验收前，迁移器必须拒绝删除 policy，而不是静默放宽。对已运行任务，
policy 删除会导致旧 run 的 authority snapshot 无效，因此切换窗口应先等待或显式终止在途任务，再开始迁移。

## 六、回退

迁移前先备份 profile 与 policy；回退只能恢复整套旧版本代码和两份配置，不能在新代码上继续
读取旧 policy。这样避免再次出现“UI 用新 profile、后端用旧 policy”的混合状态。

## 七、完成标准

1. Data Editor 不再在普通条目自动化运行链中读取 `entry-action-policy.json`。
2. 用户新增、编辑、删除规则时只维护 Automation Settings。
3. 运行时仍对 action、目标、稳定条目、文档版本、回包身份和文本产物做服务端校验。
4. `data-design-trait` 的失败不再可由“遗漏 policy 目标”触发。
5. 迁移、错误语义和回归测试覆盖上述边界，且没有兼容双读残留。
