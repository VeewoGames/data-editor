# 大文件性能与配置自动保存修复方案

- 日期：2026-10-26
- 版本：v1.0
- 状态：已完成 feature-architecture 与独立 recheck 复核，尚未实施
- 定位：方案与分阶段实施依据，不构成代码实施或正式激活授权。

## 一、问题、边界与不变量

### 方案概述

本方案解决三个相互关联但不能混为同一原因的问题：仅切换数据页面也触发配置保存失败；打开、切换大文件时存在连续整表处理；滚动宽表、换行表时仍有随总行数增长的计算和同步存储。

总体结构按配置写入、表格布局、页面上下文、文档派生四个职责组织。执行顺序为：**固定可复现基线 → 修复配置保存 → 优化滚动 → 精简打开链 → 根据剩余瓶颈补充后续计划**。每个切片同时完成实现、针对性回归和效果验证；不能把首屏提前显示等同于完整处理性能达标。

预期成果包括：配置保存不再被错误要求提供自动化 run 上下文；保存失败不丢失待保存状态；滚动不逐事件遍历整表或同步写整份页面状态；同版本派生结果得到复用；最终通过浏览器测量确认改善。Worker、列虚拟化不是已确定的实施项，只在检查点取得证据后决定。

### 已确认事实与证据边界

| 问题 | 已确认事实 | 不应推导的结论 |
| --- | --- | --- |
| 配置保存失败 | 页面出现 `HISTORY_RUN_CONTEXT_REQUIRED`；视图切换更新 `lastActiveViews` 并保存命名 profile；不执行写入的门控探针复现相同错误且回调未进入 | 不能说全部业务文档保存都缺授权；普通数据保存已有专用 author scope |
| 打开卡顿 | 打开链包含解析、消费者复制、建立 store、保存基线复制、字段分类、投影、视图计算和校验 | 预建 store 已被复用，不能误报为固定建立两次；Node 局部耗时不是浏览器整页耗时 |
| 滚动卡顿 | 已有行窗口；换行窗口每次计算仍全量构造高度数组、求和和扫描；滚动事件同步保存页面位置 | 不能说完全没有虚拟化，也不能说所有子单元格都未使用 memo |
| 宽表成本 | 现场技能表共 187 行，挂载约 30 行、36 列、1,080 个单元格、约 7,400 个表格内部 DOM 节点；横向视口只覆盖约 9 列 | 尚无浏览器 trace 证明列渲染占比，不能直接承诺列虚拟化就是主要解法 |
| 生成字段查找 | 每行通过 `binding.rows.find` 查结果，存在平方级总查找成本 | 现场技能表和特性表的生成字段响应为空，不能将该分支当作当前现场主因 |

上述现场读数来自前序只读分析，不是本方案实施后的验收结果。此前健康接口 50 次采样 p95 约 3.24ms，部分文档 HTTP 样本约 12–53ms；它们只能约束当时的接口等待，不能替代浏览器脚本、布局、绘制和内存分析。

关键代码入口：`src/App.tsx::openDocumentAt`、`handleSelectSharedView`、`flushBeforeDocumentTransition`；`src/view-profile.mjs::saveViewProfile`；`src/table/variable-row-window.mjs::buildVariableRowWindow`；`src/table/DataTable.tsx` 的滚动与行高测量。

### 范围与不变量

- 覆盖通用 JSON/CSV、数组、record-map、多集合，及现有预览大小上限内的窄表、宽表、换行和嵌套内容。
- 保留完整校验、搜索、筛选、排序、稳定 rowId、源数组顺序、跨列选择、键盘定位、编辑提交和拖拽语义。
- 保留历史闭锁、账本、receipt、authority 选择、部署校验及业务保存版本检查。
- 保持配置现有归属和格式，包括合法外置 profile；不把 `lastActiveViews` 偷换成本地临时状态。
- 不增加具体项目逻辑，不通过豁免整个 `.data-editor`、伪造 runId 或关闭保护解决误拦。
- 不新造平行保存框架、第二套文档真相源或无界文档缓存。
- 本文仅交付设计。当前页面的草稿、失败状态和未确认请求不得通过刷新、自动重试真实写入或清空状态来处理。

## 二、新增或改变的概念、唯一 owner 与数据流

### 2.1 精确配置作者作用域

三个现有 writer 继续分别拥有配置类别、目标解析、内容验证和序列化：`saveViewProfile`、`saveViewConfig`、`saveSharedViews`。历史保护层只负责验证配置类别对应的精确物理写集与作用域资格。

正常路径为：

`可信项目上下文 + 配置类别/合法名称 → writer 解析精确目标 → 配置作者准入 → 原配置锁及可选前像检查 → 原子效果再次验证 → 写入 → 响应确认`。

配置作者准入必须满足：

1. 不从 HTTP 请求接收任意“授权路径”。目标必须来自对应 writer 的既有解析器。
2. 区分逻辑所属项目与物理存储位置。`project-context.mjs` 支持 `profileBaseDir`、`DATA_EDITOR_PROFILE_HOME` 和 `userViewProfilesDir`，合法外置目标不能因不位于 projectRoot 内而被拒绝。
3. 只授权本次精确配置文件；拒绝其他项目 binding、业务文件、runtime、ledger、receipt、authority、未支持类别及物理别名。
4. 在创建目录前验证目标；最终原子效果内重新核验目标和 live scope。配置模式的精确写集检查必须位于现有“无 discovered binding 的外置路径”快速返回之前，防止外置配置作用域变成全盘写权限。
5. 配置作者准入拒绝任何已有 historical scope，包括 automation、author、publication、configuration；不得通过嵌套 writer 扩大或替换写集。操作结束后 token 失效，迟到效果拒绝。
6. 保留每次效果前的历史保护复验及既有锁。准入的短历史锁校验完成后释放，再进入配置锁；不能持 root 锁等待 configuration 锁，造成与原 configuration → 历史效果锁路径反序。

复用 `withConfigWrite`。它已有配置进程锁和迁移时可选的 `expected` 前像检查；普通配置保存当前是 replacement，不能声称所有配置已有 ETag CAS，也不在本轮暗改并发合同。

### 2.2 保存确认与切换终点

复用现有 `saveCoordinator`、profile 串行保存链和共享视图既有保存 owner。将自动保存、直接 profile 保存、显式保存与切换 flush 接到一致的确认状态，不增加旁路队列。

入队前一并捕获：`projectId、profile/配置目标、domain、snapshot、revision`。状态至少能表达待保存版本、在途版本、最后确认版本和错误。

- 成功只确认对应 revision。请求期间发生的新修改继续 pending/dirty，不能被旧响应清掉。
- 失败保留快照和错误；重试发送最新有效待保存版本，不把错误当成功。
- 文件、项目和 profile 切换等待捕获 owner 的保存终点。仅 `saved/idle` 且无未确认新 revision 才切换；`blocked/deferred/error` 保留原页面和草稿。
- 补齐 `handleSelectViewProfile` 对 flush outcome 的检查，并将直接 profile promise 纳入必要的 flush 终点。
- 同一 profile 内的视图 tab 切换保留 `lastActiveViews` 归属并合并排队，不让每次点击同步等待网络。
- 用户提示区分“数据内容保存失败”和“视图设置保存失败”，避免将个人配置错误误报成业务数据保存失败。

### 2.3 行高索引与滚动位置

Table 布局层拥有行高索引和布局版本，不把测量状态写入业务文档。

- 按 rowId 保存高度，按当前视图顺序建立可更新的前缀和索引。初始化、行序改变允许 O(N)；单行更新和 offset 定位为 O(log N)，窗口输出为 O(窗口行数)。
- 仅测量挂载行，批量提交真正变化的高度；不能每次测到一行就重建整个前缀数组，也不能在“高度没变”时先复制全部测量记录。
- 列宽、可见列、换行、字体、缩放和影响高度的内容变化使相关布局测量失效；旧布局版本的迟到测量丢弃。
- 用“首个可见 rowId + 行内偏移”作为锚点，补偿上方高度变化。锚点被过滤或删除时，选旧顺序下最近存活后继；无后继则选前驱；空表归零。选中行仍按 rowId，不以窗口索引写回数据。
- 每帧合并窗口状态更新；窗口边界不变时，避免因像素级 scrollTop 变化重复构造整张窗口视图。

页面上下文层拥有位置暂存和持久化：滚动先更新内存，尾沿合并写入；切换前 flush 旧 scope，取消旧定时器。缓存仅携带 dirty scroll entries，写入时读取最新全状态再合并，不回写旧的整份快照或覆盖无关查询、选择字段。

沿用现有 localStorage 最后写入覆盖语义。读后合并不是跨 tab 原子事务，不能承诺并发读改写时不同 key 永不丢失；本轮不引入 CRDT 或新存储协议。

正常 pagehide/visibilitychange 可执行时同步 flush 本地位置。网络 profile 保存则以应用内切换/受控关闭等待确认为准；浏览器强退、崩溃或关闭时未确认的网络请求不能承诺完成，不能伪装为 saved。

### 2.4 同版本派生结果与读取所有权

Model/view 层复用现有 store、稳定 view rows 和编辑 invalidation，统一同版本字段分类、生成结果索引、投影及就绪状态。key 包含项目、文档实例、集合、数据 revision、相关配置和生成结果版本；数据原地修改也必须失效，布局变化不能无条件触发所有数据派生。

生成结果每 binding 建一次查找索引，保留原 `find` 的首个匹配和严格 `===` 语义，不字符串化 ID；重复 ID、类型差异和 `NaN` 不匹配均有反例。无结果、dirty、冲突和 pending 元数据保持原语义。

Read coordinator 继续保证消费者隔离。只有证明解析对象没有缓存或其他共享引用、且只有一个存活消费者时，才允许转交所有权；多消费者继续取得独立可变副本。保存基线与编辑 root 必须独立，不能为提速删除保存基线复制。

若后续将 validation 或派生分片，状态必须明确 pending，仅发布完整同版本结果。依赖完整校验的保存、主键维护等操作应等待或明确阻塞；pending 不等于零错误。异步任务始终携带 scope/revision，迟到结果不能影响新页面。

## 三、推荐决策、关键理由与关键失败路径

### 推荐决策

1. **先修配置保存正确性。** 错误授权和切换确认不完整会干扰正常浏览，不能归因于文件太大。用精确配置作用域修复，保持保护规则，不修改原数据 author scope 来容纳任意元数据写入。
2. **先删除确定的滚动全量工作。** 行高索引、无变化测量合并和位置持久化都有直接源码依据，不需要先重写表格或迁移第三方框架。
3. **打开链先做同版本复用与算法精简。** 保持已存在的预建 store 和单元格 memo；减少重复分类、投影及能证明安全的复制，不以延迟执行冒充消除主线程成本。
4. **Worker 与列虚拟化以 trace 为门。** 若剩余长任务主要是解析或不可拆复制，补 Worker/所有权传递设计；若主要是宽表 cell/布局，补列窗口或渲染隔离设计。列窗口必须另外闭合表头、宽度、换行行高、跨列选择、键盘、拖拽和活动编辑器合同。不能先卸载编辑器或隐藏列以满足指标。

### 关键失败路径

- **旧保存响应晚到：** A revision 1 在途时产生 revision 2。revision 1 成功不能清除 revision 2；失败不能丢掉最新待保存快照。用户切换文件/profile 时仍需等待正确 owner 的终点。
- **旧派生任务晚到：** A 合法切到 B 后，A 的校验、生成字段和测量结果只能被丢弃；不能清 B 的 pending/error，不能使用旧计时器向 B 写滚动位置。
- **保存失败与切换相遇：** 必要的保存返回 error、blocked 或 deferred 时，切换停留在原页面，保持可见错误和草稿；不得先清 dirty 再显示失败。
- **布局变化：** 换行或列宽变化使旧高度失效，重新测量必须保持锚点；不能用固定行高截掉内容来消除跳动。
- **配置越权或部署漂移：** 无效类别、别名、其他项目、过期 token、保护前提变化均在效果前拒绝，目标零写入；原历史任务持续闭锁。

### 复核结论与限制

前序 inline 方案已完成两轮独立 recheck，结论为“可执行”。修订闭合了外置 profile、锁顺序、切换 outcome、直接保存队列、迟到确认、跨 tab 合并边界和退出语义。本文保存后已另经 feature-architecture 与独立 recheck 核对；文档复核要求补充“拒绝任何已有 historical scope 的嵌套准入”，已纳入第 2.1 节及阶段 1.4。当前没有未处理的必修发现；文档复核不等于实现验收。

## 四、最小实施切片、验证与关键引用

### 阶段 0：冻结基线与可用测量入口

目标：使后续性能结论可复现，不依赖一张截图或 Node 微基准。

- 0.1 固定中性 fixtures：JSON/CSV、数组/record-map、多集合；窄表/宽表、固定行高/换行、嵌套/模板内容、有/无生成字段。文件保持在现有产品预览大小上限内。
- 0.2 确认可用浏览器 trace/帧测量入口；固定机器、生产构建、刷新率、冷暖条件、网络与保存前置状态。记录读取、解析、复制、store、派生、校验、React、布局/绘制、峰值内存。
- 0.3 建议每种打开场景 30 次、每种滚动场景 3 轮各 10 秒固定路线；在基线检查点确认并冻结。无法取得浏览器证据时，不能用 Node 局部计时宣称浏览器通过。
- 0.4 明确打开计时是否包括等待旧保存；分别记录文件读取/处理耗时与切换门禁等待，避免归因混淆。

成果：fixture、复现步骤、原始测量和冻结验收口径。若证据改变后续方案，先补充计划，不直接跳到 Worker 或列虚拟化。

### 阶段 1：配置自动保存修复

目标：受保护项目仅浏览切换不再被错误要求自动化 run 上下文，失败状态和草稿可恢复。

- 1.1 在三个配置 writer 与历史效果门接入精确作用域，保留原序列化、配置锁、迁移前像检查和合法外置 profile。
- 1.2 复用保存协调器与串行链，补捕获 owner/revision、确认和错误状态；接齐文件、项目、profile 的 flush 终点与 outcome 检查。
- 1.3 在隔离受保护 root 验证仅切视图产生的 `lastActiveViews` 保存、快速连续更新、故障后恢复、旧响应晚到和 profile/project 切换。
- 1.4 验证业务/runtime/ledger/authority/其他项目、任意路径、别名、过期 scope 全部拒绝；分别覆盖在 automation、author、publication、configuration 作用域中再次配置准入的嵌套反例，历史原件字节与旧 run 拒绝不变。

完成条件：正向场景成功，故障场景保留原页面与待保存版本，越权场景零目标写入。失败处理不得靠清空草稿、关闭历史保护或用真实用户数据反复重试验证。

### 阶段 2：滚动最小切片

目标：稳定滚动不随总行数重复全量计算，测量修正不造成跳行。

- 2.1 在现有 row window/height owner 内实现增量索引；用计数断言证明单次滚动查询不扫描全部行，单点高度变化不重建整份索引。
- 2.2 批量测量、布局版本失效和锚点补偿；覆盖深滚动、首尾、筛选排序、行增删、宽度/字体/缩放/换行变化。
- 2.3 将位置写入改为内存暂存与合并 flush；覆盖旧 scope 定时器、正常退出、同 key 最后写入和其他字段保持，不宣称跨 tab 原子性。
- 2.4 验证选择、拖拽、键盘、编辑焦点和提交语义；使用阶段 0 相同路线复测脚本、总帧和布局。

建议目标，须在阶段 0 冻结且不是当前实测保证：稳定滚动 p95 帧间隔 ≤33ms，超过 50ms 的帧占比 ≤1%，没有超过 100ms 的明显停顿；滚动更新脚本预算 ≤8ms，口径包括事件、rAF 和相关 React 脚本，不包括布局/绘制。若工具无法可靠拆分，不能虚报脚本指标，应并列提交算法计数与总帧证据。位置持久化每秒不超过约 10 次，受控切换末值正确；锚点修正误差目标 ≤1px。

### 阶段 3：打开链最小切片

目标：减少确定的重复工作和平方级查找，保持同版本完整结果。

- 3.1 统一字段分类和同版本投影复用，保留现有 store 与局部 invalidation；避免查询、布局或无变化刷新导致不必要重建。
- 3.2 生成结果索引化，验证首匹配、严格类型、空/重复 ID、dirty/pending/冲突和版本刷新。
- 3.3 仅在能证明所有权时优化独占消费者复制；验证多消费者相互改值、取消及超时仍隔离，保存基线不受编辑污染。
- 3.4 同版本结果与原算法逐项比较；覆盖 A→B→A、同对象原地编辑、配置变化和关联晚完成。若分片必须补 pending/完整提交与依赖操作门禁测试。

建议目标，须阶段 0 冻结：固定字段复杂度的 1 万行 fixture，点击至同 scope 首个可交互表格 p95 ≤1 秒，完整派生与校验 ≤2 秒；同时报告最大主线程长任务和峰值内存，不把显示 loading 当可交互。生成索引构建与全部消费合计在 N→2N 时应接近线性，建议中位数增长不超过 2.5 倍，并以比较次数或查找计数确认算法改善，不能仅凭一次墙钟比率验收。

### 阶段 4：决定性检查点后补充计划
