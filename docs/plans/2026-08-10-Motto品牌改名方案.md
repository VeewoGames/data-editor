# Motto 品牌改名方案

## 方案概述

### 1. 总体目标和范围

本方案将产品对用户呈现的名称由 **Data Editor** 改为 **Motto**，让网页标题、空状态、启动提示、当前产品文档和 Codex 插件以同一品牌对外表达。

已确认的路线是“**Motto 品牌化，保留 `data-editor` 技术命名空间**”：不迁移现有用户的项目 registry、项目级配置、浏览器偏好、服务环境变量、npm/插件标识、仓库目录或 Nocturnel submodule 路径。

本方案的范围仅限 Data Editor 仓库中的品牌展示、活跃文档和插件元数据。它不修改 Nocturnel，也不改变数据编辑、保存、能力声明或服务生命周期的行为。

### 2. 各阶段任务概要

| 阶段 | 主要工作 | 预期成果 | 执行顺序 |
| --- | --- | --- | --- |
| A | 冻结范围并确认旧名称的技术身份 | 可审计的改名边界与文件清单 | 先执行 |
| B | 修改产品展示面与当前文档 | 浏览器、服务提示、文档统一显示 Motto | A 后执行 |
| C | 更新并刷新 Codex 插件展示元数据 | Codex 中以 Motto 展示，现有插件安装标识不变 | B 后执行 |
| D | 构建、定向测试与本地服务验收 | 改名不影响打开、项目切换和服务收尾 | C 后执行 |
| E | 记录迁移决定并准备提交 | 历史语义不被篡改，交付边界清晰 | D 后执行 |

### 3. 整体结构框架

```text
用户看见的品牌
├─ 网页标题 / 空状态 / 服务提示 ──> Motto
├─ README 与当前产品文档 ─────────> Motto
└─ Codex 插件展示信息 ────────────> Motto

既有技术身份（保持不变）
├─ package / plugin id / repository ─> data-editor
├─ 项目配置目录 ───────────────────> .data-editor/
├─ registry 与环境变量 ────────────> data-editor、DATA_EDITOR_*
├─ 浏览器本地偏好键 ──────────────> data-editor:*
└─ Nocturnel submodule 路径 ───────> tools/data-editor
```

## 一、已确认的决策与理由

### 1.1 品牌与技术标识分离

`Motto` 是产品名；`data-editor` 保持为当前稳定技术标识。这个边界避免以下用户可见损失：

- 改写 `%APPDATA%\\data-editor\\projects.json` 会让已有项目 registry 需要迁移；
- 改写 `.data-editor/` 会改变所有接入项目的配置位置；
- 改写 `data-editor:*` localStorage key 会丢失主题、布局、最近页面与草稿；
- 改写 `DATA_EDITOR_*`、临时目录前缀和服务识别文本会扩大服务生命周期和测试范围；
- 改写 npm/插件/仓库名或 `tools/data-editor` 会触发 Codex 安装、GitHub 远端和 Nocturnel submodule 的跨仓迁移。

因此，本轮不引入旧、新两套技术命名空间，也不做状态迁移；只替换用户看到的品牌文案。

### 1.2 历史记录保持原样

历史方案、冻结回执、ADR、测试夹具命名和已生成的审计产物应继续保留 `Data Editor` 或 `data-editor`，因为它们记录的是当时的真实上下文。后续只在当前文档索引或新增决定中标明“产品现名为 Motto”，不批量重写历史证据。

## 二、变更范围

### 2.1 产品展示与运行提示

| 位置 | 变更 | 保持不变 |
| --- | --- | --- |
| `index.html` | 页面 `<title>` 改为 `Motto` | URL、Vite 配置与端口 |
| `src/components/Sidebar.tsx` | 两个无活动项目 fallback 均改为 `Motto` | 项目 registry 中的项目 `name` 优先级 |
| `server.mjs`、`open.mjs`、`service-lifecycle.mjs` | 面向操作者的启动成功提示改为 Motto | 进程识别、端口和服务状态字段 |
| `src/App.tsx` | 仅替换对用户可见的“data-editor 后台服务”提示 | localStorage key 与项目 `.data-editor` 路径 |

日志标签、错误码、allowlist、schema `$id`、临时目录和进程清理标记均不在本轮替换范围内。特别是 `src/file-service.mjs` 的 allowlist 错误文本和 `src/entry-action-proposal-prompt.mjs` 的运行协议提示继续使用 `data-editor`；它们不是本轮产品展示白名单的一部分。

### 2.2 当前文档

更新 `README.md` 与 `docs/README.md`、`docs/01_产品概览.md` 至 `docs/11_文档合同与嵌套Schema.md`、`docs/99_当前限制与后续方向.md` 中的产品称呼和标题。命令、路径、环境变量、配置目录、localStorage key 与仓库 URL 中的 `data-editor` 均保持代码格式和原值。

文档需增加一条清晰说明：Motto 是产品显示名；出现 `data-editor` 时表示现有命令、路径或稳定配置命名空间，而不是旧产品。

### 2.3 Codex 插件

更新：

- `codex-plugin/.codex-plugin/plugin.json` 的 `displayName`、短/长描述和默认提示词；
- `codex-plugin/skills/open-data-editor/SKILL.md` 的用户可见标题与说明；

`defaultPrompt` 的自然语言入口应以 Motto 称呼产品；若需要出现 `data-editor`，必须明确其为插件机器标识或命令上下文，不能将其作为产品展示名。

保持不变：`plugin.json.name = "data-editor"`、脚本默认 `$PluginName = "data-editor"`、插件配置文件 `data-editor-plugin-config.json`，以免现有 Codex 安装和个人 marketplace 条目失效。`scripts/install-codex-plugin.ps1` 不改稳定标识或回执文案，但必须在本阶段作为刷新已安装插件副本的既有工具使用。

## 三、实施步骤与完成条件

### 阶段 A：改名前冻结

1. 重新检查 `git status --short --branch`，确认当前 Entry Action 相关脏改动不纳入本任务。
2. 用 `rg` 按“展示文案”和“技术标识”分别列出命中位置，形成精确修改白名单。
3. 确认本轮不改 `package.json.name`、`package-lock.json`、`.data-editor/`、`DATA_EDITOR_*`、localStorage key、Nocturnel 或 registry。

完成条件：白名单只包含本方案第 2 节列出的品牌文件；无无关脏文件被暂存或编辑。

### 阶段 B：统一产品品牌

1. 替换网页标题、`Sidebar.tsx` 的两个 fallback 默认名和面向操作者的服务提示。
2. 更新 README 与当前产品文档的标题、叙述和品牌说明。
3. 不替换代码语义中的 `data-editor`，尤其不得改动路径、事件名、持久化 key、临时目录、测试 fixture 与错误协议。

完成条件：品牌白名单中的无项目和服务启动/停止提示均显示 Motto；项目切换后的项目名称仍直接来自 registry。

### 阶段 C：同步 Codex 插件体验

1. 将插件展示名和自然语言说明更新为 Motto。
2. 保留插件机器名、安装目录与配置文件名为 `data-editor`。
3. 在刷新前解析脚本的实际 `$destinationRoot`，确认它精确等于当前用户目录下由该脚本管理的 `plugins/data-editor` 副本；比较其文件清单与仓库模板，记录额外文件和内容差异。
4. 因安装脚本会递归删除目标目录，先将完整目标副本复制到同级、带时间戳的恢复目录 `data-editor.backup-<timestamp>`，并核对备份可读取；发现目标并非预期插件副本、无法完成备份或存在无法解释的额外内容时停止刷新并请求用户决定。
5. 仅在前述审计和备份通过后，使用既有 `scripts/install-codex-plugin.ps1` 原位刷新已安装副本；此操作保留同一机器名和 marketplace 条目，不创建第二个插件。
6. 验证仓库模板、已安装副本与备份的 manifest 都是合法 JSON，技能说明仍能准确定位 `C:\\Code\\data-editor`，并复查 marketplace 条目仍为 `data-editor`。

完成条件：存在可恢复的安装前副本；Codex UI 的产品文案为 Motto；既有 marketplace 中的 `data-editor` 条目经原位刷新后继续可用，无需迁移或改名。

### 阶段 D：验证与服务收尾

1. 运行 `npm run typecheck` 和 `npm run build`。
2. 更新并运行 `tests/open-stop.test.mjs`：首次 `startMainService` 返回 Motto；bridge `/reopen` 的“已运行”路径同时包含 Motto；向 `openService(...)` 注入空 controller 消息，断言 `open.mjs` fallback 返回 Motto。
3. 新增或扩展 Playwright mock：`/api/projects` 返回空项目列表，以及返回非空列表但 `activeProjectId` 为 `null` 或未知值；两种场景都断言 `.sidebar-title` 为 Motto，并断言页面标题为 Motto。
4. 校验仓库模板与已安装插件副本的 manifest，并通过 Codex 实际插件界面确认展示名为 Motto；若修改涉及共享前端状态，再补相应 Playwright smoke。
5. 需要服务验证时，以 `npm run open` 确保主服务与 recovery bridge 已按正式入口启动，再按 health-first 分别验证 `http://127.0.0.1:8787/api/health` 与 `http://127.0.0.1:8791/health` 返回成功；Browser 最后停在 `http://127.0.0.1:8787/`。
6. 结束前运行 `npm run service:finalize`，读取其清理结果，并在其后独立复查两层 health、正式 URL 与临时进程/目录的 stopped/deleted/skipped 结果；不得只以该命令的退出码判定服务健康。

完成条件：构建和相关测试通过；品牌白名单内的页面标题、两个侧栏 fallback、服务提示和已安装插件文案均为 Motto；服务和现有 registry/偏好没有迁移或丢失。

### 阶段 E：审阅与提交准备

1. 复查 diff，确认没有改动技术命名空间或历史证据。
2. 将本方案与实现改动分开审阅；提交仅包含本专题的品牌文件。
3. 由用户单独确认后再执行 Git commit；提交后再询问是否 push。

完成条件：交付范围与本方案一致，现有 Entry Action 脏改动保持不受影响。

## 四、验收矩阵

| 验收项 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 品牌一致性 | 检查方案白名单内的网页标题、两个侧栏 fallback、服务成功提示、README、模板与已安装插件 manifest | 白名单中的产品展示统一为 Motto；协议、错误与持久化技术标识仍保留 `data-editor` |
| 项目名称不受影响 | 使用现有 registry 打开 Nocturnel | UI 仍显示项目名 `Nocturnel`，不是强制 Motto |
| 技术身份稳定 | 比对 `package.json.name`、`.data-editor/`、`DATA_EDITOR_*` 和 localStorage key | 所有既有值不变 |
| 插件可用 | 审计并备份后原位刷新；校验模板、安装副本、备份、marketplace 与 Codex 实际 UI | `data-editor` 插件标识继续可解析，已安装副本展示为 Motto，安装前副本可恢复 |
| 服务可用 | `service:finalize` 后独立检查两层 health 与正式 URL | `8787/api/health`、`8791/health` 均返回成功，正式入口为 `http://127.0.0.1:8787/` |
| 工作区隔离 | `git diff --check`、路径白名单和 `git status` | 无关 Entry Action 改动未混入 |

## 五、明确不在本轮范围内的事项

- 不改 npm 包名、GitHub 仓库名、远端 URL 或本地仓库目录 `C:\\Code\\data-editor`；
- 不改 Nocturnel 的 `tools/data-editor` submodule、`.gitmodules`、启动脚本、文档或 gitlink；
- 不迁移 `%APPDATA%\\data-editor`、`.data-editor/`、`DATA_EDITOR_HOME`、`DATA_EDITOR_*`、localStorage key、schema `$id`、事件名、错误码、日志标签、临时目录或测试夹具；
- 不批量重写 `docs/plans/`、`docs/records/`、`.claw/truth/` 等历史证据；
- 不处理当前工作树中的 Entry Action 相关改动，不提交、不推送。
- 不在未审计并完成可恢复备份的前提下覆盖 `%USERPROFILE%\\plugins\\data-editor`；安装前备份仅用于本轮回退，不改变 plugin id 或 marketplace 记录。

## 六、后续独立决策：是否进行完整技术改名

若未来要把 npm、插件机器名、仓库、目录、状态目录和 Nocturnel submodule 也统一为 Motto，必须另建跨仓迁移任务。该任务至少需要：停服与进程审计、registry/localStorage/配置迁移及回退方案、插件与 marketplace 重装路径、GitHub 仓库重命名、Nocturnel submodule 路径切换、全量测试与真实项目回归。它不属于本方案，也不能通过文字替换完成。
