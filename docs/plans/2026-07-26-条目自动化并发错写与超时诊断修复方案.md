# 条目自动化并发错写与超时诊断修复方案

## 方案概述

### 1. 总体目标和范围

本方案解决 Data Editor 条目自动化当前存在的三类高风险问题：

1. 多个 `entry-action` 可以并发修改同一源文件，造成整文件覆盖风险和结果归因失真；现有证据同时观察到相邻条目语义错写，但不能把每个错写唯一归因于某个并发 run。
2. Codex 子进程直接修改项目源文件，绕过 Data Editor 已有的 `rowId` 稳定定位、`documentEtag` 乐观并发控制与服务端保存校验。
3. 执行超时时，结果可能声称 `.reply.md` 已写入，但文件实际不存在；同时没有保留足够的 stdout、stderr 和写回提案证据。

目标是把条目自动化从“Codex 直接编辑源文件”重构为“Codex 生成结构化变更提案，Data Editor 服务端按稳定条目身份和文档版本原子提交”。修复完成后，任何自动化都不得绕过服务端直接写入正式数据文件。

本方案只定义 `data-editor` 工具层修复与验证路径。Nocturnel 已发生的错写数据另行审计、逐项确认和修复；本方案不授权修改、回滚或提交 Nocturnel 数据。

### 2. 各阶段任务概要

1. **0a 全局硬隔离**：服务端默认拒绝整个 `/api/entry-actions/run`，立即冻结旧的直接写文件链。
2. **0b 所有权基础**：一次性交付 canonical file identity、job supervisor、Windows Job Object、原子运行状态、fencing lock 与恢复基础。
3. **Authority 与严格定位**：建立 project-scoped writeback policy、profile 版本门禁和 strict rowId 唯一性。
4. **隔离 Proposal 协议**：取消 Codex 对正式源文件的直接修改权限，并用真实 Codex CLI scratch success/timeout E2E 证明。
5. **统一原子提交**：让 `/api/save` 与 proposal commit 共享 document commit mutex，并用 commit journal 覆盖崩溃窗口。
6. **状态、恢复与诊断收口**：完善 phase/outcome、人工恢复入口、原子 primitives、finalize marker 和文件级查询。
7. **按 Action 重新启用与正式验收**：只有完成 policy、profile、skill 和专项验证迁移的 action 才能启用。
8. **数据修复交接**：输出 Nocturnel 受影响条目审计清单，等待独立授权后处理。

执行顺序不可颠倒：先硬禁用旧写回路径并完成运行锁生命周期，再切换 job supervisor、proposal 和统一提交协议；旧的直接写文件路径删除、专项验证通过后，才允许重新启用条目自动化。

### 3. 整体结构框架

```text
详情面板动作
  -> POST /api/entry-actions/run
  -> allowlist 解析 sourcePath，生成 canonical physical file identity
  -> 服务端按 canonicalFileKey 获取带 fencingToken 的 action admission lock
  -> 服务进程内 job supervisor 持有 child handle、锁和运行状态
  -> 读取目标文档，记录 baseDocumentEtag 和稳定 rowId
  -> 生成 handoff
  -> Codex 在隔离环境中生成并原子发布 proposal
  -> job supervisor 将 proposal 交给唯一 proposal commit service
  -> proposal commit 与 /api/save 按 canonicalFileKey 共享 document commit mutex
  -> 在同一临界区内校验 proposal
       - runId / actionId / target 一致
       - 当前 fencing ownership 仍有效
       - strict rowId 合法且在 collection 中精确匹配一次
       - authority/profile 版本与当前权限交集仍允许
       - documentEtag 未过期
       - beforeValue 未变化
       - 字段位于 action 白名单
       - 字段类型、唯一性与正式 validator 通过
  -> commit journal: intent -> source_replaced -> verified -> result_published
  -> 重新按 rowId 读取并生成 writebackCheck
  -> 写入 result / reply / diagnostics
  -> 确认进程树退出后按 runId compare-and-release 运行锁
```

## 一、问题证据与影响判断

### 1. 同一源文件存在真实并发运行

2026-07-26 18:56:20 至 18:56:42，至少四个 `fill-data-name` 动作被并发发起，目标均位于：

```text
data/content/traits.json#traits
```

相关运行包括：

- `a77a7c36-e696-41ee-b03c-46f9a0db63b9`
- `06b0c505-67cb-46cf-978c-9a563f3ea124`
- `5b45fb5a-def1-4d43-83ed-637fed5bc611`
- `e3fff9de-4034-4b73-b91b-d28bb53adb1f`

前端的 `entryActionRunningId` 只能限制当前 React 页面实例，不能阻止多标签页、多浏览器窗口、多个客户端或直接 API 请求。`server.mjs::handleRunEntryAction(...)` 当前没有项目级、文件级或条目级互斥门禁。

### 2. 目标条目未写回，但附近条目出现语义错配

运行 `5b45fb5a-def1-4d43-83ed-637fed5bc611` 的目标是：

```text
rowId: 01KWNE8SR2N7CSH8WGQRKED87T
sourceRowIndex: 254
description: 技能暴击后，会对目标及邻近范围内敌人施加{中毒}。
```

运行结束后，该目标条目的 `id`、`trait_id`、`trait_name` 仍为空，但附近条目出现以下异常：

- 描述临时护甲的条目被写入 `trait_id: trait_venom_spread`、`trait_name: 毒性扩散`。
- 描述落雷与闪电链的条目被写入同一个 `trait_venom_spread`、`毒性扩散`。
- 描述护甲转暴击率的相邻条目被写入 `trait_critical_lightning_chain`、`暴击雷链`。
- `trait_venom_spread` 出现重复。

由于多个 Codex 进程同时读取并整文件写回，不能仅凭最终 diff 将每个错误字段唯一归因到某个 runId，也不能证明并发单独造成了每一处相邻错写；但可以确认最终数据与各 handoff 的稳定 rowId 和描述语义不一致。并发放大了丢失更新和归因失真，Codex 直接写正式文件且缺少严格目标提交门禁，才是错目标写入得以发生的核心安全缺口。

### 3. 当前 `writebackCheck` 只能观察结果，不能保护写回

`scripts/run-entry-action.mjs` 已在执行前后通过 `rowId` 重读目标条目，并输出：

- `fileChanged`
- `targetRowChanged`
- `changedFields`

这能发现“目标没有变化”，但发现时错误写入已经发生。`writebackCheck` 是事后观测，不是提交门禁。

### 4. `documentEtag` 没有覆盖 Codex 直接写文件路径

现有 `/api/save` 会检查 `documentEtag`，阻止旧编辑器快照覆盖外部写回。但 `codex exec` 使用可写工作区并直接修改源文件，不经过 `/api/save`，因此：

- 不校验 base document 版本；
- 不校验目标 rowId；
- 不校验字段旧值；
- 不受 Data Editor 保存队列约束；
- 无法把某次文件变化可靠归因到某个 runId。

### 5. 超时结果存在错误输出声明

两个复现 runId 都在 120 秒达到 `codex_exec_timeout`。结果消息声称：

```text
输出已写入 <runId>.reply.md
```

但对应 `.reply.md` 实际不存在。当前 runner 只把 stderr 保存在内存中，超时分支既不落盘 stderr，也不检查 output 文件是否存在，导致结果消息与运行证据不一致。

## 二、根因

### 根因 A：错误的写回所有权

当前 Codex 子进程同时承担“推理”和“正式数据提交”两项职责。它可以读取 handoff 后自行搜索、定位并整文件保存，Data Editor 无法验证它实际修改的是哪个稳定条目。

正式数据提交权必须回到 Data Editor 服务端；Codex 只负责提出字段级变更。

### 根因 B：缺少服务端并发控制

当前运行状态以 `<runId>.started.json` 和 `<runId>.result.json` 分散保存，没有以 `projectId + sourcePath` 为作用域的互斥租约。多个客户端可以同时启动作用于同一文件的动作。

因为实际写入单位是整文件，只做“同 rowId 互斥”仍不安全；最低安全粒度必须是源文件。

### 根因 C：定位锚点没有进入提交协议

handoff 和事后核对虽然带有 `rowId`，但 Codex 的实际编辑过程不受该身份约束。`sourceRowIndex` 仍可能被人工脚本、模型推理或数组下标误用。

稳定 `__entry_id` 必须成为服务端提交时不可绕过的目标身份，`sourceRowIndex` 只用于展示和诊断。

### 根因 D：执行结果协议把“输出路径”当成“输出已存在”

`outputPath` 是预期路径，不等于输出产物已经成功生成。当前结果模型没有独立表达：

- 输出是否存在；
- stdout/stderr 是否被截获；
- Codex 是否完成推理；
- 是否生成合法 proposal；
- proposal 是否提交成功。

### 根因 E：正式写入缺少统一提交临界区

现有 `/api/save` 的 ETag 检查与 `writeTextFile(...)` 之间包含异步步骤，未来 proposal commit 若另走一条“重读、比较、写入”链，两者仍可能同时通过旧 ETag 后互相覆盖。

因此，仅为 entry-action 增加长生命周期运行锁仍不够。所有正式数据写入者必须共享短生命周期 document commit mutex，并在同一临界区内完成重读、比较、校验和原子替换。

## 三、设计原则

1. **服务端拥有唯一写回权**：自动化子进程不得直接修改正式数据文件。
2. **服务进程拥有运行所有权**：job supervisor 持有 child handle、运行锁、状态推进和正式提交入口。
3. **两层并发控制**：长生命周期 action admission lock 防止同文件自动化并发；短生命周期 document commit mutex 覆盖 `/api/save`、proposal commit 和其他正式写入者。
4. **严格稳定身份**：提交只接受持久 `rowId`；找不到时拒绝，禁止回退 `sourceRowIndex`。
5. **比较后写入**：在同一提交临界区内同时校验 `baseDocumentEtag` 和字段 `beforeValue`，任一不一致都拒绝提交。
6. **最小字段补丁**：只提交 action 正式 authority 允许的字段，不接受整文档替换。
7. **结果可证明**：成功必须能对应到已完成发布的 proposal、提交结果和按 rowId 重读后的字段变化。
8. **失败不污染数据**：超时、冲突、输出缺失和校验失败都不得产生部分正式写入。
9. **新协议单轨运行**：项目处于早期阶段，不保留旧的 Codex 直接写文件兼容模式。

## 四、目标架构

### 1. 两层并发控制

本方案明确区分两种生命周期不同的锁，不能合并为一个模糊的“文件锁”。

#### 1.1 Canonical physical file identity

两层锁和文件级查询不能使用 UI 虚拟路径作为唯一键。服务端先通过 allowlist 和 `resolveDataFilePath(...)` 解析正式目标，再生成：

```text
canonicalFileKey = sha256(platform-normalized realpath)
```

Windows 规范化至少包括：

- `realpath` 解析 junction / symlink；
- 绝对路径；
- 统一大小写；
- 统一分隔符；
- 去除 `.` / `..` 语义。

handoff 同时保留用户可读的虚拟 `sourcePath` 和不可歧义的 `canonicalFileKey`。action admission lock、document commit mutex、file-scope active-run 与 commit journal 必须复用同一个 resolver，禁止各自实现路径归一化。

需要覆盖：不同 data source id、父子重叠 data source root、大小写差异、斜杠差异、`.` 段和 junction alias 最终都只能获得同一个物理文件键。

#### 1.2 Action admission lock

在接受运行请求前，服务端按以下键获取长生命周期运行锁：

```text
canonicalFileKey
```

锁文件建议保存到：

```text
<project>/.data-editor/runtime/entry-actions/locks/<source-key>.json
```

锁内容至少包括：

- `runId`
- `projectId`
- `sourcePath`
- `actionId`
- `rowId`
- `acquiredAt`
- `heartbeatAt`
- `expiresAt`
- `supervisorPid`
- `childPid`（可用时）
- `ownerToken`
- `fencingToken`

锁必须通过排他创建获得，不能使用“先检查、后写入”的竞态实现。第二个请求遇到有效锁时返回：

```text
409 ENTRY_ACTION_SOURCE_BUSY
```

首版采用“拒绝并提示当前运行”而不是自动排队。这样能保持行为可见，避免用户在未知队列中积累多个陈旧操作。

`fencingToken` 是按该 `canonicalFileKey` 单调递增的 generation。job supervisor 在运行期间更新 heartbeat；每次 heartbeat、phase 更新、commit journal 推进和 proposal commit 前，都必须原子验证 `runId + ownerToken + fencingToken` 仍为当前 owner。失去 ownership 的旧 job 只能追加诊断，不能提交、更新正式状态或覆盖锁。

锁释放执行 compare-and-release：只有完整 ownership 三元组仍匹配的 owner 才能释放，避免旧 runner 删除新运行的锁。

成功、失败、拒绝和已确认进程树终止的超时可以释放锁。若无法确认 Codex 子进程树已完全退出，锁进入 `failed_needs_recovery`，不得立即重新开放同文件 action。服务重启后依据 heartbeat、PID、runId 终态和进程树证据恢复；不能只按固定时间删除仍可能有效的锁。

不同源文件可以并行运行；同一文件即使目标 rowId 不同，也必须串行。

#### 1.3 Document commit mutex

正式数据写入使用短生命周期的文档提交互斥，键同样是：

```text
canonicalFileKey
```

以下路径必须共同复用唯一的 document commit coordinator：

- `/api/save`
- entry-action proposal commit
- 其他调用 `writeTextFile(...)` 修改正式数据的服务端路径

在同一临界区内连续完成：

1. 重读当前文件；
2. 强制校验 `documentEtag`；
3. 执行合同、类型、唯一性和业务校验；
4. 应用内存变更；
5. 原子替换正式文件；
6. 计算并返回新 ETag。

不能在 mutex 外检查 ETag、进入 mutex 后直接写入。`documentEtag` 在所有正式保存路径上改为必填，不能允许省略后绕过并发门禁。

action admission lock 可以跨越整个 Codex 推理时间；document commit mutex 只覆盖最终比较提交的短临界区。用户在 Codex 推理期间仍可保存，但该保存会改变 ETag，使旧 proposal 在提交时明确冲突，而不是被自动合并。

### 2. 服务进程内 Job Supervisor

推荐以服务进程内 job supervisor 取代当前完全脱离所有权的 detached runner：

1. `/api/entry-actions/run` 获得 action admission lock。
2. supervisor 写入 handoff 并启动 Codex 子进程。
3. API 仍立即返回 `started`，不等待执行完成。
4. supervisor 持有 child handle、ownerToken、运行阶段与诊断流。
5. Codex 正常退出并原子发布 proposal 后，supervisor 调用进程内 proposal commit service。
6. supervisor 写入终态，并在确认进程树退出后 compare-and-release 运行锁。

Windows 首选并固定使用 Job Object `KILL_ON_JOB_CLOSE` 管理 Codex 进程树。实现使用受控本机 ownership helper，以“挂起创建 → 分配 Job → 恢复主线程”消除普通 `spawn` 后再分配 Job 的逃逸窗口；也可以使用能在进程创建时绑定 job-list attribute 的等价原语，但必须由专项测试证明无窗口归属。

- child 使用 `CREATE_SUSPENDED` 创建，在任何用户代码运行前加入本 run 独占 Job Object，随后才恢复主线程；
- supervisor 持有 Job Object handle；
- Job Object handle 不可被 child 继承；
- 正常结束、超时、shutdown 和服务崩溃关闭 handle 时终止整个进程树；
- 记录 PID、进程开始时间、ownerToken、fencingToken 和 Job Object 标识；
- 挂起创建、Job Object 初始化、分配或恢复任一步失败时，安全终止尚未运行或已归属的 child，并以 `ENTRY_ACTION_PROCESS_OWNERSHIP_UNAVAILABLE` 拒绝启动；
- 不以 `taskkill /T` 或宽泛进程枚举作为降低保证的自动 fallback。

服务关闭时必须显式处理活跃 job：停止接收新任务，终止或等待受控子进程，写入可恢复状态，再进入正式 shutdown。

如果实现阶段证明必须保留 detached runner，则需要另起架构决策并重新复核，定义一次性 run token 的内部 commit API、服务离线行为、防重复提交和锁恢复。detached runner 不得自行回退为直接写正式文件。

#### 2.1 Recovery state machine

`failed_needs_recovery` 使用独立的恢复状态机：

```text
inspect
  -> ownership_confirmed_active: keep_locked
  -> ownership_confirmed_absent: compare_and_release
  -> evidence_insufficient: keep_locked
```

提供只读 inspect API 和本机 recovery CLI。释放操作必须：

1. 输入精确 runId；
2. 读取锁、原子运行状态和 Job Object / PID 开始时间证据；
3. 确认没有匹配进程树；
4. 验证当前 `runId + ownerToken + fencingToken`；
5. 原子追加 recovery record；
6. compare-and-release；
7. 幂等返回最终结果。

PID reuse、错误 owner、多次服务重启、重复 release 和证据不足必须有专项测试。不得提供“忽略证据强制解锁”按钮。

### 3. 结构化变更提案

Codex 不再直接编辑源文件，而是生成 `<runId>.proposal.json`。建议结构：

```json
{
  "version": 1,
  "runId": "<runId>",
  "actionId": "fill-data-name",
  "target": {
    "sourcePath": "data/content/traits.json",
    "collectionPath": "traits",
    "rowId": "<stable __entry_id>",
    "canonicalFileKey": "<sha256>",
    "baseDocumentEtag": "<sha256>",
    "automationProfileEtag": "<sha256>",
    "authorityDigest": "<sha256>",
    "fencingToken": 42
  },
  "changes": [
    {
      "field": "trait_name",
      "beforeExists": true,
      "before": "",
      "afterExists": true,
      "after": "毒性扩散"
    },
    {
      "field": "trait_id",
      "beforeExists": true,
      "before": "",
      "afterExists": true,
      "after": "trait_venom_spread"
    },
    {
      "field": "id",
      "beforeExists": true,
      "before": null,
      "afterExists": true,
      "after": 502
    }
  ],
  "summary": "根据中毒扩散机制补全名称和标识。"
}
```

proposal 先写入 `<runId>.proposal.tmp`，只有 Codex 正常退出并通过 schema 校验后，才由 supervisor 原子发布为 `<runId>.proposal.json`。文件存在或 JSON 可解析不代表推理完成；未完成发布的 `.tmp` 只能作为诊断，不得进入提交。

`beforeExists` / `afterExists` 用于区分字段缺失、显式 `null` 和删除语义。首版只允许唯一 field 出现一次；重复 field、未授权 remove 或相互冲突的 change 直接拒绝。

proposal 只描述目标条目的字段变化，不允许包含：

- 整文档内容；
- 第二个 rowId；
- 新增、删除或重排条目；
- schema 变化；
- action 未授权字段；
- 任意文件路径或命令。

如某类自动化未来确实需要跨条目或跨文件修改，应建立新的 action 类型和独立事务协议，不扩张本协议。

### 4. Action 写回白名单与校验 Authority

每个 target 应显式声明允许写回的字段。例如 `fill-data-name` 对 traits 的白名单为：

```json
{
  "file": "data/content/traits.json",
  "collection": "traits",
  "writableFields": ["trait_name", "trait_id", "id"]
}
```

安全 authority 固定为三层：

- 新建 project-scoped `entry-action writeback policy` 作为不可突破的最大写回字段、类型和唯一性 authority，由项目 owner 维护；
- automation profile 只能在最大权限内选择或缩小 `writableFields`，不能扩大权限；
- 本机 binding 只决定 provider 和 skill，完全不能影响写回权限。

`src/model/writeback-adapter.mjs` 保持通用执行器职责，只执行已经授权的 row patch，不承载权限策略。

当前 `src/automation-profile.mjs::normalizeTargetPairs(...)` 只保留 `file` 和 `collection`，因此阶段 1 必须同步扩展 profile schema、前端类型、Automation Settings 编辑链与测试。旧 profile 缺少 `writableFields` 时，写回型 action 必须 fail closed；不保留静默放行兼容。

writeback policy 与 automation profile 都需要内容 ETag。handoff 记录 `authorityDigest` 与 `automationProfileEtag`；commit 时重新读取当前 policy/profile，并要求：

- action 仍启用；
- target 仍存在；
- 当前 canonicalFileKey 与启动目标一致；
- proposal 字段属于“启动 profile 权限 ∩ 当前 profile 权限 ∩ 当前最大 authority”；
- policy/profile 发生任何无法证明只收窄且仍覆盖 proposal 的变化时，返回 `ENTRY_ACTION_AUTHORITY_STALE`。

实施前必须为每个写回字段建立 validator 清单，至少记录：

- 字段路径；
- 允许的数据类型；
- 是否允许 `null`、空字符串或字段缺失；
- 唯一性作用域；
- authority 来源；
- 错误代码。

`fill-data-name` 至少需要明确 `name` / `*_name`、语义 `*_id` 和数字 `id` 的类型及 collection 内唯一性。不能只笼统写“复用现有文档校验链”；当前没有证据表明通用 `/api/save` 已覆盖 traits/runes 的全部语义 ID 唯一性。

### 5. 隔离推理环境

移除 entry-action 执行链中的：

```text
--dangerously-bypass-approvals-and-sandbox
```

首版推荐先做小型可行性验证，再固定为“隔离快照 + supervisor 捕获最终结构化输出”：

1. 核查当前 Codex CLI 是否支持只读项目且仅允许指定产物目录可写；
2. 若不能被自动测试证明，则把必要上下文复制到隔离临时目录；
3. Codex 只在隔离目录内工作，supervisor 捕获最终输出并发布 proposal；
4. 正式项目数据目录不以可写方式暴露给 Codex。

无论采用哪种实现，验收标准都是：即使 skill 试图直接修改 `sourcePath`，正式文件也不会变化。

该变更将显式 supersede 现有 ADR 中“entry-action 使用 writable workspace”的条款；stdin prompt、异步 `started` 和本机 skill 解析等不冲突部分继续保留。

### 6. Proposal Commit Service

job supervisor 只把已完成发布的 proposal 交给进程内 proposal commit service。commit service 在 document commit mutex 内按以下顺序处理：

1. 原子验证当前锁的 `runId + ownerToken + fencingToken`。
2. 校验 runId、actionId、projectId、sourcePath、canonicalFileKey、collectionPath 与 handoff 完全一致。
3. 重读当前 writeback policy 与 automation profile，校验 authorityDigest、profile ETag 和当前权限交集。
4. 重读源文件并计算当前 `documentEtag`。
5. 若当前 ETag 不等于 `baseDocumentEtag`，返回 `ENTRY_ACTION_DOCUMENT_STALE`，不自动合并。
6. 使用 strict rowId resolver 直接扫描目标 collection：
   - rowId 必须为合法、非空的持久 `__entry_id`；
   - 精确匹配 0 次返回 `ENTRY_ACTION_TARGET_MISSING`；
   - 精确匹配多次返回 `ENTRY_ACTION_TARGET_ID_DUPLICATE`；
   - 绝不回退 `sourceRowIndex`。
7. 逐字段校验 `beforeExists + beforeValue`；不一致时返回 `ENTRY_ACTION_FIELD_STALE`。
8. 校验正式 authority、profile 白名单、类型、唯一性和文档规则。
9. 复用 `src/model/writeback-adapter.mjs` 按已确认唯一的 rowId 在内存模型中应用最小补丁，不在 `entry-actions.mjs` 新建第二套 row patcher。
10. 写入 `commit_intent` journal。
11. 将完整新文本原子替换正式文件，推进 journal 为 `source_replaced`。
12. 再次按 strict rowId 重读，生成 `writebackCheck`，推进为 `verified`。
13. 原子发布 result，最后推进为 `result_published`。

`writeTextFile(...)` 当前直接调用 `writeFile(...)`，本阶段应一并升级为同目录临时文件加原子替换，避免进程异常留下部分文件。

#### 6.1 Commit journal 与崩溃恢复

journal 至少记录：

- runId、ownerToken、fencingToken；
- canonicalFileKey、rowId；
- proposal digest；
- base ETag、预期 new ETag；
- 目标 before/after 快照；
- 当前 commit stage；
- 每次推进时间。

恢复时按 journal 幂等收敛：

- `commit_intent` 且源文件仍为 base ETag：未提交，可安全失败；
- `commit_intent` 但源文件已为 new ETag：表示可能在 replace 成功、journal 推进前崩溃；必须重算 proposal digest，并用 strict rowId 验证目标 after 值。全部匹配时幂等推进为 `source_replaced -> verified`，任一不匹配时进入 `failed_needs_recovery`；
- `source_replaced` 且源文件为 new ETag、目标 after 值匹配：继续 verified/result 发布；
- `verified`：补发 result；
- ETag 或目标值均不匹配：进入 `failed_needs_recovery`，不得猜测或重放。

这覆盖“正式文件已替换、result 尚未发布”的崩溃窗口，避免重跑造成重复动作。

#### 6.2 两类原子 Primitive

实现必须明确区分：

1. `exclusiveCreateLock`：对最终锁路径排他创建，绝不使用普通 temp+rename 模拟获取锁；
2. `atomicWrite/atomicReplace`：唯一 temp 名、同目录、排他创建、flush/close、rename/replace、失败后保持原字节，并按诊断策略保留或清理 temp。

运行状态 JSON、proposal、journal 和 result 使用 `atomicWrite`；正式数据使用 `atomicReplace`。Windows 文件占用导致替换失败时返回明确错误，不回退非原子覆盖。

### 7. 运行 Phase 与终态 Outcome

活动阶段与最终结果使用两个不同字段，不能混在同一个 `status` 枚举里。

活动 `phase`：

```text
queued
running
proposal_ready
committing
```

终态 `outcome`：

```text
completed_with_writeback
completed_without_changes
conflicted
rejected
failed
timed_out
failed_needs_recovery
```

其中：

- `completed_without_changes`：proposal 合法但没有需要提交的字段，例如目标已补全。
- `conflicted`：ETag、beforeValue 或目标身份发生变化。
- `timed_out`：Codex 未在等待上限内生成有效 proposal。
- `failed_needs_recovery`：执行已失败，但无法确认子进程树退出或锁可以安全释放，需要恢复流程介入。
- `completed_without_observed_writeback` 不再用于混合表达“没有修改、错写别处或无法归因”。

前端和 API 提供显式 `isTerminalEntryActionState(...)`。`queued`、`running`、`proposal_ready`、`committing` 必须继续轮询；只有存在终态 `outcome` 才结束等待。前端自身停止观察使用 `observation_timed_out`，不能与 runner 的 `timed_out` 混为同一语义。

结果文件应分别记录：

- `proposalPath` 与 `proposalAvailable`
- `replyPath` 与 `replyAvailable`
- `diagnosticsPath` 与 `diagnosticsAvailable`
- `commitAttempted`
- `commitResult`
- `writebackCheck`
- `lockReleased`

任何用户消息只能依据 `*Available` 声称产物存在，不能根据预期路径推断。

### 8. 超时、进程树与诊断

runner 从启动开始持续捕获 stdout 和 stderr，并写入受控诊断文件。超时时：

1. 阻止该 run 进入 proposal commit；
2. 使用可验证的 Windows 进程树 ownership 机制终止 Codex 主进程及其子孙进程；
3. 等待并确认确定属于本次 run 的进程树已退出；
4. 刷新并关闭诊断文件；
5. 将未完成发布的 proposal 临时文件仅作为诊断保留；
6. 按互斥分支落终态：
   - 进程树已确认退出：写 `timed_out`，compare-and-release；
   - 进程树无法确认退出：写 `failed_needs_recovery`，保持锁；
7. 两个 outcome 不能同时出现，活动状态必须满足 `outcome = null`，终态必须满足 `outcome != null`。

首版规定：任何 exec timeout 都不得提交 proposal，即使发现可解析的 proposal 文件。若进程树无法确认退出，结果进入 `failed_needs_recovery`，锁保持占用并等待人工或恢复流程处理，防止锁释放后的晚写回。

诊断文件需要限制体积，并对可能的凭据、环境变量和用户隐私内容做最小化处理。前端默认只展示摘要，完整诊断用于本机排障。

仅延长 `timeoutMs` 不是修复。待无并发和可诊断链落地后，再根据真实耗时分布调整默认等待上限。

### 9. 前端状态与文件级恢复

前端保留当前页面内的按钮禁用，但把它降级为体验优化，不再作为安全门禁。

当服务端返回 `ENTRY_ACTION_SOURCE_BUSY` 时，详情面板显示：

- 当前文件已有自动化运行；
- 当前 runId、动作和目标条目摘要；
- 查看状态入口；
- 不提供绕过锁的强制启动按钮。

“清理”继续只表示隐藏当前状态卡片，文案应改为“隐藏”，避免被理解为清理运行、删除证据或修复数据。

当前 `/api/entry-actions/latest` 按 action 和条目身份过滤，不能回答“同文件另一条目是否正在占用运行锁”。需要新增或扩展 file-scope active-run 查询，以 `projectId + canonical sourcePath` 返回当前活跃 run。

行级 `/latest` 继续用于恢复某条记录的历史反馈；文件级 active-run 接口接收虚拟 sourcePath，但服务端必须通过统一 resolver 得到 canonicalFileKey 后查询，用于 busy 状态和跨条目恢复。前端以服务端状态为准，不用当前页面实例的 `entryActionRunningId` 推断全局空闲。

## 五、分阶段实施计划

### 阶段 0a：全局硬隔离

主要工作：

- 在服务端 fail closed 拒绝整个 `/api/entry-actions/run`，返回固定错误码 `ENTRY_ACTION_PROTOCOL_DISABLED`。
- 正式运行默认禁用；测试只能通过 server constructor 的显式依赖注入启用，不能由环境变量或个人配置误开。
- 保留只读结果查询和现有运行证据，不删除 runtime 文件。

预期成果：

- 旧的直接写文件入口立即冻结，为后续重构提供稳定边界。

完成门禁：

- 正式服务、直接 API 和多客户端请求全部被一致拒绝。
- 测试注入不能通过正式配置路径启用。
- 阶段 0b 至阶段 5 完成前，正式写回保持禁用。

### 阶段 0b：所有权、文件身份与运行状态基础

主要工作：

- 实现唯一 `canonicalFileIdentity(...)`。
- 实现 `exclusiveCreateLock` 与运行状态 `atomicWrite`。
- 建立服务进程内 job supervisor。
- 使用 Windows Job Object `KILL_ON_JOB_CLOSE` 管理进程树；不可用时拒绝启动。
- 一次性交付 fencing lock、heartbeat、phase/outcome 基础、spawn 失败回收、shutdown 和 recovery state machine。

预期成果：

- child、锁、状态和恢复由同一 owner 管理，不再为 detached runner 建临时兼容层。

完成门禁：

- canonical alias 只能获得一个锁。
- heartbeat、phase 更新、commit 前置探针和 release 均验证 fencing ownership。
- spawn 失败、runner crash、PID reuse、错误 owner、服务重启和恢复幂等均有明确测试。
- 无法确认进程树退出时保持 `failed_needs_recovery`，recovery CLI 可按证据安全收敛。

### 阶段 1：Authority、Profile 版本与严格定位

主要工作：

- 新建 project-scoped entry-action writeback policy。
- 扩展 `src/automation-profile.mjs`、前端类型和 Automation Settings，使 profile 只能缩小权限。
- 为 policy/profile 增加 ETag/digest。
- 缺少或为空的 `writableFields` 对写回型 action fail closed。
- 新增 strict rowId resolver，要求持久 ID 格式合法且在 collection 中精确匹配一次。
- 为每个 writable field 建立 validator 清单和正式错误代码。

预期成果：

- proposal 的目标、字段和校验 authority 均有单一正式来源。

完成门禁：

- rowId 缺失、非法、不存在或重复时均 fail closed。
- profile 不能扩大 project-scoped policy。
- action 禁用、target 删除和运行期间权限收窄能阻止旧 proposal。
- 不能生成重复语义 ID。
- 旧 profile 不会因 normalize 丢字段后被静默放行。

### 阶段 2：隔离 Proposal 协议与真实 CLI 验证

主要工作：

- 为 handoff 增加 base ETag、profile ETag、authority digest、canonicalFileKey 和 fencingToken。
- 定义包含存在性语义的 proposal schema。
- 修改 prompt 和 skill 输出合同。
- 使用隔离快照，移除直接写正式源文件的旧执行模式。
- proposal 只在 Codex exit 0 后原子发布；超时和非零退出均不得提交。
- 完成真实 Codex CLI scratch success 与 timeout E2E。

预期成果：

- 真实 Codex CLI 能在隔离环境消费 handoff/skill 并产出结构化 proposal，正式源文件始终不可写。

完成门禁：

- 真实 CLI scratch success：proposal 成功发布，正式源文件零变化。
- 真实 CLI timeout：proposal 不提交，进程树退出或进入 recovery，等待窗口后仍无晚写回。
- skill 试图直接编辑正式文件时被隔离边界阻止。
- 未完成 `.tmp`、重复 field 和缺失/null 混淆 proposal 均被拒绝。

### 阶段 3：统一提交、Commit Journal 与崩溃恢复

主要工作：

- 建立 document commit mutex，并接入 `/api/save`、proposal commit 和其他正式数据写入路径。
- 在同一临界区内执行 fencing、authority/profile、ETag、strict rowId、beforeValue 和 validator 校验。
- 复用 `src/model/writeback-adapter.mjs` 应用已授权 patch。
- 实现 `atomicReplace` 与 commit journal。
- 实现 source 已替换但 result 未发布等崩溃窗口的幂等恢复。

预期成果：

- 普通保存和自动化提交不会交错覆盖；任何已发生的数据提交都能恢复出可信终态。

完成门禁：

- `/api/save` 与 proposal commit 基于同一旧 ETag 时只有一个成功。
- fencing、authority/profile、strict rowId 或 beforeValue 任一失败均为零写入。
- crash-after-rename 能依据 journal 收敛为正确 result。
- 原子替换失败保持原文件完整，不回退非原子覆盖。
- 成功结果中的 changedFields 与最终唯一目标条目一致。

### 阶段 4：状态、诊断、查询与 Finalize

主要工作：

- 完整接入 phase/outcome 显式终态判断。
- 持续保存受限 stdout/stderr，按真实 `*Available` 展示产物。
- 明确 `timed_out` / `failed_needs_recovery` 互斥分支。
- 增加 file-scope active-run 查询。
- 固定隔离目录为 `%TEMP%/data-editor-entry-action-<runId>`，写入 owner marker。
- 扩展 `service:finalize` 的安全清理规则。

预期成果：

- 状态、恢复、文件级 busy 和临时资源清理拥有可证明的协议。

完成门禁：

- 中间 phase 不会被前端误判为终态。
- runner `timed_out` 与前端 `observation_timed_out` 语义分离。
- 超时结果不声称不存在的输出已生成。
- file-scope 查询通过 canonicalFileKey 恢复 busy。
- finalize 只在“无匹配进程、无 active lock、存在可接受终态/恢复记录、marker 匹配”时删除；其他情况拒删。

### 阶段 5：按 Action 重新启用与正式验收

主要工作：

- 更新详情状态卡片和“隐藏”文案。
- 支持 busy、conflicted、timed_out、failed_needs_recovery 等状态。
- 增加按文件的多页面恢复和结果查看。
- 按 project/action eligibility 逐项重新启用，不做全局一次性放开。
- 完成浏览器真实交互验证。

预期成果：

- 用户能区分“仍在运行、被并发门禁阻止、提案冲突、执行超时、写回成功”。

完成门禁：

- 每个启用 action 都具备：正式 policy、合法 profile writableFields、已迁移 binding/skill、真实 CLI E2E 与专项测试。
- Nocturnel 未完成独立 owner handoff 前保持禁用。
- 执行 `npm run service:finalize`，无临时端口、进程或目录残留。
- finalize 后重新确认 `8787/api/health` 与 `8791/health` 健康。
- 正式 URL `http://127.0.0.1:8787/` 下完成真实交互验证。
- Browser 最终停留在正式 URL。

### 阶段 6：Nocturnel 数据审计与修复交接

主要工作：

- 以 runId、handoff rowId、Git 基线和最终 diff 建立受影响条目表。
- 每条记录列出描述、原值、现值、疑似来源、冲突和建议处置。
- 单独识别重复 ID、语义错名、仅补数字 ID 和无法归因的变化。

预期成果：

- 形成可逐项批准的数据修复清单。

完成门禁：

- 未经独立授权，不修改或回滚 Nocturnel 数据。
- 不用整文件恢复覆盖其他任务变更。
- 修复时只按稳定 `__entry_id` 定点处理，并逐项核对 diff。

## 六、测试与验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 同一项目、同一文件、两个客户端同时发起 | 一个进入运行，另一个收到 `ENTRY_ACTION_SOURCE_BUSY` |
| 同一项目、不同文件同时发起 | 两个动作可并行 |
| 同一文件、不同 rowId 同时发起 | 仍按文件级门禁串行 |

| proposal 使用错误或缺失 rowId | strict resolver 拒绝，正式文件零变化且不回退 sourceRowIndex |
| collection 中存在重复 `__entry_id` | 返回 `ENTRY_ACTION_TARGET_ID_DUPLICATE`，正式文件零变化 |
| proposal 使用正确 rowId、错误 sourceRowIndex | 仍严格按 rowId 定位；sourceRowIndex 不影响提交 |
| proposal 包含未授权字段 | 拒绝，正式文件零变化 |
| profile 缺少或声明空 `writableFields` | 写回型 action fail closed |
| profile 试图超出 project-scoped policy 最大权限 | 拒绝，不扩大权限 |
| 运行期间 action 被禁用、target 删除或权限收窄 | `ENTRY_ACTION_AUTHORITY_STALE`，proposal 不提交 |

| 执行期间目标字段被其他流程修改 | beforeValue 冲突，proposal 不提交 |
| proposal 产生重复 `trait_id` | 校验失败，正式文件零变化 |
| Codex 修改相邻条目或直接写文件 | 隔离环境阻止正式文件变化 |
| Codex 超时且没有 reply | `timed_out`，`replyAvailable:false` |
| Codex 超时但存在可解析 proposal 或部分诊断 | 保留受限诊断，任何超时 proposal 均不提交 |
| 真实 Codex CLI scratch success | skill/proposal 主链成功，正式源文件零变化 |
| 真实 Codex CLI scratch timeout | proposal 不提交，进程树退出或进入 recovery，无晚写回 |
| proposal 只写完临时文件、未原子发布 | 不提交 |
| proposal 对缺失字段、显式 `null` 与 remove 编码 | 通过 exists 语义精确区分，非法 remove 拒绝 |
| `queued/running/proposal_ready/committing` | 前端继续轮询，不误判为终态 |
| 无需修改的合法 proposal | `completed_without_changes` |
| 锁由错误 runId 或 ownerToken 请求释放 | compare-and-release 拒绝 |
| 旧 owner 在新 generation 建立后尝试 heartbeat、更新状态或 commit | fencing 校验拒绝 |
| spawn 失败或 supervisor crash | 写入可恢复状态，不遗留可被误删的假锁 |
| Codex 子孙进程在超时后仍存活 | 进入 `failed_needs_recovery`，不释放锁、无晚写回 |
| 服务重启时存在活跃 lease | 按 heartbeat、PID 和 runId 证据恢复，不启动第二个同文件 run |
| recovery CLI 遇到 PID reuse、错误 owner 或重复 release | 保持锁或幂等返回，不释放错误 generation |
| 数据文件已 replace、result 尚未发布时崩溃 | commit journal 恢复验证并补发唯一终态 |
| 数据文件 replace 成功、journal 仍为 `commit_intent` 时崩溃 | 以 new ETag + proposal digest + strict rowId after 值幂等推进；不匹配则 recovery |
| Windows child 启动即派生 descendant | 挂起创建期间先绑定 Job，恢复后 descendant 仍归属于同一 Job；关闭 handle 后全部退出 |
| 原子替换前进程异常 | 原文件完整，临时文件可清理 |
| 同文件另一 row 页面刷新后查看运行 | 从 file-scope active-run 接口恢复 busy 状态 |
| 点击“隐藏” | 只隐藏卡片，不删除运行证据、不改变任务状态 |
| `service:finalize` 遇到使用中的隔离目录 | 不删除 |
| `service:finalize` 遇到可证明陈旧的本工具隔离目录 | 安全清理，不触及其他临时目录 |

验证层级：

1. canonical identity、strict rowId 唯一性、proposal validator、policy/profile 版本、fencing 和原子 primitives 的 Node 单元测试。
2. `server.mjs` API 集成测试，重点覆盖 entry-action 双请求及 `/api/save` 与 proposal commit 的跨写入者竞态。

静态 diff、单元测试或 health 检查不能替代并发 API 测试与真实浏览器验收。

## 八、不采用的方案

### 1. 只延长超时

不能解决并发、错行、直接写文件、结果归因和输出缺失，还会扩大多个 Codex 进程同时持有旧快照的时间窗口。

### 2. 只禁用当前页面按钮

不能覆盖多标签页、多窗口、多客户端和直接 API 请求。前端状态不是并发安全边界。

### 3. 只做 rowId 级锁

当前写入单位仍是整文件。不同 rowId 同时写同一文件仍会互相覆盖，因此锁粒度必须至少是源文件。

### 4. 保留 Codex 直接写文件，再做事后核对

事后核对只能发现事故，不能撤销错写，也不能可靠区分本次写入和同时发生的其他写入。

### 5. 自动合并陈旧 proposal

首版不做自动三方合并。名称、语义 ID 和数字 ID 涉及唯一性及玩法语义，冲突时应拒绝并重新生成提案。

## 九、风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 锁文件因进程崩溃遗留 | heartbeat、Job Object、PID/start-time 与终态联合恢复；所有状态和提交验证 fencingToken |
| 旧 owner 在恢复后重新活动 | 单调 fencingToken；heartbeat、phase、journal、commit 和 release 全部验证当前 generation |
| 超时后子孙进程继续运行 | Windows Job Object `KILL_ON_JOB_CLOSE`；未确认退出时进入 `failed_needs_recovery` 并保持锁 |
| 数据已替换但 result 未发布 | commit journal 记录 intent/source_replaced/verified/result_published 并幂等恢复 |
| ETag 检查与正式写入交错 | `/api/save` 与 proposal commit 共享 document commit mutex |
| 虚拟路径别名绕过锁 | 两层锁、journal 和 file-scope 查询统一使用 canonical physical file identity |
| 运行期间权限被收窄 | commit 重读 policy/profile，并校验 authorityDigest、profile ETag 和当前权限交集 |
| 临时目录泄漏 | 固定 temp 根和 owner marker；仅在无进程、无 active lock、已有可接受终态时清理 |
| proposal 被手工篡改 | 提交时重新校验 handoff 身份、ETag、beforeValue 和字段白名单 |
| 真实 CLI 隔离能力未验证 | 使用隔离快照，并以真实 Codex CLI scratch success/timeout E2E 作为阶段门禁 |
| 原子 rename 在 Windows 被占用 | 明确失败状态，保留原文件，不回退到非原子覆盖 |
| 业务 ID 唯一性规则分散 | 实施前建立逐字段 validator authority 清单；缺失 authority 时 fail closed |
| 调试输出泄露敏感信息 | 诊断限长、脱敏、本机保存、前端默认不展开 |
| Nocturnel 脏工作区被误覆盖 | 数据修复独立计划、稳定 ID 定点补丁、逐项 diff 与授权 |

## 十、待确认决策

### 决策 1：是否立即临时禁用写回型 entry-action

推荐：**是**。

理由：当前已出现可验证的错行和重复 ID。在服务端文件锁与新写回协议落地前继续运行，会产生新的不可归因修改。

### 决策 2：并发请求是拒绝还是排队

推荐：**首版拒绝并返回当前 runId**。

理由：行为清晰、恢复简单，不会积累基于陈旧文档版本的排队任务。

### 决策 3：新协议覆盖范围

推荐：**通用旧直写协议一次删除，但按 project/action eligibility 逐项重新启用**。

理由：根因位于通用执行器和写回所有权，不能保留旧路径；但不同 action 的 policy、profile、skill 和 validator 迁移进度不同，不应全局一次性放开。

### 决策 4：Nocturnel 数据修复是否与工具层实施同批执行

推荐：**否**。

理由：两者属于不同仓库、不同风险和不同 owner 边界。应先冻结事故入口，再基于独立审计清单逐项修复数据。

### 决策 5：Runner 所有权架构

推荐：**服务进程内 job supervisor**。

理由：child handle、action admission lock、运行 phase、diagnostics 和 proposal commit authority 由同一 owner 管理，能显著降低 detached runner 的 token、服务离线、防重复提交和锁恢复复杂度。

### 决策 6：`writableFields` 的安全 Authority

推荐：**新建 project-scoped entry-action writeback policy 定义最大权限，automation profile 只能缩小，本机 binding 不参与权限**。

理由：通用 writeback adapter 只负责执行已授权 patch，不应混入项目权限；任何个人或本机配置都不应扩大正式数据写回能力。

### 决策 7：旧 writable-workspace ADR 的处置

推荐：**由 proposal 隔离协议显式 supersede 旧 ADR 的可写工作区条款**。

理由：新方案的核心安全边界要求 Codex 不能直接写正式数据。stdin prompt、异步 `started`、本机 skill 解析等未冲突事实继续保留。

### 决策 8：Windows 进程树 Ownership

推荐：**Windows Job Object `KILL_ON_JOB_CLOSE`，初始化失败即拒绝 action，不自动降级到 `taskkill /T` 或宽泛进程枚举**。

理由：只有明确的进程树 owner 才能证明超时、shutdown 和服务崩溃后不会发生晚写回；弱 fallback 会重新打开本次事故边界。

## 十一、完成定义

只有同时满足以下条件，工具层修复才算完成：

1. 旧写回型 action 在新协议通过全部门禁前保持硬禁用。
2. 所有虚拟别名通过 canonical physical file identity 收敛到同一锁键。
3. 同源文件 entry-action 被带 fencingToken 的 action admission lock 可靠串行化，锁具备完整 owner-safe 生命周期。
4. `/api/save`、proposal commit 和其他正式数据写入者共享 document commit mutex。
5. Codex 无法直接修改正式数据文件，只有服务进程内 commit authority 可以提交。
6. 所有自动化写回都在同一临界区验证 fencing、authority/profile 版本、strict 唯一 rowId、ETag 和字段存在性/旧值。
7. 写回字段受 project-scoped policy 与 profile 收窄白名单共同限制。
8. 类型、语义 ID 和数字 ID 校验均有明确 validator authority。
9. 数据文件、proposal、journal、result 和运行状态使用各自正确的原子 primitive。
10. commit journal 能恢复 source 已替换但 result 未发布的崩溃窗口。
11. 超时和失败不会产生部分写入、晚写回或错误锁释放。
12. `failed_needs_recovery` 有可审计、幂等且不支持无证据强制解锁的恢复入口。
13. 活动 phase 与终态 outcome 不会被前端混淆。
14. 结果不会声称不存在的输出已生成。
15. 成功状态能由完成发布的 proposal、journal、提交结果和最终唯一目标条目重读共同证明。
16. 真实 Codex CLI scratch success/timeout、跨写入者竞态、API、构建、finalize 和正式浏览器验收全部通过。
17. Nocturnel 数据修复保持独立，未经授权没有发生任何数据改动。
