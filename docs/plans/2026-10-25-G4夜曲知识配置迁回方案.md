# G4 夜曲知识配置迁回方案

## 方案概述

目标是让项目规则回到项目维护，同时让 Data Editor 继续只拥有通用编辑、保存、关联、嵌套合同、自动化、发布与历史保护机制。范围是 G3 切换后仍留在编辑器侧的项目知识、混合文档业务段落、当前产品文档示例及剩余配置材料的归属，不重新切换部署，不修改夜曲业务或玩法规则。

推荐采用**历史来源接收 + 已有规则 owner 对账 + 源入口历史化 + 通用合同保留**。夜曲已有的当前规则不动，过期来源作为历史证据接收；不把 11 份旧文档复制成新的 current 知识。项目配置已经在正确位置，G4 没有现行配置迁移写入。旧示例、物理删除和恢复包共享责任交 G5 单独处理。

| 顺序 | 主要任务 | 成果与出口 |
| --- | --- | --- |
| A：现状核实 | 重算知识/配置、引用、归属和 G3 保护状态 | 已形成 31 份知识判定清单、18 份配置保护清单及 40 路径候选白名单 |
| B：方案复核 | 架构独立取证、完整性与执行边界复核 | 本方案、执行计划及复核记录；本轮只做到这里 |
| C：候选准备 | 经用户允许后，在独立暂存区制作全部后像、分段补丁和索引隔离预演 | 精确执行包、全 before/after SHA、命令、恢复矩阵；再次提交执行确认 |
| D：正式迁回 | 用户明确确认精确包后，先接收证据，再发布源退出和索引 | 不覆盖当前项目规则；逐项 CAS 和状态回执 |
| E：验收 | 双仓链接/检索、通用合同保留、配置/业务/历史保护核验 | G4 验收记录；G5 继续独立 |

结构依次为当前事实与清单、owner 与不变量、承接与发布顺序、精确包要求、验证与恢复、决策。此文是正式规划参考，当前不是 apply bundle。对应的树状实施步骤见同名执行计划。

对设计师的影响：继续在夜曲现行规则和项目配置中维护游戏内容；编辑器升级不再从旧工具知识补入预算、评审状态或视图规则。历史经验仍可查，但会明确标成历史，不再与当前规则竞争。

## 三、推荐承接与发布顺序

### 3.1 精确接收位置

拟新建夜曲来源目录：`C:\Code\Nocturnel\docs\records\data-editor知识迁回来源\2026-10-25\`。其中 `objects/<原字节SHA>.source` 保存 16 份源 Markdown 的原始字节，create-only；`manifest.v1.json` 记录原绝对路径、SHA、大小、主题、段落归属和当前规则指向。不把 `.source` 作为可执行配置或当前检索正文。这些是有长期追溯价值的知识来源，方案建议保留于项目协作记录，不放个人忽略目录；不修改 Git ignore 或自动提交。

拟新建夜曲历史索引：`.claw/truth/tech/data-editor/编辑器侧项目知识承接与历史索引.md`，显式 `<!-- document-state: historical -->`。按 ADR0262 进入 tech 层；列出全部来源、现行 owner、过期原因和当前配置路径，不复制一套完整预算或旧筛选规则。更新夜曲 SUMMARY 的历史入口，不降级或覆盖已有 current 主题。

### 3.2 状态与跨仓一致性

暂存内容放本轮独立候选目录，**不能先放入 `.claw/truth` 再自称 draft**：Claw Truth 默认 current，允许状态只有 Truth current/historical、ADR accepted/superseded/historical。不得发明 draft、redirect 等 document-state；redirect 只是正文说明。

逐项顺序：

1. 刷新源/目标/保护/引用基线，冻结所有后像；确认现有夜曲 owner 已覆盖当前规则。
2. create-only 接收原字节和 manifest；全量摘要验证。已有相同字节可识别为已接收，异字节拒绝。
3. 发布 historical 索引并原生刷新夜曲检索，确认可达且不竞争 current。**现有 current owner 仍保持原样**。
4. 对 11 源以文件 CAS 替换为同路径 historical 迁移说明；对 5 混合源保留 generic current、移出或显式 dated history 标注业务段；再更新已冻结的引用、编辑器 SUMMARY 与两份中立产品文档。
5. 原生刷新 Data Editor 检索；按源别名、主题与现行 owner 逐项验证状态、链接、命中范围，生成回执。跨仓不是原子事务，不宣称文件写完等于检索已切换。

最小历史说明包含原题名、原 SHA、迁回日期、目标索引与原字节映射、现行规则 owner、历史不得作为当前执行依据的说明；不继续携带旧业务操作规则。源文件不物理删除，冻结任务与 archive 的旧入引用仍能到达历史说明。

如果某条新知识未被现有 Night owner 覆盖，先保留为历史/待决定，不自动增补 current。任何需要新增/修改当前游戏规则、扩展当前 40 路径或新增 ADR 的事项必须重新复核并提交用户决定。

候选先在隔离内容副本中验证，不启动应用、不注册 fixture 项目、不调用业务动作。原生命令已由当前 CLI 帮助确认支持 `claw search index --refresh`；本轮 help 附带后台 completion refresh deferred 解析诊断，尚未做刷新预演。遵守夜曲 ADR0262：刷新前先取得受支持的一致性数据库备份；在独立副本证明备份可用与恢复条件，不能仅拷贝活跃 `.sqlite` 而遗漏 WAL。若无可靠备份方式，停在检查点，补充受控备份/写者静默方案并复核，未解决不操作 live 索引。正式包须证明隔离索引刷新完成及状态检索有效，不能忽略诊断后称通过，不直接修补 live DB 或扩写配置。备份只用于派生索引恢复；内容已变化或有其他写者时优先从最新源原生重建，不盲目覆盖旧数据库。

## 五、验证、停止与恢复

### 5.1 验收矩阵

- **归属**：16 源逐项覆盖；11 原项目源不再输出 current/accepted 业务规则；5 混合源保留通用内容；预算/评审/描述/共享配置 current owner 与基线一致。
- **引用**：候选清单内全部 Markdown 链接及纯文本 authority 引用有正确去向；源同路径历史入口和锚点重基有效；历史对象通过 manifest 查得到，不要求 `.source` 自身相对链接可执行。
- **检索**：两仓原生刷新成功；每项至少题名、原别名、主题三组查询。11 份整体退出源及 5 份混合源的项目历史段不得继续作为 current/accepted；通用 Truth current / ADR accepted 保持。Night historical 索引明确历史，当前查询指向原有主题 owner。索引失败视为迁移未完成。
- **通用保留**：中立默认、仓库自有 fixture、文档合同、shared/profile 分层、ETag、fencing、历史非重放和恢复协议的现有 owner 保持，不要求无关代码/CLI/UI 全量回归。
- **数据与保护**：前后只读校验当前业务、配置、六份现行 Night owner、authority/ledger/evidence/provenance；复跑只读部署与旧 run 拒绝检查。若存在其他合法写者，保留数据、分类漂移，不覆盖或把全目录备份恢复。
- **范围**：写入只落确认包；无 delete、无新业务动作、无服务重启。G3 四个审批受阻的临时/证据目录及旧包失败现场继续保留，G4 不借机删除。

### 5.2 失败恢复

| 位置 | 处理 |

| 接收前源/目标/保护或归属有漂移 | 零正式迁移写入；记录差异，重新对账与冻结；不覆盖最新数据 |
| 仅接收部分原字节 | 保留已接收对象；按同 SHA create-only 续作，源 current 未变 |
| historical 索引已发布，源尚未退出 | 可保留历史接收物；项目现有 current 不变；未完成项不宣称迁回完成 |
| 部分源退出后中断 | 按逐项 receipt/实际字节向前完成同一冻结包；未知字节停止。既有 Night current owner 始终可用 |
| 目标或源被他人修改 | 不自动重放替换；重新对账。只在文件仍精确等于本轮 after 且没有新的承接依赖时，才允许审核后的单文件恢复；不能整仓恢复 |
| 索引刷新失败或仍有旧 current | 保留正确内容及失败证据，原生重建派生索引并复验；不直接改 SQLite，不通过修改游戏规则或部署保护补救；未通过不结项 |
| 历史闭锁、authority 或业务保护异常 | 停止知识发布并保留现场；不回滚 catalog、启用旧 reader、恢复业务/runtime/publication 或重签证明，交对应 owner 处理 |

本方案不新增一套永久迁移框架。临时验证脚本和一份内容清单足够；跨仓一致性由精确内容、顺序、CAS、原生索引和可审计回执共同限定，不冒充事务原子性。

## 六、复核与待确认

架构子代理已独立取证，认可 owner 与分阶段边界，提出的旧预算 authority、Claw 状态值、真实 fixture 依赖和旧示例风险均纳入本方案。独立复核结果及修改闭环见本轮复核记录。
