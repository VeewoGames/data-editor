# 项目后台计算开关方案

日期：2026-10-14。归档状态：通用项目进程控制能力已交付；Nocturnel 专用后台接入随后被人工 ingame 开关替代并移除。下文保留当时的实施证据及验收限制；旧 producer 路径仅是历史引用，相关脚本已退役。

## 一、问题、边界与不变量

### 概述

目标是在 Data Editor 左侧项目区域的自动化魔杖右边增加一个后台计算电源按钮，让用户看见进程实际状态，并直接启动或停止它。关闭后，无论重新打开编辑器还是重启电脑，都保持禁止自动启动，直到用户再次点击开启。首版只由 Nocturnel 声明此能力，其他现有项目不显示按钮。

整体结构为“项目能力声明 → Data Editor 通用控制与本机设置 → 项目生命周期 → 既有生成结果读取”。Data Editor 负责可复用的开关、许可、偏好和命令协调；Nocturnel 负责后台计算及实例身份。实施按三阶段推进：先建立通用声明和控制合同，再接入项目生命周期并迁移启动/停止入口，最后接入按钮和真实页面验证。每阶段的成果与完成条件见第四部分。

从设计师角度看，这是一项后台计算的手动控制功能：关掉可以停止计算开销；重新打开编辑器不会偷偷恢复。按钮亮起表示程序确实已就绪，不表示技能已通过评审或生成值一定有效。

### 已确认需求

1. 按钮紧邻自动化魔杖右侧，沿用现有项目按钮的尺寸、焦点与悬停说明。
2. 显隐由有效项目能力声明决定，不能判断 `projectName === 'Nocturnel'`，也不能根据 `ingame` 字段存在决定。
3. 本机许可、用户开关意图、实际进程状态和生成结果有效性分别处理。
4. 持久停用是用户明确要求；刷新、项目切换和打开脚本不得覆盖关闭意图。不开设 Windows 开机自启任务。
5. 停止只作用于该项目后台实例，不停止共享 Data Editor，不删除已有结果，不修改原始技能。
6. 当前范围为 Windows、一个固定 Node 生命周期协议和 Nocturnel 一个接入实例。没有多 provider、自定义 shell、任意参数、插件市场、后台自动重启或生成字段协议扩展。

| 当前事实 | 本方案改变 |
|---|---|

| [项目打开脚本](../../../../Nocturnel/scripts/tools/open-data-editor.ps1#L30)无条件启动 watch | 去掉直接启动块，改用同一控制入口读取偏好 |
| [项目停止脚本](../../../../Nocturnel/scripts/tools/stop-data-editor.ps1#L7)直接停止 producer | 改为同一入口先持久停用，再安全停止 |

### 界面状态

| 观察状态 | 显示与行为 |
|---|---|
| `running` | 绿色电源，说明“后台计算：运行中”；点击请求停止 |
| `stopped` | 灰色电源，说明“后台计算：已停止”；点击请求开启 |
| `starting` / `stopping` | 进度状态，禁用重复点击；由当前控制操作确认，不能保存为跨重启真值 |
| `unknown` | 问号/警示及原因；不得当成已停止，不盲目启停或误杀 |
| `failed` | 失败说明与有条件的重试；只能在已证实失败时使用 |

停止失败且目标仍存活时显示 `running` 加停止错误，同时说明“已禁止下次自动启动，当前停止尚未完成”。开启偏好为 true 但尚未就绪，也不能显示 running。视觉外另提供可访问名称、状态文本和悬停原因。

## 二、新增或改变的概念、唯一 owner 与数据流

### 项目声明与通用边界

在现有 `.data-editor/project.json` 和 capability registry 增加一类项目范围的进程能力，建议名称 `project-process-v1`。声明只含能力 ID、显示名称、固定协议版本、项目内入口与必要的实例状态资源位置。它不匹配某个文档、集合或数据字段，不能硬塞进现有文档 `match` 元组。

首版协议只支持固定 Node 启动、状态查询和停止参数；服务端解析真实 root 和入口，客户端不能传 shell、路径、PID、环境变量或任意 argv。协议的 API 字段在实现时冻结，不为未来平台预造可插拔 provider。Nocturnel 提供自身入口声明；通用编辑器中不出现该项目的业务 ID、计算规则或固定仓库路径。

声明语法无效仍遵守现有 manifest 的校验规则。合法声明下的入口缺失、许可失效、状态不可读或启动失败，属于单个进程 binding 的诊断；不得接入所有能力的资源存在校验并使项目整体退化，连带阻断原始数据保存。复用 [registry](../../../src/project-capability-registry.mjs#L35) 的项目身份、generation 和受控声明变更机制；合法的入口/协议变更使旧执行许可失配。此处不放宽现有数据 binding 的身份及保存约束。

### 唯一事实来源

| 事实 | 唯一 owner | 生命周期 |
|---|---|---|
| 项目声明及绑定身份 | 项目 manifest + 现有 registry | 随项目声明变化，绑定真实注册项目 ID/root |
| 执行许可与 `desiredEnabled`、`intentVersion` | Data Editor 本机进程设置记录 | 跨页面、编辑器重启与电脑重启保留 |
| 当前命令和状态投影 | 通用项目进程协调模块 | API、CLI 共用；操作临时状态不充当持久事实 |
| 实例单一性、身份、ready 和退出 | 项目生命周期 | kernel pipe 与 PID/root/script/nonce/创建时间核验 |
| `ingame` 值及其有效性 | Nocturnel producer + 既有 reader | 原子结果与依赖摘要，保持现有合同 |

本机进程设置放在 [runtimeHome/dataEditorHome](../../../src/project-registry.mjs#L10) 指向的同一 Data Editor home；按注册项目 ID、规范真实 root 和进程 ID识别。许可与偏好合为一份窄记录，不新建项目 registry，不放进团队 manifest、LKG、视图 profile 或 producer PID 文件。

UI、HTTP API、离线 CLI 和项目打开/停止脚本调用同一个协调模块及同一 `DATA_EDITOR_HOME`/registry 身份。Editor 未运行时，CLI 仍可保存停用并执行已许可的停止；不必为了设置关闭而启动共享 Editor。不同 home 不得被当成同一设置实例悄悄回退。

### 操作顺序与并发

正常控制流程为：显式项目/进程 ID与目标动作 → registry 解析与声明版本核验 → 同一目标的跨进程操作互斥 → 校验期望 `intentVersion` → 原子持久意图和递增版本 → 执行已许可的固定动作 → 核实当前实例 → 返回实际状态、意图版本和诊断。

1. HTTP 多页面与离线 CLI 必须取得同一控制目标的互斥；内存队列或仅原子写文件不够。互斥只保护短期控制操作，异常退出由 OS 释放；实例长期互斥仍由项目 kernel pipe 负责，两者职责不同。
2. 复用 [atomicWrite](../../../src/atomic-file.mjs#L74) 持久化小记录；互斥内比较并更新意图版本。过期反向命令返回冲突，不盲重试覆盖新意图；重复同目标命令核实后幂等。
3. 人工许可弹窗不能长期占住控制互斥。首次关闭先保存 false，再释放操作等待许可；许可确认后重新取得互斥并核对原动作、声明摘要及意图版本，只能继续该次 stop，不能转换成 start。取消许可或期间出现新的有效意图时不执行旧动作。
4. 首次开启先完成需要的许可；接受后在互斥内保存 true，再确保实例已就绪。取消许可不开始执行。所有执行动作仍需校验许可记录，客户端不能用 `trusted=true` 绕过检查。
5. 开始/停止操作和锁等待均有有限超时；超时或协调模块崩溃后重新观察实例。已持久的意图保留，不重放旧操作，不建立自动重试队列或 supervisor。
6. 打开项目时仅在许可有效且 `desiredEnabled=true` 时确保实例存在；false不启动，也不自动杀掉原本已存在的实例。状态观察不改变用户意图。

### 许可与状态查询

默认无许可且无偏好时为 false，不自动启动或停止已有进程。首次任何需要执行项目代码的操作都可触发明确许可，包括已有实例第一次点击关闭；不能要求用户先开启再关闭。许可界面说明真实 root、入口、固定执行范围，以及该入口及其导入代码将以当前用户权限运行。

许可绑定真实 root、进程 ID、入口和固定协议/执行声明摘要。普通源码字节维护不重复许可，意味着信任该项目入口的后续维护；更换入口/root/协议须重新许可。项目内路径检查不是沙盒。本次用户同意架构，不等于本轮已经写入本机许可记录。

未许可时不能运行项目 `status` 代码。可以仅读取声明允许的元数据并核对 OS 证据；不足就返回 unknown。获得许可后新增结构化 status/ready 合同，ready必须对应当前 nonce/ownerToken和OS身份，并确认该实例已进入就绪阶段。旧 `ingame.json`、历史 PID和启动命令返回成功均不能证明新实例就绪。

启动复用 [persistent-process](../../../src/persistent-process.mjs#L6) 的 Windows 隐藏 broker、固定 Node runtime、固定参数和 `shell:false`。不新增常驻管理进程、监听端口或复制 Windows Job 平台；共享 recovery bridge 只管理 Editor 本身，不能用它的 stop-service 充当该按钮。

## 三、推荐决策、关键理由与一个关键失败路径

### 已采用方案与取舍

采用“项目声明固定入口 + 本机许可及开关意图 + 一个通用协调模块 + 项目已有生命周期”。这是满足通用编辑器与项目专用计算共同要求的最小边界：声明决定是否有按钮，本机设置决定是否允许执行及是否自动恢复，项目实例决定真实运行，reader决定值是否有效。

不采用在 Sidebar 硬编码 Nocturnel 的路径/命令；这会使通用产品承载业务。也不只增加按钮并保留旧直接启动块，否则停用意图会被下一次打开覆盖。不复制 EntryAction 的 fencing、journal、admission或promotion体系；其[当前合同](../../../src/fencing-lock.mjs#L1)服务 canonical 文件写入和证据链，不是进程开关的直接复用对象。

### 关键失败路径

用户关闭 → false意图已原子持久 → 协调模块在 stop前异常退出 → 原进程可能仍在运行。重新打开时读取 false，不启动、不擅自改回 true；状态查询若确认实例存活，显示 running及“停止尚未完成”，用户可再次显式关闭。临时 starting/stopping不得跨重启保留并遮蔽真实事实。

如果锁元数据中的 PID已被其他进程复用，状态为 unknown/身份失配，不能误杀或强占。项目[已有停止机制](../../../../Nocturnel/tools/analysis/skill-ingame-lifecycle.mjs#L83)执行前后核验身份；新增控制和查询继续沿用它。清理只有在确认对应 owner已退出且不会碰到新实例时才发生。

### 对生成字段与保存的影响

停止计算后不再自动重算，但已有结果仍可按现有摘要显示。输入改变后结果失配，显示未知，不统一改为 false；重新开启后以新快照计算。外部原始文档变化仍沿用现有文档版本失配与显式重新载入规则，不增加自动工作区重载。本按钮不承载评级、实现验收或施放成功判断。

### 优雅性原则

保留的必要复杂度只有：明确执行许可、持久用户意图、跨入口互斥/CAS和当前实例身份/就绪核验。移除任何一项都会破坏本次明确需求或状态正确性。

复用现有 registry/home、atomicWrite、隐藏 broker和项目实例锁；许可与偏好合并记录，API/CLI合并 owner，状态与结果诊断独立。没有新增项目注册中心、后台重启服务、多 provider框架、TTL、结果协议、开机任务或复杂文档事务。

### 独立优雅性复核结论

结论：可执行（方案准备度），无必须修复项，未发现已确认的过度设计。许可与意图合并为窄记录、API/CLI统一owner及现有启动原语复用合理；短期操作互斥/CAS与项目长期单实例锁不重复，分别解决命令竞争与实例唯一性。实际进程状态、意图与产物有效性不能进一步合并。

复核建议只补强一条已有合同的验证：人工许可等待期间若另一页面/CLI提交相反意图或声明变化，旧确认不得覆盖新意图；已纳入第四部分矩阵。详见[独立复核记录](../../../.claw/tasks/2026-10-14/项目后台计算开关方案与优雅性复核/优雅性复核.md)。这是文档与源码边界审查，不证明新功能已运行。

## 四、最小实施切片、验证与关键引用

### 阶段顺序与完成条件

| 阶段 | 主要工作 | 预期成果与完成条件 | 下一阶段依赖 |
|---|---|---|---|
| 1：通用控制合同 | 扩窄项目声明、registry投影、本机许可/意图、共用协调模块及API/离线CLI | 未许可不执行；持久停用、跨入口互斥/CAS、单binding故障隔离有可复现反例 | 协议、版本和本机home已冻结 |
| 2：项目接入 | Nocturnel补status/ready；声明入口；迁移open/stop脚本直启直停 | 同一意图覆盖所有已知入口；复用合法实例、身份失配不误杀、关闭后重复打开不启动 | 真实实例状态可由固定协议观察 |
| 3：按钮与验收 | Sidebar按钮、按项目状态刷新、许可流程及切换保护 | Nocturnel可控；其他现有项目隐藏；真实页面状态、持久关闭、保存隔离通过 | 前两阶段合同可用，部署前完成独立审查 |

这是已授权实施的切片安排。第一阶段接口已冻结，跨仓修改清单、写入边界及当前任务由 Claw 管理；声明激活与正式许可验收在实现和独立审查通过后进行。首版不宣称已支持 Windows 以外的平台。

### 验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 当前Nocturnel/其他未声明项目 | 魔杖右出现/隐藏按钮，不能因项目名或ingame字段误显示 |
| 未许可的启动、状态代码和已有实例首次停止 | 不越权执行；首次stop可直接许可；确认后仍只stop |
| stop取消许可、执行失败、持久意图后崩溃 | false保留；实际仍运行/unknown时不谎报已停止 |
| 关闭后刷新、项目切换、重复打开、服务/电脑重启 | 不把false改为true，不自动恢复；电脑重启验证须实际证据，不由unit test冒充 |
| 双页/HTTP与离线CLI同时或相反操作 | 一份home及同一互斥，旧版本拒绝，最终意图和实例一致 |
| 人工许可弹窗等待期间，另一页面/CLI改为相反意图或声明变化 | 旧确认冲突或取消，不重试覆盖新意图，也不执行旧动作 |
| 旧产物存在、新实例未ready、PID复用/查询超时 | 不以产物或PID存在证明运行；不误杀、错误可解释 |
| 开启后退出/停止超时，目标仍在运行 | 实际状态和诊断一致，无后台自动重启 |
| 入口缺失/未许可/查询失败、原始技能保存 | 仅进程binding不可用，既有保存合同照常工作 |
| 停止后结果仍有效/依赖变化/重新开启 | 保留有效值；变化后unknown；恢复后按新数据重算，raw中不写ingame |
| 操作中切换项目/多页晚响应 | 动作只作用于发起项目，旧响应不覆盖新项目状态 |
