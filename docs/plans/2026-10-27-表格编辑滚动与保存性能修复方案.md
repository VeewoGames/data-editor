# 表格编辑、滚动与保存性能修复方案

## 方案概述

### 目标与范围

解决 Data Editor 在表格滚动、编辑单元格、切换单元格/失焦及自动保存期间的明显卡顿，同时保证数据安全和跨项目通用性。重点覆盖普通文本、带标记的结构化文本、换行行高、筛选排序和自动化历史记录较多的项目。本方案只设计和复核，不授权修改代码、业务数据、正式服务或激活升级。

### 执行顺序与预期成果

1. **阶段 0：真实路径基线与安全复现。** 固定数据、配置和交互场景，拆分失焦、浏览器主线程与保存各阶段耗时；隔离复现草稿风险，得到可比较的基线和瓶颈排序。
2. **阶段 1：修复可观测的保存前开销。** 优先研究运行记录扫描和历史证明重复工作，先证明跨进程完整性与故障恢复，再确定最小安全实现；产出不会漏判活动任务的保存路径。
3. **阶段 2：收敛失焦提交与草稿生命周期。** 以单元格身份保护当前草稿，确保切换、滚出、关闭及强制保存的正确性；依据性能证据减少同步序列化和失焦后的无效重算。
4. **阶段 3：滚动与表格派生优化。** 沿现有虚拟行窗口、测量、视图和校验 owner 做精确失效及复用，保持筛选排序、行锚点和选区结果一致。具体优化由阶段 0 证据决定。
5. **阶段 4：整体验收与受保护交付。** 重跑相同基线、并发及故障反例，检查通用项目；正式部署遵循当前受保护升级流程。阶段 0 或阶段 1 的安全检查不通过时，只规划到该检查点并停止相应实现。

草稿完整性的复现和必要修复可在阶段 0 后优先进行，不必等待保存性能优化；两个方向的交付仍需共同通过阶段 4。

### 整体结构

交互层管理活动编辑草稿；文档模型拥有已提交内容；表格/视图按变化与布局依赖派生显示；保存协调器拥有 dirty revision 与确认状态；自动化运行状态和历史证明由服务端既有 owner 持有；持久写入继续由提交协调、合同校验、journal 和写后验证共同约束。缓存或索引仅作为可证明的新鲜派生数据，不能成为新的授权真值。

## 安全与通用性不变量

- 数据文件、文档 model、运行状态、历史证明各有原 owner；派生缓存不能单独授权写入或替代 authoritative 记录，不能按项目名、路径、字段名或历史数量写业务特例。普通 JSON/CSV、数组及 record-map、项目无模板配置、不同声明式模板、合法外置 profile 均需覆盖。
- 保存必须保留已有内容 ETag、合同版本及准入、生成字段/字段写保护、同源活动任务准入、按规定的隔离/锁序、幂等键、journal、持久化后的校验和恢复。失败、冲突、不可验证、断线或超时均保留草稿与 dirty；旧响应只确认其快照 revision，不能清除后续输入。
- 编辑器与 model 之间按项目、文件、collection、稳定 rowId、字段和语言绑定草稿。切换行/字段/文件、失焦、滚出窗口、卸载、显式保存、关闭、生成及异常路径均须界定 flush 或保留时机；避免重复提交、旧回调写入新单元格；输入法组合、选区、撤销、标记结构与复制粘贴保持正确。
- 主键或引用真实变化时，仍须完整检查关联影响并按现有确认协议处理；不可仅根据“此次输入看起来不是主键”跳过一个在途或先前未完成的主键变更。
- 高度缓存基于稳定行身份、顺序、列宽、字体、换行及实际内容失效；保留上轮增量索引、批量测量、滚动锚点和编辑选区，不以全表 revision 无差别丢弃测量，也不能复用过期高度。

## 推荐设计与实施检查点

### 1. 保存检查：先量化，再证明安全

先为一次保存建立关联的阶段计时：队列等待、主键影响准备、快照克隆与序列化、合同读取、HTTP 传输、同源协调等待、运行记录枚举/读取、历史 binding/ledger/证明及锁等待、字段和合同校验、journal/替换/写后核验。记录耗时、数量和错误码，不记录文本内容、私有路径或原始业务数据；区分冷/热、进程状态与是否存在其他操作。只读测量不等于真实保存耗时，必须在独立 fixture 上执行带可核验结果的实际保存。

候选路线依次检查：先查找现有运行状态 owner 和可复用的不可变证明，能安全消除重复投影时优先做局部复用；若证据证明仍需活动索引，设计由运行状态 owner 维护的按文件身份定位的派生索引。索引的完备性、记录创建与终态、follow-up/recovery、跨进程发布、失效、启动恢复、目录外部改写和历史证明更新必须可证明。**进程内 `documentCommitCoordinator` 不能被当作跨进程锁；文件 watcher、mtime、TTL、空结果和缓存命中本身都不能证明不存在活动任务。**

特别复核活动扫描入口对无法解析的 handoff 的跳过、历史证明投影对验证失败的处理，以及 `ordinarySaveBlockingRuns` 在存在候选 run 时再次执行历史投影的语义；分别测量，不预先删除任何一次核验。检查启动、阶段转换、提案提交和恢复路径的所有生产者，以及检查完成到文件替换之间的新任务竞争窗口。

历史 receipt 的验证还依赖当前部署状态及 live 证据；仅凭 ledger 或 receipt 摘要未变化，不能缓存整次“验证成功”。可首先评估复用内容寻址的不可变对象解析与摘要，但所有依赖可变文件、authority、时序或当前状态的部分仍须按合同核验。

是否满足上述合同由专门检查点决定：在现有所有生产者和真实跨进程/异常退出模型下，给出可验证的原子边界和锁序；无法证明时保持现有权威路径、按错误语义阻塞或等待，并只做不影响决策语义的局部优化。不能直接用空列表绕过 `projectHistoricalRunActivity`，除非同时证明 binding/ledger/authority 校验及错误行为等价。此方案不删除、压缩或改写历史数据，不假设缓存可替代安全门禁。

### 2. 单元格：草稿与提交分开

复用现有 active editor handle 和文档 revision；明确草稿的唯一 owner 和身份，统一普通输入框与 contentEditable 的强制 flush/取消/卸载时序。先通过真实浏览器验证现有风险，再选择“滚出前提交”或“稳定持有草稿直到提交”的实现；组合输入未完成时不能丢字符，异常卸载不能将未确认内容伪装为已保存。模板 DOM 的序列化成本按基线优化，保证标记和 selection 等价，不能简单以纯文本替换。

### 3. 失效与滚动：复用现有能力

根据提交的行、字段和依赖，复用现有 store、校验失效和 view engine；只在可证明依赖不变时保留其他行引用和派生结果。变更影响筛选、排序、关联、主键、生成字段、校验、行序或跨行规则时，执行对应完整重算；无法证明依赖时走完整路径。缓存按版本和真实依赖失效，不通过跳过完整校验掩盖延迟。

行高沿用现有增量索引：普通内容变更失效受影响行的测量，结构/顺序改变重建或同步顺序，布局配置、字体、宽度和换行变化按实际影响失效；保留挂载行批量测量和位置锚点。检查窄/宽表可见列、DOM 数量、标记节点创建及 React 提交耗时。Worker、列虚拟化、增量写入协议只在 trace 证实必要且另行完成合同设计复核后启用，不预先引入。

## 验证与验收

1. **基线夹具。** 独立临时项目包含结构化标记、不同文本长度、换行、宽列、筛选排序/关联、普通文本和足够历史记录；至少一组匹配截图的中等表、另一组为更大表，并覆盖空/小项目。隔离项目不得写真实用户数据。记录数据规模、浏览器前台、视口、硬件负载、构建版本、路线、冷/热、样本次数与滚动事件数。
2. **交互度量。** 实际输入后切换、失焦、连续滚动、快速滚出和返回、普通文本与结构化文本分别采集；每个可重复场景至少 30 次完成样本，报告输入/失焦到可交互与可见结果的 p50/p95/max、主线程长任务、帧间隔及事件数，避免用空闲帧稀释滚动帧。记录失败和超时而非剔除。以前台正式构建复测；测试机、输入方法和内容相同，给出前后对照。
3. **保存度量。** 针对小/中/大文档和少/多历史记录，分别测冷启动、热路径、无活动、活动中和异常状态；每场景至少 30 次实际隔离保存，报告端到端到确认的 p50/p95/max、每阶段耗时和保存期间主线程长任务。`saving`、`pending`、`blocked` 和最终成功/失败分别计时；同时记录服务端 `Server-Timing` 的现有总耗时及新分段。以阶段 0 的结果冻结具体目标；建议首要目标为不再随已终止历史条数线性增长、常态保存显著缩短，同时不承诺任意机器或规模永不卡顿。
4. **数据安全。** 真浏览器验证输入→切换/失焦→滚出/返回→重载；覆盖 IME、复制剪切、标记结构、撤销、排序/筛选、选区、字号/宽度变化、生成中继续输入。注入旧响应晚到、ETag 冲突、网络中断、合同变化、写盘失败、写后校验失败、进程中断及重启；逐项比较磁盘内容、草稿、dirty、状态和恢复结果。原子替换或回滚机制不得通过测试绕过。
5. **活动索引反例。** 如果采用索引，覆盖两个进程同时启动/保存、创建记录与发布索引之间崩溃、终态写入中断、follow-up/recovery、受保护旧 run、外部文件改写、损坏与缺失、证明/配置/authority 升级、重启和索引重建。任何不完整状态不得漏放行；与原权威全量判定做结果及错误等价对比。
6. **通用性与回归。** 使用无项目模板的通用 JSON/CSV、带模板项目、其他声明式字段、record-map、多集合、不同引用关系与外置 profile；比较优化前后的数据、过滤、排序、校验、关联、保护和保存结果。上轮 165 项定向回归及本次涉及的相关测试按需要执行，不把类型检查和构建当作体验验收。

**建议冻结的量化目标：** 以阶段 0 的中等表、前台热路径为主验收场景，失焦到界面可继续交互 p95 不高于 100 ms；相同历史规模下，从触发单次保存到真实确认的 p95 不高于 1 秒，且相对同环境基线下降至少 50%。连续滚动报告有输入期间的帧间隔 p95、超过 50 ms 的比例和最长卡顿，并以无超过 100 ms 的单次主线程任务作为目标。大表和冷启动单独报告，不偷换为中等表的结果。阶段 0 若显示机器或采样条件无法可靠支撑上述目标，应先向用户说明证据和调整建议，不自行把目标降级为已通过；达不到目标须保留未完成项和下一步瓶颈证据。

## 架构与方案复核结论

经 `feature-architecture` 独立设计核查和 `recheck` 只读复核，当前方案可用于开始基线调查和安全检查点；未发现仍需阻断这些检查点的确定缺口。复核后已补入：现有 handoff 异常跳过、历史投影及二次投影、扫描至替换的竞争窗口、receipt 对当前部署和 live 证据的依赖，以及草稿安全可优先处理的顺序。

本结论不等于具体实现设计或生产性能已验收：实际浏览器各段耗时、模板滚出是否丢稿、跨进程活动索引能否满足完整性合同均未验证。若后续拟采用活动索引，必须先补齐所有生产者、原子边界、锁序、故障恢复与对照反例，再做专项复核和必要的用户决策。
