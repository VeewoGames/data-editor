# 受控事务与项目自动化解耦方案

## 方案概述

### 总体目标和范围

将 `project-transaction` 从 Data Editor 的通用条目自动化核心中移除。Data Editor 只保留可配置、项目无关的自动化入口：条目上下文、目标范围、显式工作范围、可选本机运行前检查、通用结果展示，以及现有通用数据/Markdown 写入能力。

项目自身若需要审批、专属校验、原子业务提交或恢复机制，必须由项目侧的 Skill 或项目侧执行器承担。Data Editor 不再识别 `ownerId`、`capabilityId`、项目事务 journal、事务恢复或项目专属提交结果。

本方案不改变普通 `proposal`、`result-only`、项目资料快照和 Markdown 文档目标的语义；不修改任何项目业务数据；不把 Nocturnel 的业务流程写进 Data Editor。

### 阶段概要与顺序

1. 冻结与迁移：识别现有 `project-transaction` 规则、合同和未完成运行；将规则迁为普通 `project-skill`，其项目业务提交交由项目侧 skill 处理。
2. 核心删除：删除 Data Editor 的事务 result policy、owner adapter、dispatcher、恢复监控、API、配置字段和 UI 分支。
3. 通用收口：将契约、profile、客户端类型、服务路由和测试收敛为 `proposal` / `result-only` 两条通用结果链。
4. 验证与交付：用中性 fixture 验证普通规则、项目资料快照和项目 skill；确认生产代码不含事务专属概念，再按 scoped diff 提交。

### 结构框架

```text
Data Editor 规则
  ├─ proposal: 通用条目变更提案 / 写回
  └─ project-skill: 项目 skill 的 result-only 或 proposal
  ├─ 工作范围：只读快照（默认）或项目目录可写（显式开启）
       └─ 可选：本机运行前检查

项目侧 skill / 执行器
  └─ 项目自己的审批、校验、业务写入、事务与恢复
```

## 一、现状与问题

当前 `project-transaction` 同时存在于规则 profile、动作合同、服务端结果路由、项目 owner 配置、运行 journal/recovery 和 UI 分支中：

- `src/automation-profile.mjs` 将 `ownerId`、`capabilityId` 作为规则执行字段；
- `src/entry-action-contracts.mjs` 定义 `projectTransaction` 合同；
- `server.mjs` 初始化 dispatcher、owner resolver、恢复监控并公开恢复 API；
- `src/entry-action-project-transaction.mjs` 与 `src/entry-action-project-owner-adapters.mjs` 解释项目专属提交协议；
- `src/entry-action-route.mjs` 向项目 skill 注入事务提交能力，`src/project-skill-action-service.mjs` 接收并发布事务结果，`src/entry-action-execution.mjs` 将事务作为有效结果策略；
- `src/App.tsx` 对该类型隐藏项目资料读取配置。

这使 Data Editor 必须理解某个项目的“谁有权提交、如何恢复、如何判断事务成功”，违反编辑器与项目隔离的边界，也造成普通用户无法在规则页面理解其配置差异。

## 二、目标职责边界

### Data Editor 保留

- 管理用户级自动化规则与本机 skill 绑定；
- 将当前条目、可选相邻条目和已声明项目资料快照交给 Codex skill；当规则显式选择项目目录可写时，在真实项目根目录运行同一通用 skill host；
- 支持 `proposal` 与 `result-only` 的通用结果协议；
- 展示、轮询和清理条目级运行状态；
- 继续通过既有通用合同处理允许的 JSON/Markdown 写入。

### Data Editor 删除

- `project-transaction` 结果策略；
- `ownerId`、`capabilityId` 和 `projectTransaction` 配置/合同字段；
- 项目事务 owner adapter、事务 journal、恢复监控和恢复 HTTP API；
- 为事务类型隐藏或强制配置的 UI 分支；
- 任何按项目业务含义解释事务 payload 的逻辑。

### 项目侧承担

- 项目业务规则、审批、合规检查和业务状态迁移；
- 需要时由项目 skill 创建自己的回执、journal 与恢复记录；
- 对项目数据的业务写入与最终验收。

## 三、迁移策略

### 3.1 迁移前冻结

实施前读取当前 automation profile、entry-action contracts 和 `.data-editor/runtime/project-transactions/`：

- 若存在未终态事务运行，先由原项目 owner 明确处理或废弃，Data Editor 不自动删除；
- 列出所有 `project-transaction` 规则及其 `ownerId` / `capabilityId`；
- 生成迁移报告，记录每条规则的新 project skill、目标范围和项目侧处理入口。

这是决定性检查点。无法为某条旧规则确认项目侧替代入口时，该条规则不得被静默转换或删除。

### 3.2 规则迁移

迁移单位不是单条规则，而是“规则 + `contractId` 对应合同 + 项目侧入口”。三者必须在同一保存批次内完成一致性校验：

- profile 中的规则不再含 `ownerId`、`capabilityId`，只使用 `proposal` 或 `result-only`；
- 合同同步改为同一结果策略，并删除 `projectTransaction`；
- 项目侧入口明确该规则所调用的 skill、需要的项目资料、业务写入 owner 和项目侧回执位置；
- 任一部分缺失、策略不匹配或项目侧入口未确认时，整条迁移不保存，旧规则保持停用并写入迁移报告。

完成上述原子检查后，每条旧事务规则改为普通 `project-skill`：

- 结果策略根据项目侧 skill 的输出确定为 `result-only` 或 `proposal`；
- 工作范围默认是“只读快照”；规则显式选择“允许修改项目文件”后，Codex 在真实项目根目录运行，且不再显示项目资料快照选择器，避免将声明资料误解为实际读取边界；
- 项目业务提交不再由 Data Editor 接收 `project-transaction-result`，而是由项目 skill 在自身项目边界中处理；
- 规则配置只保留通用字段，不保留 `ownerId`、`capabilityId`。

迁移必须显式保存新 profile 后才允许删除旧事务字段；不保留双读或长期兼容。

### 3.2.1 工作范围与执行根目录

`project-skill.execution.workspaceMode` 是唯一工作范围字段，且必须为以下二选一：

- `snapshot`：默认值。Data Editor 把已声明的项目资料复制到一次性快照，Codex 在快照目录运行；规则可配置 `advancedExecution.projectInput`，但 skill 不得直接写真实项目文件。需要写入时，只能返回 `proposal`，由既有通用合同完成受控 JSON/Markdown 写回。
- `project-write`：显式开启。Codex 在真实项目根目录运行，项目 skill 可以自行写项目数据、文档、回执与恢复记录；规则不得同时配置或展示 `advancedExecution.projectInput`。项目 skill 以通用 `result-only` 报告结论，Data Editor 读取结果并重载当前条目，不解释项目业务写入。

服务端和 skill host 必须区分两个目录：

- `workspaceRoot`：Codex 的运行目录。`snapshot` 为受控快照目录，`project-write` 为真实项目根目录。
- `outputRoot`：始终由 Data Editor 在独立 scratch 目录创建，用于 prompt、reply、事件与诊断输出；不得要求位于 `workspaceRoot` 内，也不得允许项目 skill 将其替换为任意路径。

因此 `project-write` 不新建第二个执行 host，只扩展现有通用 host 的根目录参数和路径校验：host 只接受服务端创建的 `workspaceRoot` 与 `outputRoot`，分别校验目录真实存在、输出产物位于 `outputRoot`，并禁止任一参数以符号链接或路径穿越逃离服务端指定根目录。

本机预检同样以 `workspaceRoot` 为执行上下文：`snapshot` 对快照运行，`project-write` 对真实项目根目录运行。预检仍属于本机绑定，不进入跨设备共享规则。

项目目录可写模式必须遵守真实项目根目录中的项目规则。实施前需核实当前 Codex CLI 的 `--ignore-rules` 语义；若它会跳过项目指令，则 `project-write` 禁止传递该参数。快照模式是否保留该参数也必须由同一 host 明确决定并覆盖测试，不能依赖隐式默认。

### 3.3 跨文件可恢复迁移协议

`automation-profile.json` 与 `entry-action-contracts.json` 是两份独立文件，不能依赖“连续写两次文件”假装原子迁移。迁移组件必须使用 Data Editor 的通用文件提交能力，并按以下协议执行：

1. **协调器与互斥**：新增仅用于配置迁移的 `automation-migration-coordinator`。它以项目 ID 为粒度持有统一迁移锁；profile 保存、contracts 保存和自动化设置联合保存必须接入同一锁。锁持有期间，其他写入者得到明确的 revision 冲突，不做重试覆盖。journal 的摘要、marker 与恢复基础优先复用 `src/entry-action-policy-migration.mjs` 的通用能力，不复制第二套迁移记录格式。
2. **预检**：读取两份文件的原文、摘要与 revision；验证选中的规则、`contractId`、旧事务声明和项目侧替代入口完全匹配。任一 revision 已变化则不开始。
3. **条件保存接口**：为 contracts 新增与 profile 对称的 load/save 接口，返回 revision，并只在传入的 expected revision 仍匹配时写入。协调器只通过两份文件的条件保存接口写入，禁止直接 `writeFile`。
4. **准备记录**：在 `.data-editor/runtime/automation-migrations/<migrationId>.json` 创建一次性 journal，保存两份文件的 before/after 摘要、revision、迁移条目和阶段枚举 `prepared`、`contract_written`、`profile_written`、`completed`、`recovery_required`；该记录不包含项目业务 payload。
5. **受控写入**：先条件写入合同的非事务版本，再条件写入不含事务字段的 profile。每次成功后更新 journal 阶段；任一条件保存冲突即停止，不进入下一步。
6. **失败处置**：第二步失败时，只有当已写入文件仍等于本次 after 摘要且另一文件仍等于 before 摘要时才回滚；若任一摘要既非 before 也非 after，则绝不覆盖外部修改，journal 标记为 `recovery_required` 并停止该规则执行。
7. **启动恢复矩阵**：服务启动和迁移入口扫描未终态 journal。`contract=before/profile=before` 清理未开始 journal；`contract=after/profile=before` 在锁内继续写 profile；`contract=after/profile=after` 写完成回执；`contract=before/profile=after` 在锁内回滚 profile；任一文件不属于记录的 before/after 摘要，或 revision 无法确认时，都只标为 `recovery_required`，提供只读诊断与人工恢复入口。
8. **完成**：两份文件均达到 after 摘要后写入完成回执；只有此时允许清理旧事务 runtime 目录和进入核心删除阶段。

该组件只服务于本次“旧事务规则退出”迁移，不成为项目业务事务框架；它只保证 Data Editor 自己两份配置文件的一致性。

### 3.4 核心删除顺序

1. 停止新建和执行 `project-transaction`，对旧规则显示明确迁移错误，不尝试运行。
2. 完成已识别规则的项目侧替换和 profile 迁移。
3. 删除事务路由、owner adapter、恢复 API 与相关运行时模块。
4. 删除 profile/contract/client 类型/UI 分支及所有事务测试。
5. 扫描生产源码、默认 fixture、活跃配置与用户可见协议文档，确保不再出现 `project-transaction`、`projectTransaction`、`ownerId` 或 `capabilityId` 的自动化语义。历史方案、迁移报告与删除后的拒绝测试断言不计入零残留范围。

## 四、实施工作包

### 阶段 1：迁移检查与项目侧替代

输入：当前项目 profile、contracts、事务运行目录和项目配置。

动作：实现只读扫描与迁移报告；以“规则 + 合同 + 项目侧入口”为单位建立显式替代映射；确认项目 skill 的输入、输出和业务写入 owner；新增 `automation-migration-coordinator`、contracts 条件保存接口、项目级统一迁移锁、双 revision 预检、迁移 journal、摘要条件回滚和启动恢复矩阵。

完成条件：不存在未分类的旧事务规则、未处理运行或未终态迁移 journal；每条规则均有项目侧替代或被用户确认废弃。

### 阶段 2：通用模型收敛

输入：阶段 1 的迁移回执。

动作：将 `automation-profile`、contracts、API 客户端和界面限制为 `proposal` / `result-only`；为 `project-skill` 增加 `workspaceMode` 单选配置，默认 `snapshot`，显式选择 `project-write` 后允许真实项目目录写入；`snapshot` 才允许配置项目资料快照，`project-write` 隐藏并拒绝该配置；将预检执行根目录和 Codex 项目规则行为切换为所选工作范围；删除事务专属字段与提示。

完成条件：用户只看到一套一致的通用执行配置；项目资料读取仅在只读快照模式下可选，本机预检按规则可选，不因项目类型出现隐藏分支。

### 阶段 3：服务端事务退场

输入：阶段 2 规则模型。

动作：改造现有 `project-skill` host 以显式接收 `workspaceRoot` 与独立 `outputRoot`；`snapshot` 继续在受控快照执行，`project-write` 在真实项目根目录执行并让项目 skill 自行写入。随后从 `server.mjs` 删除旧项目事务的 dispatcher、owner resolver、recovery monitor、启动扫描和恢复 API；保留阶段 1 新增的配置迁移 journal 启动恢复扫描。从 `src/entry-action-route.mjs` 删除事务提交注入；从 `src/project-skill-action-service.mjs` 删除事务结果解析、提交与状态发布；从 `src/entry-action-execution.mjs` 删除事务结果策略；删除事务模块、owner host 脚本与对应运行目录处理。

完成条件：服务端只能接收通用 proposal / result-only 结果；不存在事务 owner 解析或项目专属恢复逻辑。

### 阶段 4：测试与交付

动作：更新中性 fixture；删除事务正向测试；补充 profile/contract 拒绝旧事务字段、旧 skill 输出 `project-transaction-result` 被拒绝、旧事务恢复 API 不存在、路由不会向 `project-skill` 注入事务提交能力、普通 project-skill 快照、可选预检、结果状态和服务路由测试。工作范围测试必须覆盖：默认 `snapshot` 仍使用隔离目录且拒绝逃逸输出；`project-write` 的 Codex `cwd` / `-C` 指向真实项目根目录而诊断输出仍在 scratch；两种模式的预检均使用对应 `workspaceRoot`；保存时拒绝 `project-write` 与 `projectInput` 共存；`project-write` 的通用 `result-only` 会触发当前文档重载；生产代码不含 Nocturnel 业务语义。迁移组件必须覆盖锁竞争、第二文件写入失败、两类条件保存 revision 冲突、进程中断后的每种恢复矩阵状态、摘要漂移时不覆盖外部变更和 journal 完成回执。

完成条件：`npm test`、`npm run typecheck`、`npm run build`、`git diff --check` 通过；独立于 Nocturnel 的 fixture 可完成自动化配置与执行验证。

## 五、风险与保护

- 删除前存在未完成事务：不得直接删 journal 或 owner 配置，必须先由项目侧决定恢复或废弃。
- 项目 skill 尚无业务写入入口：该规则先停用并保留迁移报告，不能伪装为 `result-only` 后丢失写入能力。
- 可写工作范围扩大了 Codex 的文件访问边界：必须默认关闭、以单选明确显示，且不得与“声明项目资料快照”同时生效。
- 项目目录可写若跳过项目规则，会让项目自己的安全与内容约束失效：必须在实现前确认 CLI 参数语义，并在该模式下以可验证方式保留项目规则。
- 输出目录若仍被要求位于项目根目录，会迫使 Data Editor 的诊断文件进入业务仓库；必须保持独立 scratch 输出，并对其路径做服务端控制。
- 迁移影响用户个人 profile：保存前需 ETag/revision 保护，失败时不写入半套 profile/bindings。
- Data Editor 不接管项目业务失败：项目侧执行失败只作为自动化结果呈现，不在编辑器内增加项目错误码分支。

## 六、验收标准

- Data Editor 的规则编辑界面不再出现事务专属提示或字段；
- 所有规则都能以统一方式配置技能、目标、工作范围、可选预检和运行参数；只读快照模式才显示可选项目资料；
- `workspaceMode` 为单选且默认 `snapshot`；`project-write` 不接受项目资料快照配置，预检和 Codex 运行目录均与所选范围一致；
- `project-write` 可由项目 skill 直接写入项目文件，同时通用 `result-only` 仍可完成状态展示和当前条目重载；Data Editor 的 prompt/reply/事件始终写入独立 scratch 输出目录；
- 服务端不再加载 `.data-editor/project-transaction-owners.json`，也不暴露事务恢复 API；
- 生产代码、默认 fixture、活跃配置和用户可见协议文档对 `project-transaction` 为零残留；历史迁移记录与拒绝测试断言除外；
- 中性项目可运行 `project-skill`，且没有任何 Nocturnel/项目业务规则依赖；
- 旧规则迁移报告完整，未处理规则不会被静默删除。

## 七、非范围

- 不在 Data Editor 中实现新的通用“项目事务框架”；
- 不修改 Nocturnel 或其他项目的业务数据、业务 skill 或业务检查；
- 不承诺跨工具同时保存或跨进程业务事务；
- 不保留旧事务模型的兼容读取、兼容 API 或隐藏 fallback。
