# 条目自动化并发错写修复执行计划

## 方案概述

### 1. 总体目标和范围

本执行计划把《条目自动化并发错写与超时诊断修复方案》拆成可逐批实施、验证、暂停和交接的任务。

上位方案：

- [条目自动化并发错写与超时诊断修复方案](./2026-07-26-条目自动化并发错写与超时诊断修复方案.md)

总体目标是：

1. 立即冻结现有 Codex 直接写正式数据文件的危险入口。
2. 建立 Data Editor 服务端唯一运行与提交所有权。
3. 通过 canonical physical file identity、fencing、strict rowId、配置版本和 document commit mutex 阻止并发覆盖与错目标写入。
4. 通过隔离 proposal、commit journal、Windows Job Object 和 recovery state machine 形成可恢复执行链。
5. 在真实 Codex CLI、API、Browser 和正式服务验证全部通过后，按 project/action 逐项重新启用。

本计划的实施范围是 `C:\Code\data-editor`。Nocturnel 的 writeback policy、automation profile、skill 迁移和事故数据修复属于独立 owner handoff；未经独立授权不得修改。

本计划文档的确认不等于实施授权、Git 提交授权或 push 授权。

### 2. 各阶段任务概要

1. **D0 决策与授权门**：确认八项架构决策、工具层范围和实施授权。
2. **A 全局硬隔离**：正式服务默认拒绝所有 entry-action 运行。
3. **B 所有权基础**：先复用审计，再分三个串行 checkpoint 建立 canonical file identity、原子 primitives、job supervisor、Windows Job Object、持久 fencing lock 和 recovery。
4. **C Authority 引擎与严格定位**：以 Data Editor 自有 fixture 建立 policy schema/loader、profile ETag、authority digest、validator runtime 和 strict rowId；不在工具层代替项目 owner 定义实际可写字段。
5. **D 隔离 Proposal**：切断 Codex 对正式源文件的写权限，以真实 CLI scratch E2E 验证 proposal。
6. **E 统一提交与 Journal**：接入 document commit mutex、validator、commit journal 和崩溃恢复。
7. **F 状态、诊断与清理**：收口 phase/outcome、file-scope 查询、diagnostics 和 `service:finalize`。
8. **G 协议切换与按 Action 重新启用**：先原子切换到 proposal-only，再用工具自有 fixture 完成集成验收；真实项目 action 只能在对应 H1 owner handoff 后启用。
9. **H Nocturnel Owner Handoff 与数据审计**：H1 负责真实 policy/profile/skill 迁移并前置于 Nocturnel action 启用；H2/H3 是独立的数据审计与修复分支。

工具层主链为 `D0 -> A -> B1+B2 -> B3 -> B4+B5 -> C -> D -> E -> F -> G0 -> G1`。

真实项目迁移分支为 `F -> H1（独立 owner 授权）`，H1 可与 G1 并行准备；真实 action 的启用必须在 `G0 + G1 + H1 -> G2（对应 action）` 的 join 门后发生。

事故数据分支 `H2 -> H3` 不阻塞工具层 fixture 验收，也不因工具层完成而自动获得授权。

### 3. 整体结构框架

```text
D0 决策与实施授权
  -> A 全局 hard-disable
  -> B1+B2 identity + atomic primitives
  -> B3 supervisor + Windows Job Object
  -> B4+B5 durable fencing + recovery
  -> C policy engine + profile ETag + strict rowId（tool-owned fixture）
  -> D isolated proposal + real Codex CLI scratch E2E
  -> E unified commit mutex + validators + all-write journal
  -> F phase/outcome + diagnostics + active-run + finalize
  -> G0 legacy-disabled -> proposal-only atomic cutover
  -> G1 tool-owned fixture acceptance

F -> H1 Nocturnel policy/profile/skill owner handoff（独立授权）

G0 + G1 + H1
  -> G2 对应 Nocturnel action eligibility + acceptance

H2 事故数据审计 -> H3 逐项数据修复（分别授权）
```

任何批次失败时：

- entry-action 保持禁用；
- 不恢复旧 direct-write runner；
- 不通过延长超时、降低 sandbox 或跳过验证绕过门禁；
- 回到当前批次的设计或依赖决策，不擅自扩大范围。

### 4. 计划命令与未来交付物说明

本文列出的命令是对应批次完成时必须可运行的正式验收入口。除仓库当前已经存在的脚本或测试外，新点名的 npm script、测试文件、fixture 和 helper 都是对应批次必须新增的交付物：

- 实施者必须先把该批次声明的脚本和测试加入仓库，再执行命令；
- 文件、npm script、fixture 或 helper 缺失即该批次未完成；
- 不得把“命令当前不存在”记为 skip、通过或环境不适用；
- Windows-only、真实 CLI 和正式 Browser 门只能按各自明确的“通过”或“未验证/失败”合同报告。

## 一、执行前决策与授权门

### D0.1 必须确认的八项决策

| 决策 | 推荐基线 |
| --- | --- |
| 是否立即禁用写回型 entry-action | 是；服务端全局 fail closed |
| 并发请求拒绝还是排队 | 首版拒绝并返回当前 runId |
| 新协议覆盖范围 | 删除通用旧直写协议；按 project/action 逐项重新启用 |
| Nocturnel 数据修复是否同批 | 否；独立计划与授权 |
| Runner 所有权 | 服务进程内 job supervisor |
| 最大写回 authority | project-scoped entry-action writeback policy |
| 旧 writable-workspace ADR | 由隔离 proposal 协议显式 supersede |
| Windows 进程树 ownership | `CREATE_SUSPENDED -> Assign Job Object -> Resume`，`KILL_ON_JOB_CLOSE`，失败即拒绝 |

- 是否允许引入受控 Windows Job Object helper 或依赖；

- 需要避开的共享服务、临时端口和正在运行的其他任务。

未明确授权的内容：

- 不修改 Nocturnel；
- 不提交 Git；
- 不 push；
- 不启用任何正式 entry-action；
- 不清理历史 runtime 证据。

### D0.3 完成条件

- 八项决策有明确结果。
- 工具层实施授权与 Git 授权分开记录。
- 若任一决定偏离推荐方案，先更新修复方案和本执行计划，再重新复核受影响部分。

## 二、批次 A：全局硬隔离

### 输入

- D0 已完成。
- 正式服务仍使用旧 direct-write runner。

### 改动范围

预计涉及：

- `server.mjs`
- entry-action API 类型与错误展示
- `tests/open-stop.test.mjs`
- API client 相关测试

### 主要任务

1. 在 server construction 中加入不可由用户配置误开的 entry-action execution policy。
2. 正式默认值为 `disabled`。
3. `POST /api/entry-actions/run` 返回 `ENTRY_ACTION_PROTOCOL_DISABLED`。
4. 只读 result/latest/output 接口保持可用。
5. 测试只能通过显式 constructor dependency injection 启用旧入口夹具；不得使用环境变量或本机 profile 开启。
6. 当前 `server.mjs` 的服务创建与监听为顶层流程；实施时先提取可测试的 server factory/route wiring，再注入测试 policy，确保 production startup 无注入入口。

### 验收

- 正式服务、直接 API、多标签页和多客户端调用都被一致拒绝。
- result/latest/output 仍能读取历史记录。
- 自动化 profile 与 binding 的保存不等于允许执行。
- 定向命令：`node --test tests/open-stop.test.mjs tests/entry-action-api-disabled.test.mjs`，预期退出码 `0`。
- 类型命令：`npm run typecheck`，预期退出码 `0`。
- 构建命令：`npm run build`，预期退出码 `0`。

### 停止条件

- 若无法保证正式默认值始终禁用，停止后续批次。
- 不得以“前端隐藏按钮”代替服务端 hard-disable。

### 交付与回滚

- 该批次是唯一需要尽早落地的安全门。
- 回滚不是恢复旧运行能力；若后续失败，保持本批次生效。

## 三、批次 B：所有权、文件身份与恢复基础

### 输入

- 批次 A 已完成，正式运行入口保持禁用。

### B0 复用审计与 checkpoint 约束

开始新增基础设施前，定向审计并记录：

- `src/runtime-state.mjs` 与 `src/project-registry.mjs` 的 temp + rename 原子写入模式；
- `src/persistent-process.mjs`、`stop.mjs`、`scripts/service-finalize.mjs` 已有 PID、command-line、停止与清理证据链；
- 哪些 primitive 可抽取或升级为共享实现，哪些只能保留为调用方封装；
- Windows Job Object adapter 是唯一允许新增的系统级 ownership 能力。

批次 B 拆成三个必须串行、可独立回滚的 checkpoint：

1. **B-CP1 = B1+B2**：文件身份与共享原子 primitive。
2. **B-CP2 = B3**：Job supervisor 与 Windows ownership。
3. **B-CP3 = B4+B5**：持久 fencing 与 recovery。

进入 B-CP2 前，必须单独确认 Job Object helper/依赖、构建方式、签名要求、x64 分发与卸载策略；未确认不得选型或引入依赖。

### B1 Canonical physical file identity

主要任务：

1. 新建唯一 `canonicalFileIdentity(projectContext, sourcePath)`。
2. 通过 allowlist 和 `resolveDataFilePath(...)` 解析目标。
3. 使用 `realpath`、绝对路径、Windows case-fold、统一分隔符生成 `canonicalFileKey`。
4. handoff 同时保存虚拟 `sourcePath` 与 `canonicalFileKey`。

验收：

- 不同 source id、父子重叠 data source、大小写、斜杠、`.` 和 junction alias 收敛为同一键。
- 非 allowlist 文件和越界路径被拒绝。

### B2 原子文件 Primitives

主要任务：

1. 实现 `exclusiveCreateLock`。
2. 实现 `atomicWrite`。
3. 实现 `atomicReplace`。
4. 定义唯一 temp 命名、排他创建、flush/close、失败保留与清理策略。

验收：

- 排他锁获取不存在 check-then-write 竞态。
- Windows replace 失败时原文件字节不变。
- 运行状态不会被读取为部分 JSON。
- 三种 primitive 不互相替代。
- B-CP1 命令：`node --test tests/canonical-file-identity.test.mjs tests/atomic-file.test.mjs`，预期退出码 `0`。
- 失败注入覆盖 temp 名碰撞、flush/close 失败、磁盘满、replace `EPERM`；失败时原文件字节不变，临时产物有可诊断处置。

### B3 Job supervisor 与 Windows ownership

主要任务：

1. 新建服务进程内 job supervisor。
2. 使用受控 ownership adapter：
   - `CREATE_SUSPENDED`
   - 创建 Job Object
   - 分配 child
   - 确认 Job handle 不可继承
   - 恢复主线程
3. 设置 `KILL_ON_JOB_CLOSE`。
4. 任一步失败时安全终止并返回 `ENTRY_ACTION_PROCESS_OWNERSHIP_UNAVAILABLE`。

验收：

- child 在任何用户代码运行前已归属 Job。
- child 启动即派生 descendant 的压力测试中，关闭 Job handle 后全部退出。
- 正常结束、超时、shutdown 和服务崩溃都不会留下受控进程树。
- 失败注入覆盖 suspended child 创建后但 assign 前、assign 后但 resume 前、resume 失败和 Job handle 意外关闭。
- B-CP2 构建命令：`npm run build:job-helper`；Windows 定向命令：`node --test tests/job-supervisor-windows.test.mjs`，预期退出码均为 `0`。
- 非 Windows 环境只能报告该门“未验证”，不得以 skip 代替 Windows 门禁通过。

### B4 Fencing lock 与原子运行状态

主要任务：

1. action admission lock 使用 `canonicalFileKey`。
2. 每个 `canonicalFileKey` 拥有独立的持久 generation record；使用专用 allocator 排他锁和 atomic compare-and-increment 分配 fencingToken。
3. generation record 必须跨服务重启严格单调；记录损坏、丢失或无法判定时 fail closed，并进入 recovery，不得从 `0` 猜测重建。
4. generation 使用每 token 一个不可变 ledger record、hash chain 与独立 tail-completeness anchor；仅 head、ledger 和 anchor 全部验证通过时才可重建 head。任何缺失、损坏、未知 schema 或尾部不一致均 fail closed；首版不得 GC。
5. admission lock 只能在 generation 持久发布成功后创建，锁记录 runId、ownerToken、fencingToken、heartbeat、`jobInstanceId` 和 phase。`jobInstanceId` 由服务端每次 supervisor launch 独立生成 UUID，不复用 runId 或 command id。
6. Job ownership protocol 升级为 v2：helper 与 child 身份均为 PID 加 unsigned FILETIME decimal string；v1、字段缺失、格式非法、OS 查询失败或任一身份不匹配均为 `insufficient`。command/executable digest 只用于审计。
7. 初始锁必须有 `launching/evidence_pending` phase。helper owned ack 之前尚无 child 身份证据；此窗口崩溃只能保持锁并进入 `insufficient`，不得按 absent 释放。
8. Node 必须先校验 v2 ready 与 owned 回显（含 helper/child 双身份和每次 launch 的 `jobInstanceId`），再以 `atomicWrite -> flush -> close` 持久化完整证据并推进到 `owned/evidence_persisted` phase；写入或推进失败保持 `insufficient`，不得把 transient JSONL 当作 recovery evidence。
9. heartbeat、phase 更新、commit 前置探针和 release 都验证 ownership 三元组；claim 成功后旧 owner 在每次上述写入前都必须重新 probe 固定锁。
10. 实现 compare-and-release；不得以 atomic replace 覆盖 admission lock。

验收：

- 同一物理文件只能获得一个 admission lock。
- 旧 generation 不能 heartbeat、更新状态、提交或释放新锁。
- 不同物理文件可以并行。
- generation 分配前/后崩溃、generation 已递增但 lock 未建立、lock 建立但 handoff/state 未发布均有确定恢复结果。
- 覆盖 ledger durable / anchor old、ledger absent / anchor new、partial ledger record、anchor 损坏或指向无效 chain；除可证明的旧 anchor 后存在完整未锚定 record 外，全部 fail closed。
- 对该唯一完整未锚定 record，allocator coordinator 必须验证连续 token、filename/payload token、schema、payload hash、prev hash 与旧 anchor predecessor；验证成功时先重新发布 tail anchor、再发布 head。任一步失败保持非终态并 fail closed，不得静默跳过。

### B5 Recovery state machine

主要任务：

1. 实现只读 inspect API。
2. 实现本机 recovery CLI。
3. recovery 首个变更必须是 `fixed lock -> UUID claim-dir/lock`；只可读取 claimed record 判定，不能先读 fixed lock 再 claim。claim target 必须是预先不存在的独占目录中的路径。
4. claim 后若证据为 active 或 insufficient，只能在固定路径仍空时以 `wx` 回迁，或写 `superseded-after-claim`；绝不删除或覆盖新的 fixed lock。admission 在创建自身 fixed lock 后必须检查未终态 claim/recovery record，存在时 compare-and-release 自己的锁并返回 `recovery_required`。
5. inspect 首先扫描同 canonicalFileKey/runId 的非终态 claim；存在时输出 `insufficient` 且 reasonCode=`RECOVERY_CLAIM_IN_PROGRESS`，保留 quarantine。只有不存在该 claim 时，fixed target 缺失且无精确 completed record 才是 `RECOVERY_TARGET_ABSENT_UNPROVEN`。
6. release 需要 helper 与 child 的 PID+FILETIME、完整 fencing ownership 和 `jobInstanceId` 证据。
7. completed recovery record 仅能在 claim-first compare-and-release 已确认完成后写入；匹配键必须包含 canonicalFileKey、runId、ownerToken、fencingToken、lock schema/version 与 disposition。
8. inspect 在精确 completed recovery record 验证通过且 fixed target 缺失时返回 `decision=completed`、`outcome=already_recovered`、`released=true`、exit 0；它不是 `releasable` 或 `insufficient`。

正式 CLI 与退出合同：

1. `npm run entry-action:recover -- inspect --project <projectRoot> --run-id <runId>`
   - 退出码 `0`：输出 JSON decision，值为 `active`、`releasable`、完整可解析但证据不足的 `insufficient`，或精确 completed record 支持的 `completed`；除 `completed` 外必须同时输出 reasonCode 与 released=false；
   - 退出码 `2`：参数、I/O、JSON、未知 schema、无证明 target 缺失或证据读取错误。
2. `npm run entry-action:recover -- recover --project <projectRoot> --run-id <runId>`
   - 退出码 `0`：已依据完整证据释放，或相同 recovery record 已幂等完成；
   - 退出码 `3`：证据为 `active` 或 `insufficient`，保持锁且未释放；
   - 退出码 `2`：参数、I/O、JSON、未知 schema、无证明 target 缺失或证据读取错误。

CLI 只接收 project/runId 定位参数，ownerToken、fencingToken、jobInstanceId、helper/child PID+FILETIME 和 owner marker 必须从持久证据中读取并相互验证；不得通过命令行参数伪造 ownership。调用方必须读取 JSON 的 command、decision、outcome、released 和 reasonCode，不能仅按退出码清理状态。

验收：

- PID reuse、错误 owner、重复 release、多次重启和证据不足均不会错误释放。
- 覆盖 claim 进行中固定 target 缺失、claim 后新 admission、claim 后崩溃、completed record 匹配/不匹配、ledger/anchor 四类崩溃排列，以及 `launching/evidence_pending` 崩溃。
- 不提供无证据强制解锁按钮。
- B-CP3 命令：`node --test tests/fencing-lock.test.mjs tests/entry-action-recovery.test.mjs`，预期退出码 `0`。

### 批次 B 总门禁

- B-CP1、B-CP2、B-CP3 依次通过后才能进入 C；每个 checkpoint 分别记录改动清单、验证产物和回滚边界。
- 不允许先为 detached runner 实现临时 ownership，再在后续替换。
- 正式 entry-action 仍保持禁用。

## 四、批次 C：Authority、Profile 版本与 Strict RowId

### 输入

- 批次 B 的 canonical identity、原子状态和 supervisor 已稳定。

### C1 Project-scoped writeback policy

主要任务：

1. 新建 entry-action writeback policy schema 与加载器。
2. policy schema 支持最大 target、writable fields、类型、空值、唯一性范围和 validator reference。
3. policy 内容生成 authority digest。
4. 通用 `writeback-adapter` 只执行已授权 patch，不承载权限。
5. 使用 Data Editor 自有 fixture policy/profile 验证引擎；Nocturnel traits、skills、runes 的真实字段清单和规则保留在 H1。

验收：

- 缺 policy 时 fail closed。
- profile 和本机 binding 不能扩大 policy。
- policy schema 错误不会降级为放行。

### C2 Automation profile cutover

主要任务：

1. target 增加 `writableFields`。
2. profile 加载/保存返回并校验内容 ETag。
3. 扩展 Automation Settings 的类型、编辑与验证。
4. 旧 profile 缺少 `writableFields` 时 action 不具备启用资格。

验收：

- normalize 不再丢弃 `writableFields`。
- profile ETag 陈旧时拒绝覆盖。
- 空白、越权和非法字段列表均 fail closed。

### C3 Strict rowId resolver

主要任务：

1. 直接扫描目标 collection。
2. 验证 rowId 是合法持久 `__entry_id`。
3. 精确匹配 0 次返回 `ENTRY_ACTION_TARGET_MISSING`。
4. 精确匹配多次返回 `ENTRY_ACTION_TARGET_ID_DUPLICATE`。
5. 禁止回退 `sourceRowIndex`。

验收：

- 缺失、非法、重复和不存在的 rowId 均为零写入。
- `sourceRowIndex` 只用于显示和诊断。

### C4 Authority 版本门禁

主要任务：

1. handoff 记录 authorityDigest 和 automationProfileEtag。
2. commit 时重读当前 policy/profile。
3. 实际权限取“启动 profile ∩ 当前 profile ∩ 当前 policy”。
4. action 禁用、target 删除或权限收窄时返回 `ENTRY_ACTION_AUTHORITY_STALE`。

### 批次 C 总门禁

- fixture policy 中每个可写字段都有 validator authority，schema/loader/digest/runtime 合同成立；这不等于任何真实项目 policy 已完成。
- 命令：`node --test tests/entry-action-policy.test.mjs tests/automation-profile.test.mjs tests/strict-row-id.test.mjs`，预期退出码 `0`。
- 正式 entry-action 仍保持禁用。

## 五、批次 D：隔离 Proposal 与真实 Codex CLI

### 输入

- B 的 supervisor/ownership 可用。
- C 的 policy、profile 和 strict rowId 合同稳定。

### D1 Handoff 与 proposal schema

proposal 至少包含：

- runId、actionId；
- 虚拟 sourcePath、canonicalFileKey、collectionPath、rowId；
- baseDocumentEtag；
- automationProfileEtag、authorityDigest；
- fencingToken；
- `beforeExists/before/afterExists/after`；
- summary。

拒绝：

- 第二目标；
- 重复字段；
- 整文档内容；
- 任意命令或路径；
- 未授权 add/remove；
- 缺失/null 语义不明确的 change。

### D2 隔离执行

主要任务：

1. 使用隔离 scratch，而非正式项目可写工作区。
2. 移除 `--dangerously-bypass-approvals-and-sandbox` 的正式数据写权限。
3. supervisor 捕获 stdout/stderr 和最终结构化输出。
4. proposal 先写 `.tmp`，仅 Codex exit 0 且 schema 合法后原子发布。
5. timeout 或非零退出的 proposal 永不提交。

### D3 真实 Codex CLI scratch E2E

新增唯一正式入口：`npm run test:entry-action-cli-e2e`，对应 `tests/entry-action-cli-e2e.test.mjs`。测试必须固定使用仓库内 fixture project、fixture policy/profile 和 proposal-only fixture skill，不读取 Nocturnel 或个人 profile。

preflight 必须记录：

- `codex --version`、CLI 路径和测试 runId；
- 认证是否可用、所用 CLI 参数版本是否受支持；
- fixture、handoff 和 proposal schema 版本；
- 开始时间、观察窗口和产物目录。

专项测试固定调用以下 arg vector，不从环境变量拼接额外权限参数：

- success：`codex exec --json --skip-git-repo-check -C <scratch> -`，stdin 为仓库内 versioned success fixture prompt；
- timeout：`codex exec --json --skip-git-repo-check -C <scratch> -`，stdin 为仓库内 versioned timeout fixture prompt，由 supervisor 使用固定测试超时终止。

preflight、success、timeout readiness、timeout cutoff、终止后的额外观察窗口和整个 script 都必须有固定最大时限，并写入 fixture 配置和结果。首版基线为：

- preflight：`30_000 ms`；
- success run：`600_000 ms`；
- timeout readiness：`60_000 ms`，必须观察到 CLI `running` 或首个结构化事件；
- timeout cutoff：readiness 成立后 `1_000 ms`；
- 终止后观察窗口：`10_000 ms`；
- 整个专项 script：`720_000 ms`。

任一时限超出均非零退出并报告失败或“门禁未验证”。若真实环境证明阈值不稳定，修改阈值属于测试基线变更，需更新计划记录，不能在单次运行中动态放宽。

成功用例：

- 临时项目；
- 只读正式源；
- 真实 skill 路径；
- 真实 `codex exec`；
- proposal 原子发布；
- 正式源文件零变化。
- 记录 CLI command、exit code、proposal digest 和正式源 before/after digest。

超时用例：

- 真实 CLI 触发 timeout；
- proposal 不提交；
- Job 进程树必须确认全部退出；
- outcome 为 `timed_out`，admission lock 已按 ownership compare-and-release；
- 额外观察窗口内无晚写回。
- 固定超时注入方式和观察窗口；记录 Job/recovery 证据与清理结果。

正式 timeout E2E 只有同时满足 `tree confirmed exited + timed_out + lock released + no late write` 才能退出码 `0`。`failed_needs_recovery` 只能由独立失败注入用例验证 fail-safe；真实 CLI E2E 一旦进入该状态必须非零退出并阻止 G1/G2，不得作为 eligibility 的合格结果。

网络、认证或 CLI 版本条件不可用时，专项脚本必须非零退出并把门禁标为“未验证”；不得 skip 或记为通过。测试产物写入本次 runId 的隔离目录，成功后按 owner marker 清理，失败时保留诊断并报告路径。

批次 D 命令：

1. `node --test tests/entry-action-proposal.test.mjs`，预期退出码 `0`。
2. `npm run test:entry-action-cli-e2e`，预期退出码 `0`；无法满足真实 CLI preflight 时门禁保持未验证。

### 停止条件

- 若当前 CLI 无法在可证明的隔离边界中运行，停止并回到架构决策。
- 不得通过恢复正式工作区写权限通过 E2E。

## 六、批次 E：统一提交与 Commit Journal

### 输入

- D 只能生成不可直接写正式数据的 proposal。

### E1 Document commit coordinator

主要任务：

1. 按 canonicalFileKey 建立短生命周期 mutex。
2. `/api/save`、proposal commit 和所有正式 `writeTextFile(...)` 调用点统一接入。
3. 在同一临界区内重读、校验并原子替换。
4. 正式保存要求 documentEtag，不允许省略。
5. 等待 mutex 期间或获得 mutex 后若 policy/profile 发生变化，必须在替换前重读并拒绝陈旧 authority。

### E2 Proposal commit

校验顺序：

1. fencing ownership；
2. handoff/proposal identity；
3. 当前 policy/profile 与权限交集；
4. document ETag；
5. strict unique rowId；
6. beforeExists/beforeValue；
7. 类型、唯一性和业务 validator；
8. 通过 `writeback-adapter` 应用 patch。

任一失败均为正式文件零变化。

### E3 Commit journal

journal 覆盖 document commit coordinator 的**全部正式写入**，包括 `/api/save`、proposal commit 和迁入 coordinator 的其他正式保存；不得只覆盖 proposal。

阶段：

```text
commit_intent
  -> source_replaced
  -> verified
  -> result_published
```

journal 保存：

- 公共字段：idempotencyKey、saveType（`document_save` 或 `proposal_commit`）、canonicalFileKey；
- base/new ETag；
- before/after digest；
- 当前 stage 与时间。

按 saveType 使用判别式记录：

- `proposal_commit`：idempotencyKey 固定由 `runId + proposalDigest` 派生；必须保存 runId、ownerToken、fencingToken、rowId、proposal digest 和字段级 before/after。
- `document_save`：不伪造 entry-action ownership 三元组；客户端为每次逻辑保存生成稳定 UUID idempotencyKey，并在网络重试时复用同一 key。服务端将 key、request payload digest 和唯一保存 outcome 一起持久化并回传；相同 key 携带不同 payload 必须拒绝。

每次阶段推进都必须执行 `atomicWrite -> flush -> close` 并确认成功后，才能开始下一项不可逆操作：

1. durable `commit_intent`；
2. atomic source replace；
3. durable `source_replaced`；
4. reread verification；
5. durable `verified`；
6. 幂等 result publish。

journal 写入、flush 或 close 失败时不得继续 source replace；source replace 后 journal 推进失败则保持可恢复证据并进入恢复流程。

恢复门：

- `commit_intent + baseEtag`：未提交；
- `commit_intent + newEtag`：按 saveType 验证 after digest；`proposal_commit` 还必须验证 proposal digest 与 strict rowId after 值，匹配则继续，否则 recovery；
- `source_replaced + newEtag`：继续 verified；
- `verified`：`proposal_commit` 补发唯一 result，`document_save` 补发相同 idempotencyKey 的唯一保存 outcome；
- 无法证明时进入 `failed_needs_recovery`。

### E4 崩溃注入与竞态验收

必须覆盖：

- `/api/save` 与 proposal commit 使用同一旧 ETag；
- replace 成功、journal 尚未推进；
- source_replaced 后、verified 前；
- verified 后、result 发布前；
- result 发布后重复恢复；
- fencing generation 已变化。
- journal 写入/flush/close 失败与磁盘满；
- policy/profile 在等待 commit mutex 期间发生变化。
- `document_save` 请求丢失响应后以相同 idempotencyKey 重试，以及相同 key 携带不同 payload。

### 批次 E 总门禁

- 每个已发生的正式写入都能恢复出唯一可信终态。
- 不存在 silent overwrite、重复提交或错误 target write。
- 命令：`node --test tests/document-commit-coordinator.test.mjs tests/commit-journal.test.mjs`，预期退出码 `0`。

## 七、批次 F：状态、诊断、查询与安全清理

### F1 Phase / Outcome

活动 phase：

- `queued`
- `running`
- `proposal_ready`
- `committing`

终态 outcome：

- `completed_with_writeback`
- `completed_without_changes`
- `conflicted`
- `rejected`
- `failed`
- `timed_out`
- `failed_needs_recovery`

前端仅通过 `isTerminalEntryActionState(...)` 判断完成。页面停止观察使用 `observation_timed_out`。

### F2 输出和诊断

- result 分别记录 proposal/reply/diagnostics 的 path 与 available。
- 用户消息只依据 available 声称产物存在。
- diagnostics 限长、脱敏、本机保存。
- timeout 分支：
  - tree confirmed exited -> `timed_out` + release；
  - tree unconfirmed -> `failed_needs_recovery` + keep lock。

### F3 File-scope active-run

- API 接收虚拟 sourcePath。
- 服务端通过统一 canonical resolver 查询。
- 行级 latest 保留历史反馈。
- 文件级 active-run 提供跨 row、跨页面 busy 状态。

### F4 `service:finalize`

隔离目录固定为：

```text
%TEMP%/data-editor-entry-action-<runId>
```

目录包含 owner marker。只有同时满足以下条件才删除：

- marker 合法并匹配 runId；
- 无 matching process；
- 无 active lock；
- 存在可接受终态或 recovery record；
- 路径位于固定 temp 根。

证据不足、仍在使用、错误 marker 或非本工具目录一律拒删。
失败注入还需覆盖 owner marker 为 symlink/junction、marker/runId 不匹配以及路径逃逸。

批次 F 命令：`node --test tests/entry-action-state.test.mjs tests/service-finalize.test.mjs`，预期退出码 `0`。

1. 协议集成测试：`node --test tests/entry-action-protocol-cutover.test.mjs tests/entry-action-fixture-integration.test.mjs`，预期退出码 `0`。

4. TypeScript 诊断复核：`npm run typecheck`，预期退出码 `0`；这是重复确认，不代表新增覆盖。
5. production build：`npm run build`，预期退出码 `0`。
6. 双客户端与跨写入者 API 竞态由 fixture integration test 覆盖。

   - busy
   - conflicted
   - completed_without_changes
   - rejected
   - failed
   - timed_out
   - failed_needs_recovery（使用隔离的 seeded recovery fixture）；若通过真实 supervisor 注入，必须先执行 recovery CLI、写入 recovery record 并释放锁

## 十一、失败停止条件

遇到以下任一情况，停止当前批次并回到设计或用户决策：

1. canonical identity 无法消除同一物理文件别名。
2. Windows Job Object 无法在 child 运行前建立归属。
3. fencing generation 无法持久且原子验证。
4. atomicReplace 不能保证失败时原文件完整。
5. profile/policy 版本无法在 commit 时重新验证。
6. strict rowId 无法识别重复持久 ID。
7. 真实 Codex CLI 无法在隔离 scratch 中完成 proposal。
8. commit journal 无法恢复 crash-after-replace。
9. `service:finalize` 无法证明目标目录属于本工具且已陈旧。
10. 需要修改 Nocturnel 才能继续，但尚未取得 owner 授权。
11. 真实 CLI 的认证、网络或版本 preflight 未通过。
12. journal 任一阶段无法 durable flush/close。

停止不等于回退旧机制。正式 entry-action 继续保持禁用。

## 十二、整体完成定义

执行计划完成必须同时满足：

1. 工具层 A 至 G1 全部批次通过各自门禁；真实项目 action 另需对应 H1 与 G2。
2. 旧 direct-write 运行路径已删除，不存在兼容 fallback。
3. 两层锁统一使用 canonical physical file identity。
4. supervisor、Job Object、fencing 和 recovery 可证明没有晚写回。
5. policy/profile/strict rowId/validator 形成正式 authority。
6. Codex 只能生成隔离 proposal。
7. 所有正式写入共享 document commit coordinator。
8. 全部正式写入共享 save-type aware commit journal，并能恢复全部已定义崩溃窗口。
9. phase/outcome、诊断、file-scope 查询和 finalize 契约成立。
10. 真实 CLI、API、构建和 Browser 验收通过。
11. 工具自有 fixture action 通过 G1；只有同时通过 G0、G1、对应 owner handoff 和 action eligibility 的真实 project/action 才能通过 G2 重新启用。
12. 正式文档、Truth 和 ADR 与运行时一致。
13. Nocturnel 未授权内容保持未修改。
14. Git commit/push 仅在独立授权后执行。
