# 方案概述：条目自动化可见生命周期与稳定提案合同修复

## 目标、范围与结构

本方案修复通用 `project-skill` 条目自动化的三项失效：请求在准备完成前无法返回、准备阶段无可见时间与可终止终态、proposal 型 skill 缺少稳定且完整的提交合同。Nocturnel 的“补全名称”仅为验收样本；Data Editor 不承载名称补全等项目业务。

方案按“准入 receipt → 受监督准备 → 稳定 skill/proposal → 恢复与验收”推进。现有 authority、fencing、ETag、journal 与 commit coordinator 保持唯一写回权。

## 已确认事实

- `fill-data-name` 的 snapshot 未声明 `projectInput`，导致复制整仓；真实运行在 `queued` 停留约 370 秒后才进入 `running`。
- route 等待 project-skill 准备完成才返回，前端初始状态无 `startedAt`，因此准备期间不能计时。
- 当前运行 diagnostics 记录了失效 skill 路径，且最终 reply 不是合法 proposal。

证据见 `docs/feature-architecture/2026-08-26-1222-条目自动化可见生命周期与稳定提案合同.md`。

## 推荐设计

1. 准入成功后持久化同一 `runId` 的 `queued` 状态并立即返回 receipt；UI 从 `acceptedAt` 显示总耗时，所有 phase 只读投影服务端状态。
2. snapshot 模式取消“未声明输入则整仓复制”；`projectInput` 只包含额外项目资料，空输入创建空隔离工作区。
3. 输入准备放入 `JobSupervisor` 所有的可终止 worker，统一 `queued → preparing_input → preflight_running? → running → proposal_ready → committing → terminal`；准备超时/失败必须发布 terminal 后再清理。
4. 准入时冻结 `SkillArtifact`（解析路径、内容摘要、私有 staged 包），proposal 型 project-skill 复用完整 authority handoff 并在同一 run 内提交，禁止 fresh child run。

## 实施前冻结合同

- `acceptedAt` 不新建第二只时钟：定义为既有 `startedAt` 的 receipt 语义别名；旧状态读取回退 `startedAt → createdAt`，排序只使用该单一时间轴。
- `ProjectInput` 仅代表额外项目读取；当前目标 row/file、authority 与 skill 包由平台独立提供。删除“目标必须属于 paths”的旧 gate 与 UI 自动塞入 targets 的规则。
- receipt idempotency 以项目、动作、目标身份、请求摘要和 `idempotencyKey` 建 durable record；同 key 并发/网络重试只回放同一 receipt 或 terminal。
- 同 run 写回增加 `commitAdmittedProposal({ runDefinition, lease, result })`；既有 `submitFreshEntryActionProposal` 保留给非 project-skill 旧入口，`candidate-create` 继续独立 owner。
- prepare worker 在启动前持久化 worker intent，启动后持久化 process ownership；重启时不能证明进程已死即 fail-closed，不能发布成功或清理 scratch。
- `SkillArtifact` 闭包限定为 skill root 下常规文件；拒绝 link/junction、路径逃逸和未声明外部资源，设文件数/总大小上限，digest 覆盖所有 staged 文件，host 仅可读 staged root。

## 边界与风险

- 不扩大 `project-write` 权限，不为旧路径提供静默回退。
- 准备超时不能用外层 `Promise.race` 伪造；必须可证明终止 worker。
- Nocturnel 的最小输入由技能实际引用闭包决定，不能仅凭三个目标 JSON 猜测。
- 当前工件只能证明运行期读取过失效用户级 skill 路径，不能证明 catalog/cache 的具体漂移原因；修复以 staged artifact 消除路径依赖，不针对未证实的解析顺序做猜测性改动。
- 文档 `docs/09_Codex自动化机制.md` 与当前运行链有旧描述，需在实现完成时同步更新。

## 验收

- `/run` 在准备仍进行时立即返回 queued receipt；页面立即显示总时长和“准备资料”。
- 空 `projectInput` 不复制仓库 sentinel；显式输入、路径逃逸与链接拒绝均可验证。
- 准备/Codex 超时后进程树退出、只产生一个 terminal、正式数据不变。
- proposal handoff 与 commit 使用同一个 run/authority；失效或变更的原 skill 不影响已准入 run。
- fixture 自动化、真实窗口和 Nocturnel 受控验证分层通过。
