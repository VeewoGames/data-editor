# 数组条目排序与行级操作采用源数组真值

<!-- document-state: accepted -->

## context

主表行可以同时处于搜索、筛选和字段排序等视图状态。此时屏幕行次序与源数组次序并不等价；若直接把屏幕索引写回，会移动错误的业务条目。另一方面，`record-map` 的键顺序没有被定义为内容排序语义，却仍需要常见的复制和删除操作。

## decision

1. 仅将根数组和根对象的顶层数组 collection 定义为可排序内容，业务文档的源数组顺序是唯一排序真值；不新增 profile 或共享视图排序配置，也不采用项目、文件或玩法白名单。
2. 搜索、筛选、字段排序及受控保存/关闭/重建状态下关闭排序入口。排序调用必须用源与目标 `rowId` 加 `before | after` 解析真实数组，不得用当前屏幕索引写回。
3. `record-map` 和嵌套数组不提供排序。`record-map` 保留复制与二次确认删除，避免将“不可排序”误解为“不可编辑”。
4. 行把手统一承载点击菜单与指针拖动：超过 4px 才开始鼠标/笔拖动；触屏与键盘不进入排序。有效落点的 pointer up 才提交重排，取消语义不产生写入。
5. 复制必须生成独立条目身份；配置了业务主键时生成不冲突的后缀值，不改写原条目或既有引用。

## alternatives

- 允许在筛选、搜索或字段排序结果中按屏幕位置拖动：拒绝，因为落点没有无歧义的源数组含义。
- 为每个项目或文件维护排序启用名单：拒绝，因为该能力由数据形状和视图状态决定，白名单会把通用编辑能力改成维护负担。
- 将 `record-map` 的对象键枚举顺序当作排序：拒绝，因为其键承担目录/唯一标识语义，不构成已定义的业务先后。
- 整行任意位置可拖动：拒绝，因为会与选中和单元格编辑意图冲突。

## consequences

- 内容编辑者只能在默认源顺序下调整实际数据顺序，避免视图临时状态被误写回业务文档。
- 行级菜单和排序共享一个明确入口，删除仍保留确认防线，复制不会制造重复稳定身份或重复业务主键。
- 新增拖动能力必须维护 `DataTable` 的回调 memo 比较、取消处理和虚拟化滚动后的落点重算；任何扩展不得绕过 `mutate` 与 `documentEtag` 保存保护。
